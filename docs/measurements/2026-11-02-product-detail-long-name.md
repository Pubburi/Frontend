# FE09 상세의 긴 상품명 레이아웃 측정

## 고정 정의와 재현 조건

시간/처리량 성능 실험이 아닌, 고정 상품명에서 전체 제목과 상세가 화면에 수용되는지 확인하는 정확성 측정이다. 기본/좁은 뷰포트는 각각1280×900·390×900 CSS px, browser zoom/device scale은 같은 Chromium context의 기본값이다. 브라우저 프로덕션 빌드의 상세 제목과 특성 읽기 완료 후 `document.documentElement.scrollWidth`와 `innerWidth`를 같은 페이지에서 읽는다. 문서 너비가 뷰포트보다 크면 해당 고정 조건1건을 위반으로 정의한다. 제목을 숨기거나 자르는 해법은 허용하지 않는다.

수정 전 기준 커밋은 main `9ebbe1f78a29d61e14ca4ff2508c9e5450746ed6`, 컴파일 원본은 추적된 src 전체의 byte가 일치하는 `96048e3d598ae812132533154148b68b5cf5c52d`이다. 동결100파일 해시는 `4ea1cdb07faffd9e3f6c5cdb2f5e0d1d8e789822fd743142f18865e4d22b3d1a`다. Java17 Backend jar SHA-256 `dcb73c35b4dbf148b05775992408b8d930977e84022fbabc878e68491ed22b81`·같은 전용 폐기 MySQL8.4·동일 시연 상품/특성·동일 브라우저/입력을 유지한다. 원본 데이터나 기존 사용자 DB를 다시 초기화하지 않는다.

상품명 `ci_jpa_h06_public_features`는 직접 만든 기술 표본이며 추천/주류 사실 자료가 아니다. 실제 측정은 위 같은 시연 상품의 공개 상세에서 수행했고 이름/필드/상태를 측정 중 바꾸지 않는다. 측정 시 네트워크 지연을 주입하거나 가장 좋은 반복을 고르지 않았으며, 각 뷰포트의 고정 관측1건을 따로 기록한다. 캐시/워밍업 조건을 시간 성과로 해석하지 않는다.

| 실제 고정 조건 | 수정 전 문서 px | 수정 후 문서 px | 수정 전 조건 위반 | 수정 후 조건 위반 |
|---|---:|---:|---:|---:|
| 390px 좁은 화면 | 451 | 390 | 1/1 | 0/1 |
| 1280px 정상 대조 | 1280 | 1280 | 0/1 | 0/1 |

after는2026-11-02 11:24 UTC에 같은 원래 진단 하네스·API jar·DB/상품·Chromium/입력에서 확인했다. 수정 후100파일과 src 전체·추가 하네스를 동결한 manifest SHA-256은 `641e2afd9cd98cc85979160b2aaaa9af5853c2c1f8736bd82a2f143540c023a2`다. 실제 좁은 화면의 문서 너비/넘친 폭은 각각 **451→390px / 61→0px**, 절대 차이는 **−61px**다. 고정 조건 위반 **1/1(100%)→0/1(0%)**는 **100%p 감소**이며 정상 대조는 **0/1→0/1**, 차이 **0%p**다.0 기준의 상대 개선율은 만들지 않는다. 이 분모는 실제 사용자 오류율이나 기기 전체 인수율이 아니다.

전후 두 뷰포트의 특성 패널 전체 문자열은 같았다. 별도 읽기 전용 확인은 제목 원문/문자 조각 좌표·현재 가격·키보드 수량2·동일 Product의 로컬 담기·검수한 빈 태그를 통과했다. 업무 API 쓰기·예상하지 않은 API 오류·pageerror·성공 응답 대체는0이었다. 추가 확인을 좁은 화면/대조의 관측 수에 합산하지 않는다. 실제390px 이미지도 직접 확인했으며 body overflow 숨김·이름 생략·clipping으로 수치를 맞추지 않았다.

## 원인 분리 — 별도 fixture

동결한 이전 프로덕션100파일에서 같은 이름을 직접 작성한 ApiResponse fixture로 제공하고, 읽기 전용 진단 스타일을 한 종류씩 적용했다.390px에서 각 변형1회이며 실제 Backend 전후 표본에 합산하지 않는다. 모든 변형에서 원문 이름을 그대로 유지했다.

| 진단 변형 | 문서 px | 정보 카드 px | 제목 px | 문자 조각 너비 px |
|---|---:|---:|---:|---|
| 원래 스타일 | 451 | 439.328125 | 397.328125 | 397.328125 |
| track/item 최소폭0만 | 430 | 366 | 397.328125 | 397.328125 |
| 제목 anywhere만 | 390 | 366 | 324 | 308.953125, 88.375 |
| 최소폭0 + 제목 anywhere | 390 | 366 | 324 | 308.953125, 88.375 |

최소폭 제약만으로 텍스트 넘침을 해결할 수 없었다. 제목 줄바꿈만으로도 이 이름은 수용되지만, 상세 컨테이너 최소폭과 제목 줄바꿈을 각각 명시했다. 페이지 overflow를 숨긴 결과가 아니며, 모든 설정이 이 표본의 복구에 필수였다는 주장도 하지 않는다. 직접 작성한 fixture의 추가320/720/721/980/1280px 경계와 실제 한 조건은 별도 근거다.

## 코드·실행과 한계

- 제품 변경: [style.css](../../src/style.css)의 상세 track·직계 카드·h1.
- 재현/회귀: [smoke.spec.js](../../tests/browser/smoke.spec.js)의 `expectReadableDetailName`과 긴 상품명 시나리오. 아래 명령의 HTML/report에 뷰포트·문서·제목/문자 조각 좌표 JSON을 첨부한다.

```bash
VITE_API_BASE_URL=/api npm run build
npm run test:browser -- --grep '긴 ASCII 상품명|허용 길이의 긴 상품명'
```

실제 상세에서도 같은 너비 산식은 다음과 같다. 제어된 뷰포트를 설정하고 상품·특성 읽기가 끝난 뒤 실행한다.

```js
({ viewportPx: innerWidth, documentPx: document.documentElement.scrollWidth })
```

API fixture의 CI 검증은 실제 DB 통합이 아니다. 실제 전후 결과는 기능/내용 보존과 위 두 화면 조건만 설명하며 모든 상품명·브라우저/배율·기기·접근성·전체 FE03/C04를 완료로 바꾸지 않는다. 원본 로그/시드·자격정보·개인 경로는 공개하지 않고 필요한 기술 원값만 위 표에 둔다.
