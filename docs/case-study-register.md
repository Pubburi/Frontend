## 선정에서 제외한 주장

- 모든 비동기/권한/저장 문제의 완료 주장: 전체 Backend 통합·런타임 세션 회수·저장 불가 시 새로고침 복원·서버 멱등성과 전체 인수 조합은 별도다.
- React 전환을 실제 추천 기능 구현·전체 FE03/C04 완료로 바꾸는 주장: 현재 실제 라우트의 React 코드 이전과 로컬 검증이며 추천/최종 인수는 별도다.
- 관리자 lazy 분리·audit/테스트 수·번들 크기를 앱 성능 개선으로 해석하는 주장: 같은 조건의 전후 성능 자료가 없다.

## 더 강한 사례의 확보·교체

2026-11-01 R01 명시취향 입력은 개인 GET/PUT·선호/필수 범위·null/[]/0·계정 전환과 늦은 응답의 소유를 구현했다. [범위·검증·한계](plans/2026-11-01-explicit-preferences-ui.md)는 새 입력 기능의 실제 근거이며 추천 품질/시간 성능이나 과거 장애 성과가 아니다. 기존 계정/캐시·비동기 사례와 겹치고 더 강한 독립적인 개선을 입증한 자료가 아직 없어 README 현재 기능만 추가하고 네 사례/순서를 유지했다.

2026-11-01 F03 관리자 특성 편집은 null/검수된 빈 태그·출처·전체 교체·상품 전환 초안 소유를 구현했다. [기능/검증 기록](plans/2026-11-01-admin-product-features.md)은 새 계약의 실제 구현과 검증이며 과거 장애·시간 개선을 주장하지 않는다. 기존 네 사례보다 더 강한 독립적 문제 해결의 근거가 아직 없으므로 README 현재 기능에만 추가하고 네 사례·순서를 보존했다.

같은 F03의 독립 코드 검토에서 초기 구현의 reconnect 재조회/폼 수명과 구분자 재직렬화의 태그 변경을 찾아 고정 브라우저 결과 위반 2/2→0/2로 수정했다. 실제 재현 근거는 보강됐지만 현재 검수 카탈로그가 없는 신규 기능의 경계 검증이며, 기존 네 사례보다 더 큰 독립적 영향을 입증한 것으로 판단하지 않아 사례 교체는 보류했다. 새로 찾았다는 이유나 숫자 개수로 선정하지 않는다.

2026-11-01 후기 응답 대기 중 새 초안/같은 후기 재편집/다른 후기 편집이 이전 성공 정리에 사라지는 문제를 재현·수정했다. [제출 초안 소유 기록](plans/2026-11-01-review-draft-ownership.md)에 원인·대안·같은 조건의 결과 위반 3/3→0/3을 남겼다. 실제 제품 결함이지만 기존 FE-CS02와 같은 비동기 상태 소유 범주이며, 저장/주문·DOM focus·계정/라우트 경계보다 더 강한 독립 사례라는 근거가 없어 README 네 사례와 순서를 보존했다. 최신성·테스트 수나 성능으로 포장하지 않는다.

2026-11-01에는 FE-CS03만 삭제 처리 중 포커스 보존으로 교체했다. 기존 API client/오류 계약과 테스트는 변경하거나 삭제하지 않는다. 이 사례는 실제 확인창 상태 전환에서 발견한 사용자 결함·응답 gate·DOM focus·listener 수명·실패 복구를 다루어 기존 공통 API 소개보다 채용 관점의 근거가 강하다고 판단했다. 다른 세 사례와 순서·총 네 개는 보존했다.

2026-10-31에는 FE-CS02의 관리자 활성 탭 조회 사례를 최신 요청 보존 사례로 교체했다. 이전 사례의 관리자 상태 분리는 코드에 유지한다. 최신 사례는 실제 URL/화면 의도와 요청 누락을 재현하고, 단순 중복 차단 해제·키 분리·전송 취소와 상태 적용 버전 검사의 차이를 설명한다. 기존 FE-CS01·03·04보다 무조건 새롭다는 이유로 교체하지 않았으며 나머지 세 사례와 순서는 보존했다.

같은 날 React 전환에서 FE-CS01/02/03의 주제는 유지하고 현재 소스·소유 경계로 갱신했다. FE-CS04만 세션/개인 캐시/보호 경로 보존으로 교체했다. 이전 보안 수정의 실제 근거는 [DEPENDENCIES](DEPENDENCIES.md)·[FE01 기록](plans/2026-10-31-fe01-dependencies.md)·PR #3에 보존한다. 교체는 React라는 이름이나 최신성 때문이 아니라 실제 호환 계약·계정 전환·실패 복구·대안 판단의 근거가 더 강해졌기 때문이다.

- React 전환의 세션·상태·라우팅 동등성, 최신 요청 우선 처리, 계정 장바구니 병합처럼 실제 사용자 경계를 다루는 구현이 완료되면 현재 4개와 비교한다.
- 새 사례의 영향·재현 조건·원인 증거·대안·선택 이유·구현 기여·재현 결과가 어느 기존 사례보다 설득력 있는지 기록한다. 단순 최신성·코드량·테스트 총수로 교체하지 않는다.
- 더 강한 사례 하나가 생기면 해당 사례부터 즉시 교체한다. 네 개가 모일 때까지 기다리지 않고, 교체 근거가 없는 나머지 내용·순서는 보존한다. 최종 README는 항상 4개를 유지한다.
- 성능 과제는 변경 전에 기준 커밋·동일 입력/부하/환경·워밍업·반복·제외 조건을 정하고 실제 기준값을 측정한다. 변경 후 원값·표본 수·중앙값/분포·절대 차이·개선율·실패/누락·한계를 남긴다. 0 기준값의 상대 개선율이나 잡음 수준 차이는 개선 성과로 쓰지 않는다.
- 테스트·CI 수치와 audit 항목 수는 정확성/보안 점검 근거로만 관리하고 앱 성능 수치로 바꾸지 않는다. README에 회귀 검증 수·목록·CI 집계를 옮기지 않는다.
