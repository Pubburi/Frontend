# R06 — 취향 검색 문구의 명시 선택과 실제 검색 연결

## 범위와 기준

기준 main `e83333a`는 F11 주문/매장 인수까지 병합·검증했고 전체 필수 기능은 **7/20(R01·F01·F03·F05·F06·F09·F11)**이다. 취향 저장과 상품 검색은 있지만, 본인 취향에서 받은 검색 문구를 별도로 선택해 실제 조건에 적용하는 화면은 없었다. 이번은 새 소비 기능의 가용성 증분이며 과거 장애나 성능 개선으로 표시하지 않는다. R06 완료/8개 집계는 실제 인수와 최신 리뷰·CI·병합/main의 최종 게이트 뒤 조정자가 판정한다.

기존 홈의 전체 주류 진입·주요 메뉴를 이용해 `/products`의 「취향 조건으로 검색」으로 연결한다. 홈에 중복 폼을 늘리지 않는다. [Backend 본인 문구 계약](https://github.com/Pubburi/Backend/blob/main/docs/SEARCH-PHRASES.md)과 [Recommendation typed wire](https://github.com/Pubburi/Recommendation/blob/main/docs/SEARCH-PHRASES-API.md)를 소비하며 제공자 생성 규칙/DB/모델을 프론트에 복제하지 않는다. 전체 F02 엔진/자동완성·FE03/C04·DB 전환의 별도 미완료는 유지한다.

## 사용자가 선택하는 경계

- 회원은 주종·맛·향·목표 도수의 네 항목을 이번 검색에 사용할지 각각 선택한다. 초기값은 모두 미선택이며 저장된 선호 자체를 바꾸지 않는다. 저장된 필수 가격·도수 범위는 제공자가 항상 적용한다.
- 「검색 문구 가져오기」를 눌렀을 때만 `POST /api/users/me/search-phrases`에 `searchOptInFields`와 `limit:5`를 보낸다. 계정 ID·취향 snapshot·임의 조건/URL은 보내지 않는다. 비회원은 고정 `/products` 링크를 사용하고 본인 POST를 호출하지 않는다.
- 문구를 가져오는 동안 현재 상품 URL·조회·미제출 입력은 유지한다. 문구의 조건을 보여주고 별도 적용 링크를 눌렀을 때만 기존 검색어·주종·범위·태그·정렬·페이지와 미제출 초안을 교체한다. 기존 값과 합치지 않으며 반환된 ordered pairs 뒤 `sort=name&page=1`을 붙인다.
- URLSearchParams로 pair를 한 번만 인코딩한다. 쉼표/개행은 단일 태그에 남기고 비ASCII 문자·대소문자·도수 소수 표기·실제0을 재작성하지 않는다. 최종 상품 수·현재 검색400·빈 결과는 실제 상품 검색 API가 판정한다.
- 제공자의 `product_count:null`은 미계산이며0으로 표시하지 않는다. 생략한 문구 수는 상품 수가 아니다. 미확인 선호·검수된 빈 배열·목표/필수 범위 충돌의 빈 문구는 전체 상품 fallback과 구분한다.

## 응답과 현재 요청의 소유

ApiResponse 안의 source/algorithm·고정 template/label·모든 typed condition·정확한 ordered query_pairs·개수/진단/분기를 검증한 뒤에만 적용 링크를 보여준다. 임의 URL·다른 query key·불일치 pair·잘못된 숫자·알 수 없는/추가 필드와 `product_count:0` 같은 wire는 적용하지 않는다. 조건을 빼서 복구하거나 클라이언트 문구를 생성하지 않는다. provider snapshot 결속은 Backend가 수행하며 프론트 검사는 이를 대신하지 않는다.

화면은 현재 세션 query 객체·계정 ID·경로 key의 새 view에 속한다. 명시 요청마다 새 revision/선택 snapshot을 사용하고 독립적인 현재 me 확인 뒤 POST한다. 선택 변경·이탈·인증 쓰기는 이전 view/요청을 잃게 하며, me가 늦게 성공해도 더 이상 현재 선택이 아니면 이전 POST를 시작하지 않는다. 이미 전송한 옛200/401은 새 선택·다른 계정·같은 계정 재로그인·경로를 바꾸지 않는다. 실패한 인증 쓰기 뒤 남은 캐시도 새 요청의 me 확인을 대체하지 않는다.

대기 동안 이전 문구는 숨기고 단일 요청을 유지한다. 현재401은 명시 재로그인과 원래 검색 경로 복귀로 처리한다.400은 저장 조건 수정,409는 현재 취향 재요청,5xx/네트워크와 `UNAVAILABLE`은 명시 재요청을 안내하며 기존 검색을 보존한다. 자동 재시도/포커스·재연결 POST나 무조건 기본 검색 이동은 없다. 오프라인에 대기 요청을 큐잉하지 않고 명시 시도 결과를 표시한다. 문구/선택/계정 snapshot은 디스크에 저장하지 않으며 카트·F05/F06 보관 정책은 바꾸지 않는다.

## 구현 전에 고정한 검증

기준 소스78/production100파일·README와 수용 기준·실제 관찰 하네스를 제품 편집 전에 고정했다. 실제 하네스는 같은 Backend/Recommendation과 자체 작성 계정·별도 시연 대조 상품만 사용한다. 원본80상품·기존 사용자 DB를 수정하지 않는다. 실제 본인 문구 POST/독립 상품 GET·인증 대조와 업무 데이터 쓰기를 구분하고 자격 값은 결과에서도 마스킹한다.

로컬 단위/production Chromium은 명시 opt-in·hard 보존·0/Decimal scale/리터럴·typed wire 거부·unknown/empty/conflict·400/401/409/503/UNAVAILABLE·초안/URL 보존·늦은 me/POST·계정/ABA·불확실 logout과1280/390px 키보드를 확인한다. 기존 필터/초기화/Back·F05/F06/F09/주문·Product7 카트·소수 평점·저장 거부는 전체 검사로 유지한다. API fixture의 제어 경합과 실제 세 서버 근거를 합산하지 않는다.

초기 선택17조건은14개 성공/3개 작성 전제 실패였다. 두 보류 응답의 중복 전송 검사는 aria-disabled 버튼을 Playwright click으로 눌러 도구가 활성화를 기다렸다. native Enter로 실제 실행 guard를 검사하도록 바꿨다. 복귀 주소 한 검사는 브라우저의 한글 percent encoding과 원문 문자열을 비교했으며 resolved URL 동일성으로 고쳤다. 원 spec·trace·JUnit·로그를 보존하고 timeout/retry/skip을 늘리지 않았다. 제품 실패/개선 수치로 넣지 않는다. 별도 소스 검토에서는 enum 검사가 배열을 문자열로 변환할 수 있던 경계를 엄격한 string 검사와 배열/객체 거부 단위로 보완했다.

초기 전체 검사는 단위158개·브라우저354개를 통과하고 기존 Shift+Tab 한 조건이 실패했다. 새 비회원 기본 링크가 결과 region 바로 앞의 조작이 되었는데 기존 검사가 그 자리를 전체 해제 버튼으로 고정했기 때문이다. 원 보고서를 보존하고 실제 이전 링크로 이탈한 포커스가 응답 뒤에도 유지되는지 같은 의미의 assertion을 보완했다.

그 뒤 초기 미병합 후보에서 이미 적용한 문구와 동일 URL을 재적용할 때 새 미제출 입력이 남는 결함을1280/390px 두 조건 모두 재현했다. 상품 폼의 복원이 URL 문자열 변화에만 의존해 같은 주소의 새 경로 key에서는 실행되지 않는 원인이었다. 일반 현재 탭 적용만 부모의 초안/검증 상태를 정확한 조건으로 동기 복원하도록 최소 callback을 추가했다. 전체 URL effect·페이지/검색 소유는 바꾸지 않고 modifier 새 탭에서는 부모 입력을 보존한다. 같은 조건의 native modifier 새 탭/부모 보존은 수정 전부터 정상이며 이를 실패로 세지 않는다.

재현 준비 중 implicit select의 exact label이 option 문자열을 포함하던 선택자와, 새 탭이 page-only fixture 밖으로 나가던 전제를 각각 원 보고서로 보존했다. 기존 combobox 역할/이름과 context 전체 API fixture·새 탭 관측으로 정정한 뒤 제품 원값을 고정했고, 이 도구 실패를 위 제품 두 조건이나 자연 오류율에 더하지 않는다. 첫 후보 소스/빌드·전체 검사와 실제 성공 근거도 최종 후보와 구분해 보존한다.

보완한 동일 두 조건은 위반2/2→0/2였고 전체 R06 선택22조건과 기존 페이지 포커스10조건을 같은 production 빌드에서 통과했다. 이 수용 결함은 초기 미병합 후보의 결과이며 기존 main 장애나 성능 개선으로 확대하지 않는다. 최종 실제 하네스에도 같은 URL/새 탭 관측만 추가하고 원 하네스/보고서를 보존한 뒤, 개정한 같은 바이트로 원 기준/최종 후보를 다시 대조한다.

## 최종 로컬 검사와 실제 연결

보완 후 Node24.22.1 `npm run check`는 exit0으로 완료했다. 저장소 검사·locked 설치·audit0·이미지 도구·strict TypeScript·단위158개·production 빌드·Chromium357개를 통과했다. 두 JUnit의 새 시각/실제 testcase와 실패·오류·skip0을 확인했다. 새 단위25개와 R06 브라우저22조건은 전체 수에 포함되며 별도로 더하지 않는다. 초기 전체 검사와 원 후보/실패 trace는 최종 결과로 덮어쓰지 않았다.

최종 소스83파일·production100파일·테스트/설정15파일을 불변 해시로 고정하고 실제 실행 뒤에도 같은 바이트임을 확인했다. 개정 실제 하네스(SHA-256 `7f8ef33d4b77378ca5dac836e95946c0fccf65b76619dc2a2b0f3b187fd0c43e`)를 원 기준과 최종 후보에 동일하게 사용했다. 원 하네스/첫 실제 성공 근거는 별도로 보존한다.

원 main 기준은1280/390px에서 새 영역 부재와 독립 본인 문구/상품 GET의 정상 참조를 확인했다. 최종 legacy MySQL과 별도 TLS PostgreSQL/JPA·고정된 실제 Recommendation에서는 각각 두 폭에서 다음을 확인했다. 기준/최종 Backend JAR은 구분하고 각 실행의 실제 현재 응답을 독립 대조했다. 동일 JAR의 과거 장애 개선이나 모든 DB 전환으로 표현하지 않는다.

최종 각 제공자 실행의 화면 문구 POST는14회, 독립 대조 POST는6회다. 취향/상품/주문 등 화면 업무 쓰기는0이고 인증 대조/작성 fixture 준비·정리는 별도로 관리했다. 예상외 API/pageerror·응답 대체는0이었다. 원본80상품·5매장·기존 사용자 자료를 보존하며 작성 계정과 새 대조 상품만 사용했다. 실제 이름/자격·개인 경로는 공개 근거에 넣지 않는다.

각 실제 실행의 소유 세 프로세스 종료와 새 대조 상품 정리를 확인했고, 세 전용 DB의 원본 범위 해시도 불변이었다. 사용자 공유 서버/원본 DB를 검증용으로 기동하거나 수정하지 않았다.
