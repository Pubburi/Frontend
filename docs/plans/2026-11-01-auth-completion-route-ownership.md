# FE03 — 늦은 인증 성공과 현재 경로의 소유 분리

## 기준·고정 조건과 사전 재현

기준 main `16c8dd6b`의 프로덕션 웹100파일, 입력·하네스와 사전 결과를 불변 보존했다. 기존 AccountPage는 로그인 또는 가입 후 자동 로그인 성공 뒤 제출 당시 redirect로 항상 navigate했다. 그 사이 사용자가 다른 화면을 선택하고 폼이 사라져도 성공 callback은 계속 살아 있었다.

Node24·Chromium·독립127.0.0.1 OS 동적 포트의 같은 API fixture에서 다음 두 조건을 각1회 확인했다. 로그인200 전달만 보류하고, 사용자가 `/products`로 SPA 이동해 상품 목록을 확인한 뒤 원래 성공을 해제한다. 로그인 시도의 옛 목적지는 `/cart`다.

| 고정 조건 | 기준 완료 후 | 수정 완료 후 | 인증/쓰기 확인 |
|---|---|---|---|
| 기존 회원 로그인200 | 옛/cart로 강제 이동 | 현재/products 유지 | 헤더 본인 반영·로그인1회 |
| 가입201 후 자동 로그인200 | 옛/cart로 강제 이동 | 현재/products 유지 | 헤더 본인 반영·가입1/로그인1회 |

동일 하네스(`62f0d191b444…`)/입력과 불변 기준/수정 생산 빌드의 경로 소유 위반은 **2/2→0/2**, 고정 집합의 위반 비율은100%→0%(100%p 차이)다. 양쪽 인프라는 성공했고 예상외API·pageerror는 없었다. 제어한 응답 전달 경합의 기능 정확성 관측이며 자연지연·실사용 오류율·서비스 성능이 아니다. 앞선 가입201 뒤 자동 로그인 실패 복구와 다른 **성공 완료의 화면 이동** 경계다.

## 원인과 구현

서버 로그인과 전역 session 반영은 완료되어야 하지만, 사라진 폼이 현재 라우터를 조작할 권한까지 갖는 것은 아니다. 로그인을 취소한 척하거나 성공을 무시하면 이미 발급된 서버 세션과 웹의 인증 캐시가 다시 어긋나므로 채택하지 않았다.

- 시작 시 location.key와 검증한 안전한 redirect를 캡처한다. 성공의 폼 정리/옛 redirect는 해당 AccountPage가 여전히 mounted이고 현재 location.key도 같은 경우에만 수행한다.
- 서버의 실제 로그인200, 기존 cache.clear와 session 계정 반영은 위치와 독립적으로 유지한다. 새로 선택한 공개 화면에서도 현재 로그인 헤더를 반영하며 개인 캐시 정리 정책을 완화하지 않는다.
- 같은 URL로 나갔다 재진입한 새 폼은 이전 컴포넌트의 mounted 소유를 받지 않는다. 같은 폼에서 redirect만 바꾼 경우도 새 location.key를 따르고 현재 guest guard의 목적지를 보존한다.
- 가입201 뒤 자동 로그인 실패의 완료 사실/전역 안내는 유지한다. 로컬 복구 폼 전환은 실제로 남은 컴포넌트에만 적용하며 비밀번호를 storage에 보관하지 않는다. 기존 singleflight·pending 자격 잠금·가입 실패/명시적 재시도는 유지한다.

탐색 링크 전체를 막거나 HTTP 성공을 화면 이탈만으로 롤백하는 대신 서버 인증 수명과 UI 이동 수명을 구분했다. 여러 탭의 로그인 순서·동시에 외부에서 수행한 세션 변경까지 새로 조정하는 기능은 아니다.

## 회귀와 상태

새 production browser 회귀는 고정 두 성공 이탈 조건, 동일URL뒤로 재진입·새 redirect 재진입, 같은 컴포넌트에서 redirect만 변경하는 경계다. 기존 정상 가입/로그인 목적지·가입 완료/자동 로그인 실패·중복 생성 방지·계정 전환/개인 캐시·장바구니/미제출 요청 회귀도 유지한다. 추가 경계를 두 고정 조건의 분모에 합산하지 않는다.

Node24 `npm run check`의 저장소 검사·locked 설치·audit(취약점0)·이미지 도구·strict TypeScript·단위62개·프로덕션 빌드·Chromium149개가 통과했다. 새 경계는 위 브라우저5개이며 테스트 집계는 서비스 성능이 아니다. 최종100파일의 물리 manifest SHA는 `b7fd8ea0b522…`, compact 파일 목록 SHA는 `2f482948d881…`다. 그 동결 빌드에서도 같은 하네스의 두 조건0/2·인프라 성공을 확인했다.

4173은 기존 listener 없음 확인 후 자체 preview를 사용하고 종료 후 listener 없음도 확인했다. 독립 전후 하네스는 별도 OS 동적 포트에서 실행·정리했다. 위 fixture는 실제 Backend/DB E2E가 아니며 별도 실제 서버 결과도 아래 조건에서 확인했다. 최신 head 리뷰/CI·병합/main CI는 별도 게이트이며 전체FE03/C04·PostgreSQL DB06과 신규 사용자 기능을 완료로 체크하지 않는다.

## 실제 서버 비교 절차

1. 조정자가 같은 seed·고정 기존회원/신규가입ID·비밀번호·입력 namespace를 한 runner에서 before/after의 별도 폐기 DB에 공유한다. 기존회원은 실제 POST201로 사전 준비하고 신규가입ID는 비워둔다. 현재 MySQL은 PostgreSQL 이관 전 회귀 기준이다.
2. 기존회원 로그인/신규UI가입201 후 자동 로그인에서 실제 POST/auth/login을 route.fetch로 서버에 보낸다. 실제200·현재USER 본문을 확인하고 **해당 APIResponse의 브라우저 전달만** 보류한다. 원응답을 그대로 fulfill하며 성공 상태/본문을 합성하지 않는다.
3. 사용자가 SPA 상품 목록으로 이동해 목록을 확인한 뒤 원응답을 해제한다. 현재 경로·헤더와 별도 실제 auth/me의 동일 본인/USER를 함께 확인한다. 각 로그인1회·UI가입1회 여부도 확인한다.
4. 별도 stay 대조군은 폼에 그대로 둔 두 흐름의 정상/cart redirect를 확인한다. 기존회원은 같은 사전 계정을 새 context에서 사용하고 신규 대조군은 별도의 고정 추가ID로 UI가입한다. 이 대조군은 이탈 두 조건의 분모에 합산하지 않는다.

각 조건은 새 브라우저 context를 사용하며 기존 사용자DB/공유 포트를 쓰지 않는다. 최초 비회원 auth/me401만 정상 응답으로 구분하고 예상외 API·JavaScript 오류/인프라 실패는 경로 위반과 분리한다. 원문 하네스·보고서·불변100파일·개인 경로·실제 자격은 ignored 기록에 보존한다.

## 실제 서버 전후 결과

동일 Backend jar(`dcb73c35b4db…`)·고정 Recommendation B0·Java17/MySQL8.4/Node24/Chromium을 사용했다. 최초 상품80개의 같은 seed로 만든 별도 폐기 before/after DB에 한 runner의 같은 기존회원ID·신규가입ID·비밀번호·namespace를 공유했다. 기존회원은 실제 POST201로 준비하고 신규ID/정상대조군의 별도 추가ID는 각각 UI가입했다. 기준 main `16c8dd6b`와 수정의 불변 웹100파일(물리 manifest `0c2ac55f0433…`/`b7fd8ea0b522…`) 및 같은 하네스(`a78ba6fa5542…`)를 실행 전에 확인했다.

경로 소유 위반은 **2/2→0/2**, 고정 집합의 위반 비율은100%→0%(100%p 차이)였다. 양쪽 인프라는 성공했다. 실제 로그인은 모두 성공했고 기준의 문제는 세션 실패가 아니라 옛 화면의 추가 navigate였다. 수정에서도 서버 인증·현재 본인 헤더를 유지하면서 사용자가 선택한 공개 경로를 보존했다.

### 별도 정상 대조군과 한계

두 빌드 각각에서 폼에 머문 기존회원 로그인과 신규회원 자동로그인을 각1회 확인했다. 둘 다 옛 제출이 여전히 현재 의도인/cart로 정상 이동해 **정상 대조군 위반은 양쪽0/2**였다. 이 결과는 이탈 두 조건과 별도이며 분모에 합산하지 않는다. 같은URL/새redirect 재진입·같은폼의redirect 변경은 앞의 추가 production fixture 근거다.

서버에 실제 로그인 요청을 먼저 보내 확인한 성공 응답의 전달만 제어했다. 성공API 응답 합성·예상외 API 오류·pageerror는 없었고 웹 프록시→Backend→고정 Recommendation의 기본 목록 BASELINE도 확인했다. 자연 지연/실사용 오류율·시간 성능·추천 품질 성과가 아니다. 이전 가입 실패 복구/개인 캐시 검증의 분모와도 섞지 않는다.

현재 MySQL API의 PostgreSQL 이관 전 회귀 기준이다. 제공자 전환 뒤 API·세션 쿠키/계정·현재 경로/정상 목적지를 다시 확인해야 하며 DB06·전체FE03/C04를 완료로 바꾸지 않는다. 브라우저/보조기술·여러 탭과 외부 세션 변경의 전 조합을 확인한 것도 아니다.
