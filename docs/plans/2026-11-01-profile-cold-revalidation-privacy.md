# FE03 — 데이터 없는 401 재검증 중 개인 캐시 차폐

## 기준·조건과 사전 관측

기준 main `5050891`의 프로덕션 웹 100개 파일과 최초 재현 결과를 불변 보존했다. 앞선 [명시적 로그인 복구](2026-11-01-profile-session-recovery.md)의 실제 서버 두 조건과 별개의 추가 경계다. 그때는 두 조회가 401인 복구 흐름과 이미 성공 데이터가 있는 profile의 재검증을 확인했으며, 이번에는 **profile은 데이터 없는 최초 401, orders는 기존 200 개인 캐시**인 조건을 고정했다.

Node 24·Chromium의 독립 127.0.0.1 동적 포트에서 같은 직접 작성한 API fixture를 사용했다. 시연 USER의 profile 첫 GET은 401, orders 첫 GET은 자체 작성한 주문 1건의 200이다. 재연결로 발생한 두 번째 GET은 모두 응답을 보류하고, 관측 후 실제 fixture 401로 완료한다. 별도 DB·서버·공유 서비스는 실행하지 않는다.

| 고정 1조건의 관측 시점 | 기준 main | 수정 웹 |
|---|---|---|
| 최초 profile401/orders200 완료 | 재로그인 조작 표시·주문 숨김 | 동일 |
| 재연결 두 GET 응답 보류 | 조작 사라짐·기존 주문 1건 재표시 | 조작 비활성·기존 주문 숨김 유지 |
| 두 GET401 완료 | 조작 복원·주문 숨김 | 조작 활성·주문 숨김 유지 |

같은 입력/하네스(`c6302fcabb2b…`)와 불변 기준/수정 프로덕션 빌드에서 각 한 번 확인했다. 개인 캐시 재노출 위반은 **1/1 → 0/1**, 이 고정 집합의 비율은 100% → 0%(100%p 차이)다. 양쪽 인프라는 성공했고 예상외 API·pageerror는 없었다. 기준의 실패 종료는 재노출 관측이며 준비/실행 실패와 구분했다. 최초 읽기 전용 관측도 별도로 보존했다.

자체 API fixture의 응답 보류 조건이며 실제 Backend 통합·자연 장애율·다른 계정 정보 유출·지연/성능 측정은 아니다. 앞선 실제 서버 두 조건의 분모에 합산하지 않는다. 서버 API와 PostgreSQL 이관 구현은 변경하지 않는다.

## 원인과 선택

TanStack Query는 데이터 없는 실패 query를 refetch할 때 status를 pending으로, error를 null로 바꾼다. 기존 화면은 현재 result.isError의 401만 찾았으므로 이미 관측한 인증 실패를 잃었다. 같은 시점에 다른 query는 200 데이터를 보존해 주문 내역을 다시 그렸다. 이 관측의 수명은 현재 error 필드보다 길다.

컴포넌트 state에만 기억하면 응답 보류 중 화면 이탈/재진입에서도 다시 잃을 수 있어 QueryClient 수명의 작은 profile 전용 관측 저장소를 두었다. 저장하는 것은 현재 session query/계정 객체, 실패 query 객체와 그때의 dataUpdateCount다. 원문 데이터·인증 정보·브라우저 storage에 새 항목을 기록하지 않는다.

- 현재 본인의 profile/orders에서 실제 error 갱신으로 관측한 ApiClientError401만 등록한다. 다른 계정·다른 API·최초403/5xx는 관측을 만들지 않으며 전역 로그아웃도 없다.
- 같은 실패 query의 pending/paused·다른 query200·기존 dataUpdateCount는 관측을 해제하지 않는다. 같은 query의 실제 fetch 성공으로 dataUpdateCount가 증가하거나 실제 인증/query 소유가 교체·제거되어야 해제한다. setQueryData의 수동 캐시 갱신도 인증 확인이 아니므로 해제 근거로 삼지 않는다.
- 그동안 두 개인 내용은 함께 숨긴다. 현재 인증/실패 query가 fetching 또는 paused면 복구 조작도 기다린다. 조작 직전 현재 저장소/인증/query 소유와 진행 상태를 재검사한다.
- 401 뒤503 등 새 인증 확인 없는 실패도 차폐를 유지한다. 조회가 idle로 끝났다면 사용자가 명시적 재로그인을 선택할 수 있다. 이를 자동 로그아웃·성공 확인으로 바꾸지 않는다. 같은 실패 query의 새200이면 기존 현재 결과로 복원한다.
- query 제거/인증 초기화 시 해당 관측을 버리고, 같은 ID 재로그인·다른 계정의 늦은 이전 HTTP가 새 query에 붙지 않게 한다. 기존 장바구니/미제출 요청과 API 계약은 유지한다.

모든 개인 조회를 무조건 단일 로딩 화면으로 합치거나, 오류 코드가 사라진 errorUpdateCount만으로 판단하는 방식은 택하지 않았다. 401을 실제로 관측한 현재 소유와 후속 권위 성공을 구분하는 범위로 한정했다. 저장소는 QueryClient별이며 query 제거/인증 교체에 정리한다.

## 검증과 완료 상태

관측 저장소 단위 검증은 cold pending·paused, 다른 조회200/기존 dataUpdateCount·수동 캐시 갱신, 뒤503/새 fetch 성공, query 제거/재생성, 같은 ID/다른 계정의 늦은 이전 오류, 최초403/503의 독립 정책을 확인한다. 추가 브라우저는 cold401 후 재연결의401/503/새 성공과 보류 중 화면 재진입·offline paused 재진입을 확인한다. 이 추가 조건을 고정 한 조건이나 앞선 실제 두 조건에 합산하지 않는다.

기존 명시적 복구의 실제 두 조건은 역사 근거로 보존하며, 이번 변경 후의 계정 세대/기존 정책·장바구니/요청은 기존 production fixture 회귀와 함께 다시 확인했다. Node 24 `npm run check`의 저장소 검사·locked 설치·audit(취약점0)·이미지 도구·strict TypeScript·단위62개·프로덕션 빌드·Chromium140개가 통과했다. 새 단위는9개, 새 브라우저 경계는4개이며 이 집계는 서비스 성능이 아니다.

최종100개 파일의 물리 manifest SHA는 `8e74016ef3b6…`, compact 파일 목록 SHA는 `3cbfc118df34…`다. 최종 빌드로도 같은 하네스/동일 fixture를 실행해 위 추가1조건의 재노출 위반0/1·인프라 성공을 확인했고, 기준/수정의 API 시작/응답 순서도 같았다. 로컬 최종 검사 preview는4173의 기존 listener가 없음을 먼저 확인해 시작했고 종료 뒤 listener 없음도 확인했다. 독립 비교는 별도 OS 동적 포트만 사용했다. 원문 도구·동결 전후100파일·수동 캐시 인증 경계 추가 전의 중간 결과는 ignored 기록으로 구분 보존했다. 이번 추가 fixture를 실제 서버 전후 비교로 바꾸어 표현하지 않는다. 최신 head의 리뷰/CI·병합/main CI는 별도 게이트다.

전체 FE03/C04·PostgreSQL DB06은 여전히 미완료다. PostgreSQL 기반 서버에서 기존 API/세션 오류·복귀를 다시 확인해야 하며, 실제 세션 만료의 모든 타이밍·다중 창 동기화·모든 브라우저/보조기술을 보장하는 변경은 아니다.
