# FE03 상품 페이지 이동의 적용 검색 조건 보존

## 범위·기준

- 기준 main은 `895c6c7`이다. 검색 결과의 이전/다음 페이지가 아직 제출하지 않은 검색어·주종·정렬을 함께 전송하던 기존 고객 탐색 결함만 수정한다.
- 기존 `/api/products`·ApiResponse·페이지 크기12·상품 일곱 필드·URL query와 Query key를 유지한다. 가격/도수/태그 필터를 추가하거나 F02·전체 FE03/C04를 완료로 바꾸지 않는다.
- 기존 검색 초안 칩과 전체 해제 동작은 보존한다. 페이지 이동은 현재 URL의 적용 조건을 따르며, 검색하기나 Enter로 새 초안을 제출하면 첫 페이지로 이동한다. URL이 바뀐 뒤 입력값을 URL에서 복원하는 기존 동작도 유지한다.

## 문제·원인

`type=탁주&q=시연&sort=name&page=1`의 결과를 읽은 뒤 검색어·주종·정렬 중 하나를 편집만 하고 다음을 누르면, 편집값이 검색하기 없이 `page=2`에 적용됐다. 다른 검색의 첫 페이지를 건너뛰거나 기존 결과가 빈 화면으로 바뀔 수 있었다.

화면에는 URL에서 해석한 `filters`와 입력 중인 `form`이 따로 있었지만 검색 제출과 페이지 이동이 같은 `navigate`를 호출했다. 이 함수는 항상 `form`을 직렬화했다. Query key는 잘못 제출한 조건의 응답을 올바르게 분리할 뿐, 제출 의도 자체를 교정하지 못한다.

페이지 이동은 `filters`, 명시적 검색 제출은 `form`을 전달하도록 같은 URL 작성 함수의 입력만 구분했다. 입력할 때마다 자동 검색하는 대안은 기존 명시 제출과 초안/초기화 동작을 바꾸므로 선택하지 않았다. 페이지 버튼을 막거나 이전 응답을 취소하는 방식으로 조건 선택 문제를 해결하지 않는다.

## 사전 고정·프로덕션 fixture 검증

제품 소스를 바꾸기 전에 기존100개 프로덕션 파일·기준 소스와 작성한 시나리오의 SHA-256을 고정했다. 직접 작성한 탁주14개에서 검색어·주종·정렬을 각각 미제출로 바꾸고 다음을 누르는 세 조건을 같은 Chromium/프로덕션 파일에 먼저 실행했다. 세 조건 모두 URL assertion에서 실패했고, 실제 URL에 미제출 값과 `page=2`가 함께 들어갔다. 고정 조건 위반은 **3/3→0/3**이다.

첫 실행의 sandbox loopback EPERM과 동적 포트를 worker마다 다시 고른 설정의 connection refused는 하네스 준비 실패로 보존했다. 제품 소스/시나리오를 바꾸지 않고 한 동적 포트를 전체 실행에 전달하도록 고친 뒤 위 baseline을 재현했다. 준비 실패를 제품 결함 분모에 넣지 않는다.

```bash
npm run typecheck
VITE_API_BASE_URL=/api npm run build
npm run test:browser -- --grep '상품 페이지 이동은 미제출|다음 페이지의 검색 초안|이전 페이지의 늦은 응답|390px 키보드 페이지 이동|기본 검색 URL에서 미제출|진행 중 검색'
npm run check
```

선택한 프로덕션 Chromium8개에서 다음을 확인했다.

- 미제출 검색어·주종·정렬 각각의 페이지 이동이 원래 URL/API 조건과 두 번째 페이지 상품을 유지한다.
- 새 초안의 Enter 제출은 첫 페이지를 표시하고 뒤로 가기는 이전 검색·페이지·입력값을 복원한다. 전체 해제는 기본 첫 페이지로 돌아간다.
- 이전 페이지 GET을 보류한 동안 새 검색을 제출해도 늦은 이전 응답이 새 결과를 덮지 않는다.
- 390px 웹의 Enter 페이지 이동·결과·가로 너비와 기존 미제출 칩/해제 동작을 유지한다.

fixture는 실제 주류/추천 자료나 Backend 통합 E2E가 아니다. 위 정확성 재현을 자연 발생 오류율이나 시간 성능 개선 수치로 바꾸지 않는다. 실제 서버의 별도 한 조건/정상 대조와 fixture 세 조건을 합산하지 않는다.

Node **24.22.1**의 전체 `npm run check`에서 저장소 검사·locked 설치·audit 취약점 **0**·이미지 도구·strict TypeScript·단위 **76개**·프로덕션 빌드·Chromium **201개**가 통과했다. 최종100개 프로덕션 파일과 소스/시나리오를 SHA-256으로 동결했고 검사 뒤 같은 byte임을 확인했다. 자체 preview는 종료했고 기존 사용자 프로세스를 변경하지 않았다. 최신 PR/CI·완료 Codex 리뷰·미해결 대화·병합/main CI와 정리는 조정자가 확인한다.

## 별도 실제 서버 확인

같은 불변 legacy Backend jar(SHA-256 `dcb73c35b4dbf148b05775992408b8d930977e84022fbabc878e68491ed22b81`), 폐기 MySQL의 같은80개 시연 상품, 고정 Recommendation `d0e333a`와 기준/후보 프로덕션 웹을 사용했다. 두 웹에 같은 Chromium/1280px·읽기 전용 하네스(SHA-256 `4a6594f1d4f2c4c392e5e3d20f0c5798d07d9bd4362acc44b6f1e859a6e0a35a`)를 적용했다. 성공 응답을 대체하지 않았고 업무 API 쓰기는 없었다.

전체 상품의 `sort=name&page=1`에서 검색어·주종·정렬을 편집만 하고 다음을 누르는 **실제 한 조건**을 확인했다. 기준 웹은 미제출 검색어·사케·priceDesc와 page2를 전송해0개를 표시했다. 후보 웹은 원래 sort=name/page2와12개 상품을 표시했고, 상품 ID/표시 이름은 초안을 바꾸지 않은 정상 대조와 같았다. 고정 실제 조건 위반은 **1/1→0/1**이며 별도 정상 대조는 **0/1→0/1**이다. fixture 세 조건이나 좁은 웹 결과와 합산하지 않는다.

예상하지 않은 API 오류·pageerror·응답 대체·업무 쓰기는 없었고 별도 기본 추천은 BASELINE이었다. 원본 DB/기존 사용자 프로세스를 사용하지 않았으며 조정자가 시작한 검증 프로세스만 정리했다. 이는 고객 페이지 이동의 선택한 실제 연결 근거이며 전체 FE03/C04·JPA/DB 전환·자연 오류율·시간 성능 인수가 아니다.

## README 사례 판단·인계

실제 검색 의도와 URL 경계의 작은 결함이지만 현재 네 사례의 주문 입력 소유, 경로별 최신 응답, 파괴적 작업의 DOM 포커스, 인증 캐시와 진행 중 HTTP보다 더 강한 독립 원인/영향을 입증하지 못했다. README 전체와 네 사례/순서를 보존하고 [선정 기록](../case-study-register.md)에 비교 이유만 남긴다. 테스트·CI 집계는 README에 옮기지 않는다.

비공개 기획 주소·개인 경로·자격정보·원문 로컬 로그는 공개 문서/PR에 포함하지 않는다. 원본 DB/공유 포트·다른 저장소를 변경하지 않으며 실제 서버 검증은 조정자의 소유 자원에서 진행한다.
