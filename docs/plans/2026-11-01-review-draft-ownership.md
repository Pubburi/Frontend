# FE03 후기 저장 완료와 현재 초안의 소유 분리

## 범위와 기준

- 기준 main: `0de9768c00972833398dc3596a2a6314411b1055` (`#10`). 고객 상품 상세의 기존 후기 등록·수정만 변경한다.
- FE02 코드 이전을 반복하거나 새 R/F 기능을 추가하지 않는다. 후기 API·세션·쓰기 singleflight·상품 ID/query key·삭제 확인창·장바구니·CSS/자산은 유지한다.
- FE03의 쓰기/입력 경계를 검증하는 작은 수정이다. 전체 FE03/C04, 실제 Backend 통합, 원격 PR/CI·리뷰·병합 완료와 구분한다.

## 관측·원인

현재 등록 textarea와 편집 입력은 전송 중에도 새 입력을 허용하며 편집 취소도 가능하다. 그러나 등록 성공은 무조건 `setText('')`, 수정 성공은 무조건 `setEditing(null)`을 실행했다. 서버에 보낸 내용과 그 뒤 사용자가 작성한 현재 초안을 구분하지 않아, 정상 성공 응답이 오히려 새 입력을 잃게 했다. 쓰기 중복 차단이나 조회 query key는 이 로컬 입력 정리의 소유를 해결하지 않는다.

수정 전에 자체 ApiResponse fixture로 응답을 Promise gate에 보류한 프로덕션 Chromium에서 아래 세 고객 흐름을 재현했다. 임의의 대기 시간으로 경합을 우연히 만들지 않고 요청 수신→새 입력→gate 해제 순서를 고정했다.

| 고정 시나리오 | 수정 전 결과 위반 | 수정 후 같은 결과 위반 |
|---|---:|---:|
| 후기 등록 전송 뒤 다음 본문·평점 입력 | 1/1: 새 본문이 빈 값으로 변경 | 0/1 |
| 수정 전송 뒤 취소하고 같은 후기를 같은 내용으로 다시 편집 | 1/1: 새 편집창 제거 | 0/1 |
| 수정 전송 뒤 취소하고 다른 후기 편집 | 1/1: 다른 후기 편집창 제거 | 0/1 |
| 합계 | **3/3** | **0/3** |

조건은 Node 24·locked 의존성·Vite `/api` 프로덕션 빌드·Playwright Chromium/Desktop Chrome 기본 1280×720·같은 회원/상품/자체 후기 fixture다. 기존 DB·공유 서버·외부 서비스는 사용하지 않았다. 기준 dist와 변경 후 dist의 파일별 SHA-256은 ignored 인계에 기록한다. 최초 검증 준비에서 select의 실제 접근 이름과 맞지 않는 exact-label selector를 고친 시도는 제품 결함 분모에 넣지 않았다.

이 분모는 정해진 회귀 흐름의 정확성이고 실제 사용자 오류율·추천 품질·시간 성능이 아니다. 전후 지연·로딩 시간이나 오류율 상대 개선을 산출하지 않았다.

## 선택과 구현

등록의 평점/본문을 하나의 불변 초안으로 관리하고, 등록·수정 시작 시 제출한 객체를 보관한다. 성공 뒤 함수형 setter가 **현재 초안이 제출한 객체와 동일할 때만** 내용을 비우거나 편집을 닫는다. 입력 변경이나 취소 후 다시 편집하기는 새 객체를 만들므로, 같은 후기 ID·같은 본문으로 돌아와도 새 편집 세션을 이전 완료가 정리하지 않는다. 조회 갱신은 계속 실행해 실제 서버 저장 결과를 목록에 반영한다.

- 새 입력이 없었던 등록 성공은 본문을 비우고 평점을 유지한다. 새 입력이 없었던 수정 성공은 편집을 닫는다.
- 응답 대기 중 바꾼 초안·다시 연 편집은 유지한다. 자동으로 재전송하거나 최신 초안을 이미 저장한 것처럼 서버 payload를 바꾸지 않는다.
- 요청 실패는 기존 오류 계약으로 안내하고 현재 초안을 유지한다. 등록 재시도는 사용자의 다음 제출로만 실행한다.
- 기존 편집 취소는 편집창 닫기이며 이미 전송한 서버 작업을 취소하지 않는다. 전송 취소·서버 멱등성은 이번 변경에 추가하지 않는다.

대안으로 전송 중 모든 입력/취소를 잠글 수 있지만 기존의 다음 입력·편집 전환을 막는다. 문자열/후기 ID만 비교하면 같은 내용을 다시 입력하거나 같은 후기를 다시 여는 세션을 구분할 수 없다. 별도 전역 버전 카운터나 상태 라이브러리 추가 대신 기존 React 불변 상태의 정체성과 함수형 updater로 정리의 소유를 제한했다. 객체를 직접 변경하지 않는 현재 입력 패턴을 유지해야 한다.

공식 근거: [React useState의 updater와 객체 상태](https://react.dev/reference/react/useState). 현재 상태로부터 다음 상태를 결정하는 updater와 객체 교체 규칙을 적용했다.

## 검증

```bash
VITE_API_BASE_URL=/api npm run build
npm run test:browser -- --grep '초안을 지우지|취소 뒤 다시'
npm run check
```

앞의 세 동일 재현은 수정 후 모두 통과했다. 추가 브라우저 회귀는 편집창을 닫지 않고 계속 입력한 수정, 등록 503 뒤 초안 보존·명시적 재제출·서버 반영, 기존 변경 없는 성공 뒤 초기화를 확인한다. 각 요청 payload·횟수와 서버 fixture 내용도 확인해 초안 보존을 자동 중복 저장이나 미저장 내용의 서버 반영으로 혼동하지 않는다. 기존 후기 CRUD·최신 조회·장바구니·권한·관리자·확인창 키보드 회귀를 함께 실행한다.

최종 `npm run check`는 Node 24.22.1에서 저장소 검사·locked 설치·audit 0·PNG/방향 JPEG 변환·strict TypeScript·단위 25개·프로덕션 빌드·Chromium 25개를 통과했다. Chromium은 기존 20개와 이번 5개 흐름이며 미처리 API·pageerror도 없었다. source 변경 후 이 전체 검증은 한 번 실행했고, 이후에는 문서/인계만 정리했다. 원격 PR/필수 CI·최신 head 리뷰·main 반영·실제 서버의 새 흐름 확인은 조정자가 별도로 관리한다. 테스트 수·CI 시간을 앱 성능으로 사용하지 않는다.

## 대표 사례 비교와 남은 경계

이번 후보는 파괴적인 비동기 초안 정리의 실제 원인·같은 값의 새 편집 구분·대안·수정 전후 재현이 있는 제품 개선이다. 다만 기존 FE-CS02의 검색/상세 경로별 응답 격리와 같은 비동기 상태 소유 범주에 속하고, FE-CS01의 저장 실패/성공 주문, FE-CS03의 파괴적 확인창·DOM focus 수명, FE-CS04의 계정/캐시/라우트 이전보다 독립적으로 더 강한 영향을 입증한 것은 아니다. 최신성이나 회귀 개수로 강제 교체하지 않고 README 네 사례·순서를 보존한다. 이 후보와 판단은 register에 남긴다.

검증은 프론트 자체 API fixture이며 실제 Backend의 쓰기 권한·동시 수정·응답 유실/멱등성이나 전체 시각/접근성 인수의 완료가 아니다. 상품 ID로 컴포넌트를 구분하는 기존 경로 수명은 유지하며, 전역 성공/오류 알림의 다른 화면 전환 의미와 여러 창의 동시 편집 정책도 이번 수정 범위를 넘어선다. 실제 서버 검증이 추가되면 그 근거를 별도 구분해 기록한다.
