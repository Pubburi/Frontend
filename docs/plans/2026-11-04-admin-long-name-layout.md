# FE14 관리자 허용 이름의 가로폭과 전체 원문

## 범위·기준

FE14는 FE03/C04의 필수 관리자 인수 결함이며 선택적 최적화가 아니다. 전체 20개 MVP의 12월 31일·FE03의 11월 22일 목표와 현재 완료 8/20을 유지한다. 관리자 [키보드 편집 진입](2026-11-04-admin-keyboard-edit-focus.md)과 [검사 격리](2026-11-04-browser-fixture-isolation.md)는 이미 병합한 독립 작업이다.

현재 main `7c709a4`의 제품 소스 85개·production 파일 100개와 README를 수정 전에 동결했다. 세 탭의 허용 100자 ASCII 이름은 상품 `P`·매장 `M`·회원 `U`의 반복이며 1280/390px에서 같은 입력·하네스·관측 산식을 사용한다. 이름을 줄이거나 숨겨 너비만 맞추지 않는다. 기존 행은 바꾸지 않으며 실제 API 검증은 새 소유 상품·매장·회원만 조회한다.

## 수정 전 재현과 원인 분리

같은 이름의 현재 main fixture에서 문서 너비는 다음과 같다. 이전 키보드 작업에서 분리해 둔 원값과 같았으며, 포커스와 다음 Tab은 정상이었다.

| 화면 | 상품 | 매장 | 회원 |
|---|---:|---:|---:|
| 1280px | 1280 | 1589 | 1372 |
| 390px | 1133 | 1506 | 1271 |

문서 넘침은 5/6조건이다. 문서가 맞는 상품 1280px도 이름의 마지막 문자 조각은 x=1215.875로 셀의 오른쪽 x=509.765625를 넘어 다른 열에 겹쳤다. 따라서 문서폭·전체 문자 조각·셀 경계·다른 열 겹침·폼/버튼을 검사하는 같은 여섯 회귀는 6/6 실패했다. 서로 다른 위반 산식을 하나의 자연 오류율로 합산하지 않는다.

긴 이름은 공백 없이 이어져 기본 줄바꿈 기회가 없었다. grid 셀에서 텍스트가 넘치거나 최소 콘텐츠 너비가 상위 표·폼까지 전달됐다. 동결 빌드에 진단 스타일만 적용해 최소폭과 줄바꿈을 분리했다. `min-width: 0`만으로는 작은 화면에서 입력 상자를 줄여도 이름의 문서 넘침이 남았다. 이름 셀의 `overflow-wrap: anywhere`만 적용했을 때는 여섯 조건 모두 문서가 각 viewport 너비에 맞았다. 이 진단은 작성 fixture이며 실제 두 DB 인수와 별도다.

## 구현·보존

관리자 표의 직접 이름 셀에 `overflow-wrap: anywhere` 한 속성을 적용한다. 전체 원문을 필요한 만큼 줄바꿈하고 최소 콘텐츠 너비도 문자 단위로 계산하게 한다. 이 조건을 복구하는 데 불필요한 상위 grid·폼·공통 컨트롤 변경은 추가하지 않는다.

`overflow-x: hidden`, ellipsis, clipping, 줄 수 제한이나 이름·글꼴 축소는 쓰지 않는다. API·인증/query·정렬/페이지·편집 초안·값·저장/삭제·키보드 진입 코드는 유지한다. 단일 행 입력의 100자 값과 끝 문자까지의 키보드 편집도 보존한다.

## 검증·인계 기준

- 같은 여섯 이름/화면에서 목록과 편집 후 문서폭, 전체 `Range` 문자 조각의 viewport·자기 셀 내 수용, 다른 열과의 비겹침, 입력/select/버튼 너비를 확인한다. DOM 원문·입력값이 정확하고 숨김이 없어야 한다.
- 기존 일반 이름·Enter/Space·다음 Tab·포인터/비활성 script·현재 초안/auth/경로와 늦은 조회 검사를 유지한다. 전체 필수 `npm run check`의 API guard/IPC 수명·R06 같은 URL/native popup·F05/F06/F09·주문 snapshot 회귀도 유지한다.
- 실제 legacy MySQL와 별도 TLS PostgreSQL/JPA의 동일 전후 환경에서 같은 GET-only 하네스를 실행한다. 새 소유 세 행의 정확한 ID를 페이지 조회로 찾고 API 전체 page/item 해시와 100자 원문을 결속한다. 로그인/정리 로그아웃과 업무 쓰기를 구분하며, 원래 상품·매장·사용자 행은 변경하지 않는다.
- 최종 source/dist/하네스 해시·원 실패·실제 결과·검사 종료를 동결해 인계한다. 최신 CI·완료 Codex 리뷰·미해결 지적 없음·한국어 Squash·main CI/브랜치 정리는 별도 최종 게이트다.

## 실제 두 DB 전후

동결한 같은 하네스와 각 제공자의 같은 Backend jar·고정 Recommendation, 같은 소유 DB/입력에서 두 폭을 다시 관측했다. 실제 API가 100자 이름 등록을 허용함을 fixture 준비에서 확인했고, 브라우저는 새 상품·매장·회원만 선택했다. 상품은 실제 페이지 조회로 5페이지에서 찾았으며 회원/매장은 1페이지에서 찾았다.

| 실제 제공자 | 문서 넘침 전→후 | 전체 배치 위반 전→후 | 보존 대조 |
|---|---|---|---|
| legacy MySQL | 5/6→0/6 | 6/6→0/6 | 전체100자·첫 focus·다음 Tab·현재 page/item 해시 일치 |
| 별도 TLS PostgreSQL/JPA | 5/6→0/6 | 6/6→0/6 | 전체100자·첫 focus·다음 Tab·현재 page/item 해시 일치 |

각 제공자의 API 전체 page/선택 item 6조건 해시가 전후 같았다. 로그인 2회·정리 로그아웃 2회는 업무 쓰기와 별도이며, 화면의 업무 쓰기·예상외 API/pageerror·응답 대체는 모두 0이었다. 원래 사용자 DB와 원본 행을 수정하는 흐름은 사용하지 않았다. fixture 준비의 새 행 작성은 브라우저의 GET-only 관측과 구분한다.

같은 regression으로 관리자 24조건이 통과했다. 별도 production fixture 이미지에서도 전체 이름의 줄바꿈·입력값과 버튼 수용을 확인했다. 실제 두 DB·fixture·원인 분리 조건의 분모를 합산하지 않으며, 새 R/F 완료나 전체 FE03/C04 인수로 올리지 않는다.

## 최종 필수 검사

Node 24.22.1의 `npm run check`가 exit 0으로 끝났다. 저장소·locked 설치/audit·이미지 도구·strict TypeScript·단위 165개·production 빌드·정상 Chromium 381개를 통과했고, 두 JUnit의 failure/error/skip은 0이었다. 정상 runner의 누락 API는 0이며 child/server exit 0·소유 preview close를 확인했다. 별도 의도 누락 negative 1조건과 IPC 해제 1조건도 통과했으며 정상 browser 수에 더하지 않았다.

최종 제품 source 85개/production 100개와 회귀·하네스 해시는 실제 인수에 사용한 동결 후보와 같다. 제품 소스 변경은 CSS 한 줄뿐이며 README 전체는 기준 main과 byte가 같다.

## README·한계

여섯 작성 조건과 두 DB의 실제 관측을 전체 FE03/C04·모든 화면/브라우저/보조기술 인수로 확대하지 않는다. 너비는 레이아웃 정확성 값이며 시간 성능이나 실제 사용자의 자연 오류율을 측정한 것이 아니다.
