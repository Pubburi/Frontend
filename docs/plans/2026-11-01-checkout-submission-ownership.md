# FE03 — 주문 완료와 다음 장바구니 입력의 소유

## 기준과 고정 비교

기준 main `ecab082cc547554b97cceb962dffbb75ba3b2195`의 고객 데모 주문을 대상으로 했다. 기존 프로덕션 웹은 조정자가 100개 파일의 크기/SHA를 확인해 불변 보존했다. 두 조건의 입력·판정은 수정 전에 고정했다.

- 탁주 1개와 `제출한 요청`을 전송한 뒤, 응답 대기 중 다른 상품 1개를 새로 담는다. 원래 생성 주문에는 제출 상품/수량/요청만 있어야 하고, 미제출 상품은 장바구니에 남아야 한다.
- 같은 주문을 전송한 뒤 응답 대기 중 요청사항을 `다음 주문 요청`으로 새로 쓴다. 서버에는 원래 요청이 저장되고 다음 주문 폼에는 새 요청이 남아야 한다. 성공 뒤 다른 상품을 담아 폼을 다시 열고 값을 확인한다.

Node 24·Chromium·프로덕션 웹·직접 작성한 API fixture의 동일 두 조건에서 원래 주문 생성/제출 내용/단일 전송을 확인한 뒤 새 입력을 검사했다. 수정 전은 새 상품이 사라지고 새 요청사항은 빈 문자열이 됐다. 수정 후 두 값이 보존된다.

| 고정 조건 — 각 1회 | 수정 전 입력 유실 | 수정 후 입력 유실 |
|---|---:|---:|
| 주문 전송 뒤 새 상품 추가 | 1/1 | 0/1 |
| 주문 전송 뒤 다음 요청사항 작성 | 1/1 | 0/1 |

고정 집합의 유실은 2/2 → 0/2, 해당 비율은 100% → 0%(100%p 차이)다. 입력/후처리의 정확성 관측이며 운영 사용자 오류율·자연 지연·성능 성과가 아니다. 추가 경계 회귀는 이 분모에 합산하지 않는다. API fixture와 실제 Backend/MySQL 검증은 구분한다.

## 원인과 구현

기존 checkout은 전송 시점의 items/orderForm을 읽어 올바른 API 본문을 보냈지만, 성공하면 **완료 시점의** 모든 items를 `save([])`로 비우고 현재 폼의 orderTable을 초기화했다. 또한 CartPage가 사라져도 이전 checkout 콜백은 profile로 이동했다. 전송된 주문과 이후 사용자 의도의 수명을 구분하지 않은 것이 원인이다.

- 각 상품 행은 메모리 전용 소유 토큰을 갖는다. 새로 담는 행은 새 토큰이며, 같은 행의 추가/수량 수정은 같은 토큰을 유지한다. 삭제 후 다시 담기는 값이 같아도 새 행이다. 토큰은 저장 배열/API에 추가하지 않는다.
- 제출 시 상품별 수량/행 토큰과 폼 객체를 캡처한다. API에는 원래 상품 ID·수량·주문 방식·요청사항만 보낸다.
- 서버 성공 후 같은 행 토큰에서 **제출한 수량만** 차감한다. 2개 제출 뒤 1개 추가하면 1개가 남는다. 미제출 상품과 삭제 후 다시 담은 행은 그대로 둔다. 기존량을 제출량보다 줄였으면 남는 추가분은 0으로 정리하며 음수 수량이나 다른 행 전체 삭제를 만들지 않는다. 이미 전송한 주문의 수량을 취소/수정하는 동작은 아니다.
- 폼 객체가 아직 제출 때와 같을 때만 요청사항을 비운다. 이후 새 요청/방식을 입력했거나 같은 값으로 다시 작성한 폼은 다음 입력으로 유지한다.
- 원래 CartPage가 유지되고 경로 key가 같은 경우에만 성공 뒤 profile로 이동한다. 이탈/재진입의 새로운 화면은 이전 성공이 강제로 이동시키지 않는다. 원래 계정의 주문/카탈로그 재조회와 성공 안내는 유지한다.
- 접수 중에는 전송된 주문은 바뀌지 않고 추가 수량/새 요청은 다음 주문에 남는다는 의미를 안내한다. 기존 단일 submit 보호·정상 성공의 정리·거절 시 현재 입력 보존·보관 실패와 서버 성공의 분리는 유지한다.

전체 장바구니를 비우는 방식은 제출되지 않은 입력을 지운다. 현재 수량만 비교해 차감하면 삭제/다시 담기의 새 의도를 구분하지 못하고, 값 비교만으로 메모를 초기화하면 같은 값의 새 폼까지 지운다. 모든 담기/화면 이동을 막는 방식 대신 원래 API 전송과 다음 장바구니를 분리해 기존 탐색·편집을 허용했다.

## 검증과 상태

상태 단위에서는 기존 저장 호환/보관 차단/성공·실패에 더해 제출량 차감·새 상품·행 삭제/재추가·제출량보다 감소·같은 값의 새 요청·거절 후 추가 입력을 확인했다. Chromium에서는 위 두 비교와 별도로 같은 상품 추가분, 삭제/다시 담기와 CartPage 재진입, 수량 감소 후 다른 상품, 중복 submit 차단·거절 뒤 명시적 새 수량 재주문을 확인했다. 늦은 성공의 경로 비탈취도 확인한다. 추가 경계가 원래 두 조건의 관측 횟수를 늘리는 것은 아니다.

Node 24의 `npm run check`가 통과했다. 저장소 검사·locked 설치·audit(취약점 0)·이미지 도구·strict TypeScript·단위 53개·프로덕션 빌드·Chromium 106개를 확인했다. 테스트 범위이며 서비스 성능 수치가 아니다.

실제 서버 비교는 조정자가 같은 조건의 전용 폐기 DB에서 별도로 실행했다. 실제 POST /api/orders의 201/서버 반영을 먼저 확인하고 원래 응답의 전달만 보류한 동안 다음 상품/요청을 입력했다. 원래 주문을 조회해 상품·수량·요청이 바뀌지 않았는지 확인하고 원응답 전달 뒤 서버를 다시 조회했다. 현재 장바구니·다음 폼·이탈 경로의 결과는 따로 집계했으며 고정 두 조건의 위반 2/2 → 0/2를 확인했다.

최신 head CI/Codex 리뷰·병합/main CI는 별도 게이트다. FE03/C04 최종 체크리스트 전체나 새 R/F 기능 완료를 주장하지 않는다. 여러 창·전체 새로고침 중인 주문의 조정, 서버 멱등성, 계정 장바구니/병합·실제 PG는 이번 메모리 소유 경계의 보장 범위가 아니다. 보관 차단 중 새로고침 복원을 보장하지 않는다.

## 실제 서버 비교 조건과 결과

Java 17·MySQL 8.4·Node 24·Chromium의 같은 실행 환경에서 초기 80상품의 동일 시연 seed를 서로 다른 두 폐기 스키마에 준비했다. 같은 계정/인증 입력·같은 상품 선택/수량/메모·같은 검증 도구를 사용했다. 기존 사용자 DB/볼륨을 초기화하거나 사용하지 않았다.

같은 Backend jar(SHA256 `ddd3ab6f70f2cb2b7d0b296ac85a1acd4f2f68934733babefe9df930211c9a65`)에 기준 main `ecab082`와 수정 프로덕션 웹을 연결했다. 기준 웹의 compact 파일 목록 SHA256은 `082b241d1bb93e408f270e07aab82d5a0bef823b5bba6843cdb5abb3927dc0c2`, 수정 웹은 `f520671e257e01c1e3069736042fad27fe258ee58473c303074231ff564320e1`이다. 수정 100파일의 manifest 파일 자체 SHA256은 `02434ee618a38588170113e5ce9058c946c73c2a6bb218843dcffc6be1a4bb71`이며 두 hash의 의미를 구분한다. 앱/빌드 파일을 동결하고 다시 빌드하지 않은 상태에서 비교했다.

| 실제 서버 — 각 조건/모드 1회 | 기준 웹 위반 | 수정 웹 위반 | 수정 후 결과 |
|---|---:|---:|---|
| 주문 반영 뒤 새 상품 추가 | 1/1 | 0/1 | 미제출 상품 보존·원래 제출 상품 정리·현재 탐색 경로 유지 |
| 주문 반영 뒤 새 요청사항 작성 | 1/1 | 0/1 | 원래 주문 메모 불변·다음 폼의 새 메모 보존 |

두 모드 각각 실제 주문 POST 201은 2건이고, 원래 상품 수량 1개/제출 메모를 전달 전과 전달 뒤 서버 조회로 확인했다. 수정 후 추가 상품·다음 메모·현재 경로 판정이 모두 성립했다. 두 실행 모두 인프라 성공·예상외 API 오류/pageerror 없음이었고 API 업무 응답 mocking은 사용하지 않았다. 최초 로그인 전 auth/me 401만 정상 비회원 응답으로 구분했다. 웹 프록시→Backend→고정 Recommendation B0의 공개 기본 목록 BASELINE도 확인했다.

실제 서버 비교의 위반은 2/2 → 0/2, 이 고정 집합의 비율은 100% → 0%(100%p 차이)다. 두 조건을 각각 한 번 실행한 기능/정합성 결과이며 실제 사용자 오류율·자연 지연/부하·시간 성능 개선으로 확대하지 않는다. 실제 서버에 먼저 주문을 반영한 뒤 **그 원래 응답의 브라우저 전달만 제어한** 결정적 경합이다. 같은 상품 추가량·삭제 후 다시 담기·수량 감소·거절/재주문·재진입은 별도 단위/fixture 근거로 구분하고 실제 두 조건의 분모에 더하지 않는다.

### 준비 오류의 분리

초기 실제 시도는 장바구니 링크 클릭 뒤 React 화면이 마운트되기 전에 DOM 행 수를 읽어 정리를 건너뛸 수 있었다. 첫 수정 웹 실행의 두 번째 준비는 남은 상품 때문에 예상 주문 금액 버튼을 찾지 못했고, 단계 진단을 추가한 다음 시도에서도 정리 뒤 DOM/저장 항목이 남은 상태를 확인했다. 두 준비 실패 원문은 ignored 기록으로 보존하고 전체 인수 성공이나 제품 오류율의 표본으로 합산하지 않았다.

실행 도구에서 `/cart` URL·실제 장바구니 heading·저장 배열 길이와 DOM 행 수의 일치를 먼저 기다리고, 각 UI 삭제 뒤 행 수 감소/최종 저장 0을 확인하도록 준비 경계를 수정했다. timeout 확대·무조건 재시도로 덮지 않았다. 이후 SHA256 `cc58118b55cf76c99016f0d7cc992d82f75d08dbba38f94e2f4367d06f52f289`인 **같은 수정 도구**와 새로 만든 두 동일 seed 스키마의 전후 결과만 위 최종 실제 비교로 채택했다. 이 검증 도구 수정 때문에 앱/빌드 산출물을 바꾸지 않았다.

### 공개 재현 절차와 근거

1. 같은 시연 seed·계정 입력을 별도 폐기 before/after 스키마에 준비한다. 기준/수정 웹 파일들의 크기/SHA를 확인해 동결하고 같은 Backend jar에 연결한다.
2. 고정 첫 상품 1개와 원래 메모를 장바구니에서 전송한다. 실제 POST를 서버로 전달해 201을 확인하고 주문 조회에서 원래 상품/수량/메모를 먼저 확인한다.
3. 업무 응답을 가짜로 만들지 않고 원응답의 전달만 보류한다. 새 상품을 담아 탐색 경로에 남거나, 원래 장바구니에서 다음 메모를 입력한다.
4. 원응답을 전달하고 성공 안내 뒤 서버 주문을 다시 조회한다. 단일 POST와 원래 내용 불변을 확인한 뒤 미제출 상품·다음 폼·현재 경로를 집계한다.
5. 장바구니의 실제 마운트/저장 배열/표시 행을 일치시킨 다음 UI로 시연 항목을 정리하고 다음 조건을 진행한다. 제품 판정은 다음 조건을 막지 않게 집계하되 인프라/준비 실패는 별도로 분리한다.

공개 근거는 [제출 수량·행/폼 소유 코드](../../src/state/cart.ts), [성공 이동 경계](../../src/pages/AccountPages.tsx), [상태 회귀](../../src/state/cart.test.ts), [고정 API fixture](../../tests/browser/smoke.spec.js)와 위 절차다. 실행 도구/원문 보고서는 ignored 기록에 보존하고 계정·인증·개인 경로·원문 로그를 공개하지 않는다.

## 대표 사례 비교

실제 원주문을 유지한 채 다음 입력을 보존한 근거가 추가돼, 기존 첫 번째 저장/프레임워크 전환 설명보다 문제의 영향·원인·대안·수량/행/폼/화면 수명이 명확해졌다. README 첫 번째 한 개만 이 사례로 교체하고 기존 설명은 register의 고정 이전 README 링크로 보존했다. 나머지 세 사례와 순서·총 네 개는 유지했다. README에는 회귀 횟수·실험 절차·CI 집계를 넣지 않는다.
