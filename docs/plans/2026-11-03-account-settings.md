# F09 — 본인 계정 설정과 비밀번호 변경

## 범위와 제공 계약

기준 main `88b8833`에서 필수 F09의 이름·비밀번호 수정을 `/settings`에 연결하고 기존 `/preferences` 취향 수정으로 안내한다. 현재 완료는5/20(R01·F01·F03·F05·F06)이며 F09 완료는 실제 인수와 최신 리뷰/CI·병합/main 확인 뒤 판정한다. 전체 FE03/C04·PostgreSQL 전환과 별도다. 기준 화면에 이 수정 경로가 없는 것은 신규 기능 제공 전 상태이며 과거 운영 장애나 성능 개선으로 표현하지 않는다.

조사 당시 관리자 회원 수정만 제공되어 본인 수정에 우회 사용하지 않았다. Backend가 같은 작업의 [본인 수정 공급 PR](https://github.com/Pubburi/Backend/pull/37)에서 전용 계약을 제공하고 웹이 소비한다. 상세 검증/세션 잠금의 정본은 [Backend API 계약](https://github.com/Pubburi/Backend/blob/main/docs/API-MAP.md)·[세션 권위](https://github.com/Pubburi/Backend/blob/main/docs/SESSION-AUTHORITY.md)다.

- `PUT /api/users/me/profile`은 `{name}`만, `PUT /api/users/me/password`는 `{currentPassword,newPassword}`만 보내고 성공 `data:true`/200을 확인한다. 계정 ID·권한·스탬프·epoch를 URL query/본문에서 선택하지 않는다.
- 이름은 공백만 입력할 수 없고 최대100자다. 현재 비밀번호는 기존 짧은 자격도 검증하도록 NotBlank/최대100자이고, 새 비밀번호만 NotBlank/4–100자·UTF-8 최대72바이트다. 현재 제공자의 실제 BCrypt 경계를 따라 새 암호만 바이트 길이를 검사하고, 기존 현재 암호 검증에는 새 바이트 제한을 소급하지 않는다. UTF-16 길이와 원문을 유지하며 암호의 trim·대소문자/Unicode 변환을 하지 않는다.
- 현재 암호 오류403은 유효한 현재 로그인을 유지한다.401은 회수/비로그인이므로 수정폼을 감추고 명시적 재로그인에 원래 설정 경로/query를 보존한다.400과503/통신 장애를 구분한다.
- 이름 변경은 자격을 유지하며, 비밀번호 변경은 현재 세션을 유지하고 다른 기존 세션을 회수한다. 웹은 성공 뒤 현재 me를 다시 확인하고 기존 본인 profile 등 개인 읽기를 stale 처리한다. 변경 성공을 후속 읽기 실패 때문에 쓰기 실패로 바꾸지 않는다.

## 화면·요청·비밀 입력 소유

마이페이지의 설정 링크에서 이름·비밀번호 두 폼과 기존 취향 링크를 제공한다. 경로 key와 현재 session query/계정 소유의 새 서버 확인 전에는 전송하지 않는다. 이미 확인한 주소로 돌아와도 새 진입을 확인한다. 인증 쓰기/계정 전환은 이전 편집기를 제거하고 비밀 입력을 남기지 않는다.

계정별 미완료 HTTP의 토큰만 인증 캐시 밖에 둔다. 로그인/로그아웃의 캐시 초기화가 진행 중인 같은 계정 쓰기를 끝낸 것으로 보이지 않게 하고, 다른 계정은 독립적으로 동작한다. 같은 계정 재로그인도 이전 HTTP 정착 뒤 새 me로 편집을 시작한다. 늦은 이전 계정/이전 경로의 성공·오류는 현재 초안/알림/경로를 바꾸지 않는다. 실제 인증·캐시 초기화와 기존 장바구니 형식은 유지한다.

이름은 제출 객체와 현재 초안을 구분해 전송 중 새 입력을 보존한다. 전송한 비밀번호는 즉시 입력칸에서 지우며 후속 입력은 새 초안으로 보존한다. 비밀번호는 이 화면의 메모리/전송 중에만 존재하고 계정 쓰기 토큰·브라우저 저장소·로그에 넣지 않는다. 화면 이탈/새 진입은 비밀 입력을 지운다. 이미 브라우저 암호 관리자가 저장하는 정책을 이 구현이 제어한다고 주장하지 않는다.

불확실한 쓰기 응답은 자동 재전송하지 않는다. 현재 권위를 다시 확인하기 전 다음 제출을 막으며 명시적 읽기 복구를 제공한다. 특히 me200은 비밀번호 변경 여부의 증명이 아니므로 해당 한계를 안내한다. 비밀번호 쓰기는 F05의 기존 인증 쓰기 차폐에도 포함해, 종료 뒤 시작한 실제 세션 읽기 전 최근 기록의 노출/기록을 재활성화하지 않는다. 겹친 읽기나 수동 캐시는 이 확인을 대신하지 않는다.

## 허용 이름의 필수 좁은 화면 경계

최종 확인에서 허용100자 ASCII 이름을 저장하는390px 조건을 먼저 고정했다. 초기 F09 후보의 메뉴 열린 문서 폭은1146px, 마이페이지는2164px였고 이름/제목 DOM 원문은 그대로이나 문자 영역이 화면 밖으로 나갔다. 이는 새 F09 후보의 기본 입력 인수 결함이며 기존 main 전체/운영 장애로 표현하지 않는다.

메뉴 이름의 최소 폭·최대 배치 폭과 원문 줄바꿈, 프로필 내용의 최소 폭/최대 폭과 제목 줄바꿈만 명시했다. 값을 줄이거나 숨기지 않고 같은 조건의 문서 폭을 각각390px로 맞췄으며 이름/제목 전체 원문과 모든 문자 조각이 화면 안에 있는지 JSON 좌표로 확인했다. 이 한 조건의 여러 UI 영역을 독립 표본이나 시간 성능 개선율로 합산하지 않는다. 최초 빌드/소스·조건·원 좌표를 보존하고 최종 후보는 별도100파일로 동결한다.

이 확인의 첫 선택 runner를 전체 검사와 겹쳐 기동한 것은 작성자의 실행 조정 실수였다. 포트 충돌로 기동이 거부됐고 같은 Playwright outputDir 정리로 전체 검사의 한 trace 파일 정리에서 ENOENT가 발생했다. 원 로그/JUnit/남은 trace를 보존하고 제품 assertion 실패와 구분했다. 기존 주문 코드를 고치거나 해당 검증을 skip하지 않고 모든 같은 outputDir runner를 직렬화한 뒤 필수 전체 검사를 새로 실행한다.

이후 필수 전체 회귀에서 비교 URL의 제거 직후 빠른 Back이 표2개/메뉴 선택1개로 남는 기존 F06 경계가 관측됐다. 이름/암호 코드를 바꾸거나 기존 비교 검증을 늦춰 숨기지 않고 [별도 F06 수정 PR #38](https://github.com/Pubburi/Frontend/pull/38)로 처리했다. 원래 main에서 정상 commit 대조는 유지하고 독립 React task gate의 빠른 이동 실패를 먼저 고정했으며, URL의 실제 반영만 공유 선택을 갱신하게 했다. 해당 수정의 단위118/Chromium287·별도 실제 GET 두 폭의 제어 조건2/2→0/2와 정상 대조·원문 보관 보존은 이 F09 검사와 합산하지 않는다.

F09는 한 목적의 구현 커밋으로 안전하게 보존한 뒤, F06의 main `f7995e7`·필수 main CI 성공과 브랜치 정리를 확인하고 일반 merge로 반영했다. 두 작업의 사례 기록을 모두 보존해 충돌을 해결했으며 force/rebase로 이력을 다시 쓰지 않았다. 최신 F09 전체 검사와 두 제공자의 실제 인수는 이 통합 소스에서 다시 확인한다. 과거 후보의 선택/실제 성공이나 실패를 최신 전체 검사 성공·F09 완료로 대신하지 않는다.
