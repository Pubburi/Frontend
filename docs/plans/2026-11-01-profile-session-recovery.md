# FE03 — 마이페이지 서버 세션 상실의 명시적 로그인 복구

## 기준과 사전 재현

기준 main `3ac5096`의 프로덕션 웹과 Node 24·Chromium에서 두 조건을 고정했다. `session` query는 정상 로그인 계정을 Infinity staleTime으로 보존한다. 서버 세션만 사라지고 React 캐시는 남은 상태에서 본인 정보/주문 조회가 401이면 마이페이지는 일반 `다시 시도`만 제공했다. 재조회도 401을 반복하며, 로그인 화면을 직접 열어도 guest guard가 캐시된 계정을 보고 마이페이지로 보냈다. 명시적인 로그아웃이나 전체 새로고침은 별도 우회 방법이다.

| 고정 조건 — 각 1회 | 서버 세션을 잃기 전 화면 | 기준 관측 | 수정 관측 |
|---|---|---|---|
| first-read | 로그인한 상품 목록 → SPA 마이 진입 | 첫 본인 정보/주문 401 뒤 재시도 반복, 로그인 복귀 없음 | 명시적 로그인 → 원래 마이페이지/현재 본인 결과 |
| refresh | 로그인한 마이페이지 → 새로고침 | 기존 query 데이터가 있는 상태의 401도 같은 복귀 차단 | 개인 내용 숨김 → 명시적 로그인 → 권위 재조회 |

같은 API fixture와 불변 기준 웹에서 두 복구 위반을 각각 재현했다. 수정 웹은 두 조건 모두 로그인 경유 후 원래 마이페이지의 현재 본인 결과로 복귀해 2/2 → 0/2였다. 오류 UI의 버튼이 실제로 준비된 뒤 조작하고, 성공 주문이 없는 정상 빈 상태를 오류 준비 완료로 간주하지 않았다. 본인 GET의 실제 fixture 401/반복 요청과 현재 URL을 구분해 기록했다. 이는 두 고정 기능 조건의 관측이며 자연 장애율·운영 사용자 오류율·시간 성능이 아니다.

## 원인·선택과 구현

인증 캐시의 계정이 여전히 존재하므로 보호 경로/guest 경로의 기준과 서버 개인 조회의 실패가 달랐다. 일반 재시도는 서버 세션을 복구하지 않는다. 모든 API 401에서 전역 로그아웃하는 방식은 늦은 이전 계정 응답이 새 인증을 지우거나 다른 화면의 정책을 바꾸므로 채택하지 않았다. 403·5xx를 인증 상실로 취급하지도 않는다.

- ProfilePage의 현재 본인 정보 또는 주문 query가 ApiClientError 401이면 캐시된 개인 내용을 감추고 `다시 로그인` 조작을 제공한다. 어느 한 조회만 401이어도 같은 경계이며 자동 로그아웃/자동 재전송은 없다.
- 명시적 조작 직전 현재 session query 객체/계정 객체와 실패 query 객체/error 객체가 관측했던 소유와 같은지 다시 확인한다. 로그인/로그아웃의 기존 cache.clear로 생기는 새 인증 세대를 이전 오류가 정리하지 못한다.
- 인증 또는 해당 실패 조회를 재검증 중이면 전환을 기다린다. 재연결 성공으로 이미 회복한 현재 결과를 오래된 오류 조작이 지우지 않는다. 대기 중에도 캐시된 개인 내용을 다시 노출하지 않는다.
- 유효한 현재 401의 명시적 복구에서만 기존 인증 전환과 같은 개인 query 정리를 수행하고 session을 null로 둔다. `/account?redirect=`에 현재 pathname/query를 보존하며 실제 재로그인 뒤 현재 서버 결과를 조회한다.
- 기기 장바구니·미제출 주문 요청과 별도 메모리 상태는 지우지 않는다. 403/500/503은 기존 일반 재시도를 유지한다. 서버 인증·권한 정책과 다른 페이지의 오류 처리는 바꾸지 않는다.

새로고침 강제나 주기적 세션 폴링 대신 사용자가 복귀를 선택하는 작은 경계를 택했다. 서버의 세션 수명 자체를 바꾸거나 여러 창의 즉각적인 인증 동기화·진행 중 모든 쓰기의 취소를 보장하는 변경은 아니다.

## 검증 범위와 상태

두 고정 조건 외에 본인 정보/주문 단독 401, 캐시 내용 숨김, 403/500/503의 일반 재시도, 이전 A의 늦은 401 뒤 같은 A/다른 B 새 인증, 다른 계정 로그인에서 장바구니/미제출 요청 보존, 390px Enter/복귀 query 보존, 재연결 GET 대기/성공의 전환 차단을 별도 회귀로 둔다. 추가 경계를 두 조건의 비교 분모에 합산하지 않는다.

Node 24 `npm run check`의 저장소 검사·locked 설치·audit(취약점 0)·이미지 도구·strict TypeScript·단위 53개·프로덕션 빌드·Chromium 136개가 통과했다. 새 회귀는 고정 두 조건과 별도 열 경계다. API fixture는 Frontend의 상태/응답 처리 검증이며 실제 Backend/DB 통합이 아니다. 별도 실제 서버 비교도 아래 두 조건에서 통과했다. 최신 head 리뷰/CI·병합/main CI는 별도 게이트이며 전체 FE03/C04 최종 인수와 새 필수 R/F 기능, PostgreSQL 전환 DB06 검증은 완료 처리하지 않는다.

추가 재연결 회귀의 첫 전체 실행은 준비 전제를 잘못 정해 실패했다. 캐시가 없는 최초 401의 refetch는 query-core가 pending으로 바꾸므로, 캐시된 기존 데이터를 가진 error 재검증의 비활성 버튼 조건과 달랐다. 기존 profile 200을 읽은 뒤 새로고침 401→재연결 GET 보류 순서로 대상 조건을 명시했고 단독 회귀를 통과했다. 앱을 우회하거나 timeout/재시도를 늘리지 않았으며, 이 준비 실패를 고정 두 복구 조건의 제품 위반이나 개선 횟수에 합산하지 않는다.

## 실제 서버 비교 절차

1. 조정자가 동일 seed·동일 계정 생성/입력·동일 Backend와 도구를 사용하는 별도 폐기 before/after DB와 불변 웹을 준비한다. 이번 MySQL 비교는 PostgreSQL 이관 전 동작의 기준 확인이며 원본 DB/사용자 데이터에는 접근하지 않는다.
2. 두 조건은 각각 새로운 브라우저 context와 소유 시연 계정으로 시작한다. 실제 회원 생성 201/boolean과 UI 로그인 200/본인 세션을 확인한다.
3. React 로그아웃 조작을 누르지 않고 같은 context의 실제 POST `/api/auth/logout` 200을 호출한다. 실제 auth/me 401과 SPA의 캐시된 로그아웃 버튼을 함께 확인한다. 이는 서버 세션/쿠키만 무효화한 통제 조건이며 자연 장애 재현이라는 뜻이 아니다.
4. first-read는 상품 목록에서 SPA 마이로 들어가고 refresh는 이미 읽은 마이페이지를 새로고침한다. 본인 정보/주문의 현재 401을 둘 다 확인한다. 기준의 일반 재시도는 반복 401을 집계하고, 복구 버튼 부재를 인프라 장애와 구분한다.
5. 수정 웹의 명시적 재로그인은 원래 profile 목적지로 돌아가야 한다. 실제 로그인 200과 새 본인 정보/주문 200·서버 본인 계정/프로필을 확인한다. 업무 성공 응답을 mock하지 않는다. 예상외 API/JavaScript 오류와 제품 위반은 별도로 집계한다.

원문 도구/결과와 개인 경로·계정·비밀번호는 ignored 기록에만 보존한다. 공개 근거는 [ProfilePage의 복구/소유 검사](../../src/pages/AccountPages.tsx), [session 읽기/캐시 정책](../../src/queries.ts), [경로 보호](../../src/App.tsx), [고정 및 추가 browser fixture](../../tests/browser/smoke.spec.js)와 위 재현 절차다.

## 실제 서버 전후 결과

조정자가 동일 Backend jar(`dcb73c35b4db…`)·Java 17·MySQL 8.4·Node 24·Chromium과 동일 seed 80개 상품을 사용했다. before/after는 각각 독립된 전용 폐기 DB이며 계정 생성 순서·시연 ID/비밀번호·입력 namespace와 하네스(`6161b08366d8…`)를 같게 했다. 기준 main `3ac5096`의 불변 웹 100개 파일(물리 manifest SHA `e649f7590fe9…`)과 수정 웹 100개 파일(`5a31f0bf391b…`)은 실행 전에 크기/SHA를 확인했다. 두 조건은 각 모드에서 한 번씩, 별도의 새 브라우저 context/시연 계정으로 실행했다.

| 실제 고정 조건 | 기준 복구 | 수정 복구 | 실제 업무/세션 확인 |
|---|---|---|---|
| 첫 마이페이지 진입 first-read | 일반 재시도 401 반복, 로그인 조작 없음 | 명시적 로그인 후 원래 profile 복귀 | 회원 생성201·초기/복구 로그인200·현재 본인 auth/me/profile/orders 확인 |
| 기존 마이페이지 새로고침 refresh | 캐시가 있어도 일반 재시도 401 반복 | 개인 내용 숨김·로그인 후 새 본인 결과 | 초기 profile/orders200·서버 logout200·두 조회401·복구200 확인 |

복구 위반은 **2/2 → 0/2**, 이 고정 집합의 비율은 100% → 0%(100%p 차이)다. 인프라는 양쪽 모두 성공했으며 기준 실행의 실패 종료는 의도한 제품 복구 부재를 뜻한다. 실제 서버의 logout으로 세션/쿠키를 무효화하고 SPA의 기존 계정 캐시를 남긴 제어 조건이다. 자연 세션 만료 빈도·운영 사용자 오류율·지연/성능 향상으로 일반화하지 않는다.

양쪽 모두 실제 회원 생성201/정상 초기 로그인과 서버 logout200 뒤 auth/me401을 확인했다. 수정은 다시 입력한 실제 자격으로 로그인200을 마친 뒤 현재 본인 profile/orders를 200으로 읽고 별도 서버 조회에서도 본인 계정/이름/USER·주문 배열을 확인했다. 최초 비회원 auth/me401과 통제 조건의 본인 GET401은 예상 결과로 분리했고, 예상외 API 오류·pageerror·API mocking은 모두 없었다. 웹 프록시→Backend→고정 Recommendation B0의 기본 목록 BASELINE도 확인했다. 이는 기본 추천의 새 품질 성과가 아니다.

다른 계정의 늦은 오류·403/5xx·재연결 대기·장바구니/미제출 요청·390px Enter는 앞의 추가 API fixture 근거다. 두 실제 고정 조건의 분모에 합산하거나 실제 서버의 모든 오류/키보드 인수로 확장하지 않는다. 현재 MySQL 검증은 PostgreSQL 이관 전 회귀 기준이며, 전환 후 같은 `/api`·ApiResponse·세션쿠키·인증 오류/복귀를 실제 PostgreSQL 기반 서버로 다시 확인해야 한다. DB06·전체 FE03/C04는 여전히 미완료다.
