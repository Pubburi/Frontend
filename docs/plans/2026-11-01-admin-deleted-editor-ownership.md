# FE03 — 성공 삭제와 현재 편집 입력의 소유 분리

## 기준과 사전 재현

기준 main `216fa139`의 생산 웹100파일·입력·하네스와 결과를 불변 보존했다. 상품/매장/타회원의 현재 편집 행을 확인 삭제하면 목록/특성 편집은 정리되지만 기본 draft.editing은 남았다. 기존값이 유효한 폼의 변경 저장을 다시 누르면 이미 삭제된 ID로 PUT404를 보냈다.

Node24·Chromium·독립127 동적 포트의 같은 API fixture에서 자체 기술 행3개를 각각1회 확인했다. 현재 관리자 본인은 대상에서 제외하고 필수 이미지/입력도 준비했다.

| 고정 조건 | 기준 DELETE200 후 | 수정 DELETE200 후 |
|---|---|---|
| 현재 상품 편집 행 삭제 | 옛 변경 저장 유지·후속PUT404 | 새 작성 폼으로 초기화·옛PUT0 |
| 현재 매장 편집 행 삭제 | 옛 변경 저장 유지·후속PUT404 | 새 작성 폼으로 초기화·옛PUT0 |
| 현재 타회원 편집 행 삭제 | 옛 변경 저장 유지·후속PUT404 | 편집 폼 닫힘·옛PUT0 |

동일 하네스(`e31f94a5e548…`)/입력과 불변 전후 웹에서 편집 소유 위반은3/3→0/3, 이 고정 집합의 위반 비율은100%→0%(100%p 차이)였다. 양쪽 인프라는 성공했고 예상외API·pageerror는 없었다. 기준의 정확한 삭제 대상 후속404는 의도한 재현 결과이며 예상외 API 실패와 구분한다. 기능 정확성 조건이고 자연 오류율·시간 성능이 아니다. 삭제의 업무 실패나 데이터 유실을 재현했다고 표시하지 않는다.

## 사전 계약: 삭제 사실·편집 대상·새 revision

- 삭제 시작 시 편집과 revision이 그대로인 **같은 대상**만 초기화한다. 다른 행 편집/새 작성은 객체 그대로 보존한다.
- 같은ID라도 그동안 다시 열거나 입력을 바꾼 **새 revision은 버리지 않는다**. 현재 입력을 남기고 삭제 안내·저장 차단 상태로 전환한다. 버튼뿐 아니라 submit handler에서도 옛ID PUT을 막는다. 복사/편집 취소 또는 새 권위 목록에서 명시적으로 다른 편집을 선택할 수 있다. 자동 복제·회원 재생성 API는 추가하지 않는다.
- 취소/서버 거절은 기존 입력과 삭제 확인을 보존한다. 실제 DELETE200 뒤 목록 읽기 실패는 재삭제 실패로 바꾸지 않고 알려진 삭제와 현재 편집을 먼저 정리한다.
- 다른/같은 관리자ID의 새 로그인 세대에는 이전 응답으로 폼/캐시를 지우거나 재조회를 시작하지 않는다. 새 인증의 자체 권위 조회를 따른다.

무조건 전체 reset은 다른 초안을 잃고, 같은ID의 새 입력을 그냥 편집 상태로 남기면 다시404를 만든다. 삭제와 입력 소유를 나누고, 사라진 대상의 새 입력은 저장할 수 없는 보관 상태로 명시했다. 이 상태는 현재 폼에만 존재하며 명시적 초기화/새 편집으로 해제한다.

## 구현과 한계

draft의 불투명 Symbol revision을 편집/입력/초기화마다 갱신한다. 성공한 삭제 사실은 QueryClient의 활성 listener에1회 전달하고, 같은 tab/actor 및 현재 session query·actor 객체 소유를 모두 검사한다. 원문 draft나 비밀번호를 이벤트/별도 cache에 넣지 않는다. 이로써 삭제 대기 중 탭 이탈/재진입한 새 Panel도 자기 입력을 잃지 않고 사실을 받는다. 영구ID tombstone은 남기지 않아 이후 재생성된 UserID의 명시적 새 편집을 막지 않는다.

삭제 성공 후 현재 인증 범위의 관련 목록 요청을 취소하고 await 뒤 인증 소유를 다시 확인한다. 캐시에 실제로 남은 삭제 행만 제거하고 해당 목록의 알려진 총수를 보정한 뒤 이벤트/권위 재조회를 수행한다. 다른 인증 세대는 취소 전부터 배제한다. 이미 전송된 업무 DELETE 자체를 취소한 척하거나 실제 서버 삭제를 되돌리는 기능은 아니다.

### 검토 중 추가 재현: 비활성 이전 목록 응답

기본 폼 정리만 적용하고 목록 취소는 아직 없는 후보 빌드를 별도 동결해1조건을 재현했다. 삭제 전에 시작한 목록GET2를 옛 행 snapshot으로 보류하고 Panel을 이탈한다. DELETE200/캐시 행 제거 뒤 옛GET2를 전달하고 같은 tab으로 돌아와 새GET3도 보류하면, 후보는 삭제 행을1개 다시 표시했다. inactive query는 기본 invalidate/refetch에서 빠져 옛 성공이 캐시를 덮을 수 있었다.

같은 별도 하네스(`e18dc7ad478b…`)의 후보/최종 빌드에서 이 재등장은1/1→0/1이었다. 양쪽 인프라가 성공했고 HTTP 옛 응답은 양쪽 모두 끝까지 전달됐으며 새 권위GET 완료 후에는 양쪽 모두 행이 없었다. 따라서 단순 네트워크 실패가 아니라 **그 사이 캐시 적용 차이**다. 이는 최초 main의 고정3조건과 별개인 검토 중 후보1조건이며 운영/과거 장애 수치나 합산4/4로 표현하지 않는다.

## 검증 상태

정책 단위는 동일/새revision·동일값 재편집·다른 행/새 작성·client간 전달/해제 수명을 확인한다. production browser는 고정3조건과 실제 Back/탭 재진입의 새 입력3개, 다른/새 초안, 취소/거절/명시적 재시도, 쓰기 뒤 읽기 실패, 같은/다른 관리자 새 인증, 같은 UserID 재생성의 명시적 편집, 늦은 비활성 목록을 확인한다. 삭제 차단 폼의 강제submit은 방어 handler 검증이며 실제 사용자가 disabled 버튼을 클릭했다는 뜻이 아니다. 좁은 웹 안내의 가로 넘침도 별도로 확인한다.

Node24 `npm run check`의 저장소 검사·locked 설치·audit(취약점0)·이미지 도구·strict TypeScript·단위68개·프로덕션 빌드·Chromium163개가 통과했다. 새 정책 단위6개와 새 브라우저14개이며 이 집계는 서비스 성능이 아니다. 최종100파일의 물리 manifest SHA는 `b5d74e22e6cd…`, compact 파일 목록 SHA는 `310de1d87256…`다. 동결 빌드에서도 고정3조건과 별도 후보1조건을 각 하네스로 확인했다. 기존 listener 없음 뒤 자체4173 preview를 시작하고 종료 뒤 listener 없음도 확인했으며, 동적 fixture의 HTTP/browser도 각각 finally로 정리했다.

위 API fixture/검토 후보 조건은 Backend/DB 통합 E2E가 아니며 실제 서버 고정3조건도 아래 범위에서 통과했다. 최신 head 리뷰/CI·병합/main CI는 별도 게이트다. 전체FE03/C04·PostgreSQL DB06은 여전히 미완료며 여러 외부 작업자의 삭제/동시 재생성·모든 보조 기술 조합을 해결했다고 표시하지 않는다.

## 실제 서버 비교 절차

조정자가 동일 관리자/비밀번호·seed·생성 순서·namespace와 한 불변 하네스를 별도 폐기 before/after DB에서 사용한다. public API로 자체 상품/매장을 POST201, 타회원을 POST/users201로 만들고 GET으로 확인한다. 관리자 본인ID와 타회원ID가 다름을 검증한다. UI에서 해당 행을 편집/확인 삭제해 실제 DELETE200·대상GET404/목록 제거를 확인한다. 기준에 남은 stale 폼만 정확한 대상의 PUT404/NOT_FOUND로 확인하고, 수정은 폼 정리·옛PUT0을 판정한다. 정상 초기 비회원 auth/me401과 이 재현의 정확한404만 예상 결과로 분리한다.

성공API 응답을 합성하지 않으며 원본DB/seed 행을 삭제하지 않는다. 현재 MySQL은 PostgreSQL 이관 전 API 회귀 기준이다. 새 입력/인증/늦은GET 경합은 별도 fixture로 유지하고 실제 고정3조건과 분모를 섞지 않는다. 원문 하네스/로그·불변100파일·개인 경로/자격은 ignored 기록에 보존한다.

## 실제 서버 전후 결과

동일 Backend jar(`dcb73c35b4db…`)·고정 Recommendation B0·Java17/MySQL8.4/Node24/Chromium을 사용했다. 최초 상품80개의 같은 seed인 별도 폐기 before/after DB를 준비하고 한 runner의 같은 관리자ID/비밀번호·namespace·생성 순서를 공유했다. 기준 main `216fa139`와 수정의 생산 웹100파일(물리 manifest `b7fd8ea0b522…`/`b5d74e22e6cd…`), 같은 하네스(`52dea865bfcb…`)를 실행 전에 확인했다. 자체3행을 각각1회 검증했다.

| 실제 고정 조건 | 양쪽 서버 확인 | 기준 UI/후속 저장 | 수정 UI/후속 저장 |
|---|---|---|---|
| 현재 상품 편집 삭제 | POST201/GET·DELETE200·GET404/목록 없음 | 옛폼·정확한 옛ID PUT404 | 새 작성 초기화·옛PUT0 |

| 현재 타회원 편집 삭제 | POST/users201/GET·DELETE200·GET404/목록 없음 | 옛폼·정확한 옛ID PUT404 | 편집 폼 닫힘·옛PUT0 |

편집 소유 위반은 **3/3→0/3**, 고정 집합의 위반 비율은100%→0%(100%p 차이)였다. 양쪽 인프라는 성공했다. 현재 관리자 본인을 삭제하지 않았고, 기준에서 재현한 후속PUT은 이미 확인된 같은 삭제 대상의404/NOT_FOUND였다. 정상 DELETE나 후속 GET404를 오류 개선율에 섞지 않는다. 성공API 응답 합성·예상외API·pageerror는 없었으며 웹 프록시→Backend→고정 Recommendation의 기본 목록 BASELINE도 확인했다.

이는 현재 입력 그대로인 편집의 삭제 완료3조건이다. 새revision·탭 재진입·새 인증·거절/읽기 실패·새 UserID·추가 늦은GET은 위 별도 production fixture 근거이며 실제 서버3조건의 분모에 합산하지 않는다. 처음의 fixture3/검토후보1도 서로 합산하지 않는다. 자연 오류율·시간 성능·추천/실사용 성과가 아니다.

현재 MySQL API의 PostgreSQL 이관 전 회귀 기준이며 제공자 전환 뒤 같은 생성/삭제/404·폼/입력 소유와 권한을 다시 확인해야 한다. DB06·전체FE03/C04를 완료로 바꾸지 않는다.
