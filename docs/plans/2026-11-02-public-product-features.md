# 공개 상품 상세의 등록 특성·출처 조회

## 범위·현재 상태

- 기준 main은 `3141837a91e323d132f55031407076fa1606c81c`다. 공개 상세에 기존 `GET /api/products/{id}/features` 소비를 추가한다. 기존 Product 일곱 필드·특성 응답 여덟 필드·ApiResponse·세션·관리자 전체 PUT 계약을 바꾸지 않는다.
- 제공자 정본은 Backend의 [상품 특성 계약](https://github.com/Pubburi/Backend/blob/main/docs/PRODUCT-FEATURES.md)과 [OpenAPI](https://github.com/Pubburi/Backend/blob/main/docs/openapi/product-features.json)다. 데이터 수집·검수·권리 판단과 추천 점수/이유는 해당 제공자의 소유다.
- 기준 화면에는 관리자 GET/PUT 편집만 있고 공개 상세에는 특성 패널이 없다. 이번은 새 소비자 기능이며, 없던 기능을 과거 장애·오류율 감소·성능 개선으로 기록하지 않는다. 기존 F03 관리자 편집 완료 상태를 유지하며 R04 추천 이유·전체 FE03/C04·PostgreSQL 전환 인수는 완료로 바꾸지 않는다.
- 구현·로컬 검사와 아래 실제 legacy API의 세 상태 연결을 확인했다. 최신 PR/CI·Codex 리뷰·병합은 별도로 확인한다. 최종 기한과 기존 20개 필수 기능의 분모는 유지한다.

## 사용자 의미와 선택

상품이 정상 조회된 상세에 **상품 특성** 영역을 표시한다. 용량은 mL이며 설명·맛/향 태그·출처명·공개 출처 메모를 서버 원값으로 보여 준다. 가격/주종/도수에서 맛·향·용량을 추정하지 않는다. null은 **미확인**, 검수한 빈 태그 배열은 **등록된 태그 없음**이다. 빈 배열을 맛이나 향이 없다는 사실로 바꾸지 않는다. 개별 태그 안의 개행도 같은 태그의 원문으로 보존한다.

문자열은 React 텍스트로 렌더링한다. 출처 URL은 `new URL`로 해석한 절대 HTTP(S) 중 계정 정보가 없는 주소만 새 창 링크로 제공하고 `noopener noreferrer`를 적용한다. 상대/실행 프로토콜·제어 문자·자격정보 포함 주소는 탐색 링크나 원문으로 노출하지 않는다. 출처명·메모를 이용 권리 승인이나 독립적인 사실 검수로 표현하지 않는다.

기본 상품 응답에 특성을 합치는 대안은 기존 API/장바구니 저장 형식을 바꾸고 기본 상세의 실패 경계까지 결합하므로 선택하지 않았다. 상세가 성공한 상품 한 개만 별도 query로 읽는다. 목록 N+1 조회나 특성 쓰기를 추가하지 않는다. 상품 ID가 포함된 query key로 이전 상품 응답을 분리하고, 응답의 productId도 현재 ID와 일치해야 표시한다.

초기·재조회 중에는 특성 로딩만, 실패에는 특성 오류와 명시 재시도만 표시한다. 기본 상품 가격/담기·후기 영역을 특성 실패에 종속시키지 않는다. 캐시가 있어도 현재 재조회가 진행 중이면 이전 특성을 다시 표시하지 않으며, 관리자 저장 후 공개 상세 재진입은 기존 stale query 정책의 새 GET을 따른다. 전송 취소·다른 창 실시간 갱신·원자적인 상품/특성 버전 스냅샷을 제공하는 것은 아니다.

## 사전 고정과 검증

제품 소스를 바꾸기 전 기준 커밋·100개 프로덕션 파일의 해시·정상/미확인/검수 빈 태그/로딩·실패·재시도/이전 상품/안전하지 않은 URL의 기대 결과를 ignored 기록에 고정했다. 비교 대상은 기능 제공 여부와 계약 보존이다. 시간 측정·자연 발생 오류율·사용자 만족도의 실험은 하지 않았다.

```bash
npm run typecheck
npm run test -- src/publicProductFeatures.test.ts
VITE_API_BASE_URL=/api npm run build
npm run test:browser -- --grep '공개 상품 특성|공개 검수 빈|공개 특성|이전 상품의 늦은 특성|특성 응답 productId|390px 공개 특성|없는 상품은 특성|관리자 특성 저장 뒤 공개'
npm run check
```

선택 단위 검사 3개와 프로덕션 Chromium 13개가 통과했다. 다음은 직접 작성한 ApiResponse fixture에서 확인한 사용자 결과다.

- mL·설명 원문·단일 개행 태그·출처/메모 텍스트·새 창 링크 속성, 기존 Product 장바구니 형식과 무쓰기 조회.
- all-null과 검수한 빈 태그 배열의 구별, 안전하지 않은 URL의 비탐색/자격정보 비노출과 HTML 같은 원문의 비실행.
- 특성 GET 보류·503/명시 재시도에도 기본 상품·담기·후기가 동작하고, 완료가 담은 수량을 바꾸지 않는 경계.
- 이전 상품의 늦은 특성이 현재 상품을 덮지 않음, productId 불일치의 안전한 오류/재시도, 상품404의 특성 요청 미실행.
- 관리자 특성 저장 후 공개 상세 재진입의 최신 값, 390px 긴 원문/태그·키보드 출처 링크와 가로 넘침.

fixture와 실제 API/DB 연결은 서로 다른 근거다. 태그·출처는 허구 시연 입력이며 실제 카탈로그 사실·라이선스·학습/평가 자료가 아니다. 전후 성능 수치나 테스트 수를 서비스 성과로 표시하지 않는다.

Node **24.22.1**의 전체 `npm run check`에서 저장소 검사·locked 설치·audit 취약점 **0**·이미지 도구·strict TypeScript·단위 **76개**·프로덕션 빌드·Chromium **189개**가 통과했다. 첫 샌드박스 실행은 npm registry DNS 제한으로 audit에서 중단됐으며 성공으로 기록하지 않았다. 네트워크 접근을 허용한 실행 경로로 같은 필수 검사를 완료했고 실패 무시/무조건 재시도 설정을 추가하지 않았다. 검증이 시작한 preview만 종료했고 공유 포트나 기존 사용자 프로세스를 변경하지 않았다. 이후 제품 소스·빌드·설치·원 하네스를 동결했다.

### 실제 서버 확인 조건

동일한 불변 Backend jar와 Recommendation, 분리된 폐기 MySQL 시연 DB, 기준/후보 웹의 동결 프로덕션 파일과 같은 하네스를 사용한다. 실제 관리자 인증 뒤 새 시연 상품을 POST하여 반환 ID만 사용하고, 미확인→정상 값→검수 빈 태그를 실제 PUT/공개 GET/고객 상세에서 확인한다. 원본 상품/기존 사용자 DB는 수정하지 않으며 성공 API 응답을 가로채지 않는다. 기준 웹의 패널 미제공은 예상된 새 기능 부재로 기록한다.

실제 비교는 Backend jar SHA-256 `dcb73c35b4dbf148b05775992408b8d930977e84022fbabc878e68491ed22b81`과 Recommendation `38b32b88122dd3d9489c9459bae506c402adcfd7`, 각각 같은 80상품 시연 카탈로그에서 시작한 폐기 MySQL 8.4 DB와 동일 관리자 입력을 사용했다. 기준/후보 웹은 각각 100개 파일의 SHA-256을 고정했다. 실제 POST201로 반환받은 상품 ID에만 PUT200/GET200을 수행했으며 원본 상품·사용자 DB를 수정하지 않았다.

| 실제 API 상태 | 기준 웹의 예상 결과 | 후보 웹의 확인 결과 |
|---|---|---|
| 일곱 값 null | 기존 패널 미제공 | 용량·설명·맛·향·출처·메모 미확인 |
| 등록 값·개행 포함 단일 태그·출처 | 기존 패널 미제공 | mL·문자열/태그 원문·안전한 출처 링크 |
| 검수한 빈 맛/향 배열 | 기존 패널 미제공 | 등록된 태그 없음과 다른 미확인 값 구별 |

1280px의 세 관측에서 기본 상품 제목과 담기 버튼을 유지했고, 예상하지 않은 API 오류·pageerror·성공 응답 대체는 없었다. 별도로 연결한 기본 추천은 BASELINE이었다. 패널 부재→세 상태 제공은 새 기능의 제공 결과이며 과거 오류율 감소나 품질/시간 성과가 아니다.

최초 실제 후보 검사는 필드 표시 뒤 390px의 문서 전체 가로 넘침 검사에서 멈췄다. 읽기 전용 진단에서 같은 긴 ASCII 시연 상품명은 기준·후보 모두 390px 화면에 문서 너비 451px와 동일한 상세 grid/H1 확장을 만들었다. 특성 표시 회귀로 분류하지 않았으며 기존 상세의 긴 상품명/최소폭 결함을 FE03 후속 항목으로 남겼다. 원 하네스는 후보에만 이 전체 문서 조건을 적용했던 비대칭이 있었다. 실패 기록과 원 하네스 SHA-256 `8d6e59a5bd222033fbe96e8de6576108b668a24ae45f081541e45170591983c5`를 보존하고, 제품 소스/빌드를 바꾸지 않은 채 그 블록만 제외한 하네스 `c5ead50fa165e1061b9f9d51fe6a7d0f801e259edede4bfd4fa6b8df68e095b6`를 기준·후보 양쪽의 새 폐기 DB에 동일하게 적용해 위 결과를 확인했다. 따라서 실제 서버 근거는 **1280px 특성 필드 세 관측**이며 전체 390px/시각 인수 통과를 주장하지 않는다. 좁은 화면의 긴 특성 원문 검증은 위 직접 작성한 fixture의 독립 근거로 유지한다.

후보 웹과 선택적인 JPA 부분 제공자 연결은 위 전후 비교와 별도다. JPA에서 아직 제공하지 않는 후기 API의 정확한 404만 별도 기록하며 특성 GET/패널과 혼동하지 않는다. 이 선택 연결을 전체 상세 동등성·전체 JPA/DB 전환 완료로 확장하지 않는다.

## README 사례 판단·인계

기존 네 사례는 실제 주문/다음 입력, 경로별 최신 응답, 삭제 중 포커스, 인증 캐시와 진행 중 쓰기의 원인·대안·재현을 다룬다. 이번 새 읽기 소비는 그보다 강한 독립적인 문제 해결의 증거를 확보한 상태가 아니다. 현재 기능 한 행만 갱신하고 네 사례의 본문·순서는 보존하며 [선정 기록](../case-study-register.md)에 이유를 남긴다.

로컬 검사·실제 서버 결과·동결 파일/하네스·PR 초안과 원격 head는 ignored 인계에서 추적한다. 비공개 기획 주소·개인 경로·자격정보·원문 로컬 로그는 공개 문서/PR 근거에 포함하지 않는다. 최신 PR/CI·리뷰·native conversation·병합 main 검증과 정리는 조정자가 처리한다.
