# FE03 — 관리자 저장 응답과 새 편집 초안의 소유

## 기준과 범위

기준 main `091b4d6`의 기존 관리자 상품·매장·회원 저장을 대상으로 했다. 저장 요청이 진행되는 동안 입력을 계속하거나 다른 대상을 열 수 있지만, 이전 저장 성공은 현재 편집까지 무조건 초기화했다. 신규 기능이나 검색 UI를 추가하지 않고 기본 CRUD의 실제 입력 유실을 수정한다. 전체 FE03/C04 인수와 필수 기능 완료 집계는 유지한다.

수정 전 dist 100개 파일은 조정자가 불변 경로에 보존하고 크기/내용 SHA를 확인했다. Node 24.22.1·Playwright 1.64.1 Chromium·프로덕션 웹·직접 작성한 API fixture·고정 상품/매장/회원·유효 PUT을 보류하는 순서를 사용했다. 서버 응답/후속 조회/성공 표시가 끝난 뒤 현재 폼을 확인한다. 자연 지연이나 실제 사용자 오류율을 측정한 실험은 아니다.

## 재현과 원인

| 같은 조건의 새 편집 | 수정 전 유실 | 수정 후 유실 |
|---|---:|---:|
| 상품 저장 대기 중 같은 폼에 계속 입력 | 1/1 | 0/1 |
| 상품 저장 대기 중 다른 상품을 편집 | 1/1 | 0/1 |
| 상품 저장 대기 중 취소 후 신규 초안 작성 | 1/1 | 0/1 |
| 매장 저장 대기 중 다른 매장을 편집 | 1/1 | 0/1 |
| 회원 저장 대기 중 다른 회원을 편집 | 1/1 | 0/1 |

원래 상품/매장 폼은 빈 값으로 바뀌었고 회원 편집 폼은 닫혔다. 고정 다섯 조건의 유실은 5/5 → 0/5, 해당 집합의 유실 비율은 100% → 0%(100%p 차이)다. 실제 사용자 오류율·서비스 성능 개선율로 확대하지 않는다. 필수 이미지가 없는 상품의 준비 시도는 HTML 검증으로 PUT이 0건이었으므로 이 분모에서 제외했다. 이미지가 있는 유효 제출로 기준을 다시 확보했다.

기존 코드는 form과 editing을 별도 상태로 두고 `ui.run` 성공 뒤 `reset()`을 호출했다. 제출 시점의 API 대상/본문은 이미 고정돼 있어도, 완료 시점의 폼이 여전히 그 제출의 소유인지 검사하지 않았다. 따라서 다른 행/새 입력을 선택한 결과도 이전 요청의 후처리로 사라졌다.

## 구현과 대안

- 편집 대상과 입력 폼을 하나의 immutable draft 상태로 묶는다. 입력·대상 선택·취소/초기화는 새로운 draft를 만든다.
- 저장 시작 때 draft의 폼과 대상을 캡처한다. 실제 API 요청은 그 제출 대상/본문을 사용한다.
- 성공 뒤 현재 draft가 제출 객체와 동일한 경우에만 폼/대상을 함께 초기화한다. 사용자가 이어서 입력하거나 다른 대상을 열었으면 그대로 둔다. 값이 같아도 취소 뒤 다시 연 편집은 다른 의도다.
- 변경 없는 성공의 기존 초기화, 쓰기 거절의 입력 보존, 단일 pending 키와 명시적 재제출, API·권한·목록/카탈로그 재조회는 유지한다. 비밀번호/폼을 외부 저장소에 보관하지 않는다.

저장 중 폼/다른 행 선택을 모두 막는 방법은 사용 가능한 편집 흐름을 제한하므로 선택하지 않았다. 대상 ID만 비교하면 같은 대상의 새 입력과 취소/재진입을 구분하지 못하고, 값 비교도 새 편집 의도를 잃는다. 늦은 응답을 서버에서 취소할 수 있다고 가정하는 대신 로컬 후처리의 소유만 확인한다.

## 검증과 한계

같은 다섯 조건 외에 동일 값으로 재편집하기, 신규 POST 뒤 다음 초안, 쓰기 거절 뒤 다른 대상의 명시적 저장, 새 편집이 없을 때의 정상 초기화를 확인한다. 기존 고객·관리자 CRUD·상품 특성·취향/기본 목록·찜·장바구니/가격·권한·포커스 흐름도 전체 검사에서 유지한다.

실제 서버 비교 harness는 조정자 전용으로 작성한다. 동일 seed/규모의 서로 다른 전용 스키마에 같은 관리자/다른 회원·고정 namespace·생성 순서/입력을 사용한다. 실제 PUT 200과 DB 반영을 먼저 확인하고, 원본 응답의 브라우저 전달만 잠시 보류한 동안 새 초안을 작성한다. 응답·권위 조회/성공 후 초안 위반을 계속 집계하며 인프라 실패는 별도로 둔다. API 업무 응답을 가짜로 만들지 않지만, 제어한 전달 경합이라는 조건은 명시한다. 실행/공유 자원은 조정자가 소유한다.

- 구현/선택 회귀: 위 다섯 조건의 유실 0/5와 추가 경계까지 브라우저 9개 통과.
- 전체 Node 24 검사: `npm run check`가 통과했다. 저장소 검사·locked npm ci·audit(취약점 0)·이미지 도구·strict TypeScript·단위 48개·프로덕션 빌드·Chromium 89개를 확인했다. 새 관리자 초안 경계는 9개다. 테스트 범위이며 서비스 성능 수치가 아니다.
- 실제 서버 before/after: harness 작성·구문검사 후 조정자 실행 대기.
- 최신 head CI·Codex 리뷰·병합/main CI와 전체 FE03/C04 최종 인수는 별도 게이트다.

관리자 권한/계정 전환 전체 경쟁, 서버에 이미 반영된 뒤 재조회 실패의 조정, 여러 창의 동시 편집은 이번 로컬 초안 보존으로 해결했다고 주장하지 않는다. README의 기존 네 사례와 순서는 유지하며 실제 근거는 이 계획/PR에서 관리한다.
