# F02 맛·향 태그의 반복 조건 검색

## 범위·기준

- 기준 main은 `8417ffe`다. 공개 상품 목록에 맛/향 태그 조건을 추가해 기존 [Backend 상품 검색 계약](https://github.com/Pubburi/Backend/blob/main/docs/PRODUCT-SEARCH.md)의 반복 `tasteTag`/`aromaTag`를 소비한다. 가격·도수 네 범위·실제0·주종/검색어·정렬/페이지·ApiResponse·Product 일곱 필드·세션/장바구니는 보존한다.
- 새 소비자 기능의 제공이며, 기준 화면의 태그 입력 부재/URL 미소비를 과거 장애나 오류율/시간 성능 개선으로 기록하지 않는다. OpenSearch·자동완성·동의어/오타·전체 F02와 FE03/C04 인수는 별도다.
- 목록은 상품 특성을 추가 수집하거나 맛을 추정하지 않는다. 검색 조건이 없는 배열은 **검색 제한 없음**이며 원천 특성의 null/검수한[] 상태를 선언하는 값이 아니다. 양성 조건에서 미확인/빈 특성이 제외되는 것은 제공자 검색 의미다.

## 입력·정규화·직렬화

별도 검색 fieldset에서 **맛 조건 추가/향 조건 추가**로 textarea 한 행을 만든다. 행 하나가 태그 하나이며 쉼표·내부 개행을 구분자로 나누지 않는다. Enter는 textarea 안에서 개행을 입력하고, 검색하기 버튼의 키보드 Enter나 다른 검색 필드의 Enter는 새 조건을 첫 페이지에 적용한다. 행 추가는 새 입력에, 삭제는 인접 입력/추가 버튼에 포커스를 연결한다.

제공자는 각 종류 최대20개·원문과 Locale.ROOT 소문자 변환 뒤 각각40 UTF-16 단위까지 허용한다. 클라이언트는 Java17 Character whitespace에 따른 앞뒤 strip과 ASCII A–Z 변환만 수행한다. NBSP·figure/narrow NBSP·FEFF와 내부 쉼표/개행·모든 비ASCII 대소문자/코드포인트를 URL/API에서 보존하며, 나머지 정규화의 권위는 제공자에게 둔다.

로컬에서 확정할 수 있는 빈 행·원문 초과 길이·정확/ASCII 동등 중복·21개는 지우거나 자르지 않고 오류 설명/첫 오류 포커스로 수정한다. URL로 동일하게 표현할 수 없는 고립 surrogate도 거절해 다른 문자로 바뀌는 전송을 막는다. 비ASCII 정규화 중복·변환 뒤 길이 초과는 실제 제공자의400으로 처리한다. 그 응답은 조건 수정 안내·현재 URL/새 초안을 보존하고 명시적 수정 버튼만 포커스를 이동한다. 재연결 자동 재요청이나 무제약 fallback은 하지 않으며 실패 필드/원인을 추측하지 않는다. 두 종류 사이의 같은 문자열은 서로 다른 조건이므로 허용한다.

기존 관리자 태그 편집기는 원천의 확인 상태를 편집하므로 재사용하지 않았다. 검색 전용 행을 사용해 원천 사실과 검색 의도를 구분한다. 쉼표/개행으로 입력 전체를 split하는 대안은 단일 태그를 바꾸고, 배열을 `String()`으로 직렬화하는 대안은 여러 태그를 쉼표 한 값으로 합치므로 선택하지 않았다.

URL은 `getAll`로 각 종류의 모든 원문을 복원하고, 검증한 검색/페이지 URL과 API는 `append`로 값을 반복한다. 직접 URL의 로컬에서 확정 가능한 빈/원문 긴/정확·ASCII 동등 중복/21개 조건은 상품 GET 없이 수정/해제를 안내한다. 빈 배열은 파라미터를 생략하지만 명시한 빈 항목을 조용히 제거하지 않는다. 기존 단일 query 값의 직렬화는 유지한다.

현재 적용 태그는 URL에서 별도로 표시하고 미제출 행 편집은 결과/API를 바꾸지 않는다. 검색은 정규화한 입력을 첫 페이지에 반영하고, 같은 의미의 URL에 다시 제출해도 입력을 정규화한다. 이전/다음은 현재 적용 조건만 사용하며 반복 태그·가격/도수·뒤로/새로고침/전체 해제와 이전 GET의 늦은 응답 격리를 보존한다.

## 사전 고정·로컬 검증

제품 소스를 바꾸기 전에 기준100개 프로덕션 파일·소스/README·직접 작성한 시나리오를 SHA-256으로 고정했다. 같은 새 입력 시나리오를 기존 프로덕션 웹에 먼저 실행해 조건 추가 버튼 부재를 확인했다. 기능 부재 관측이며 결함 감소의 분모가 아니다. 원 시나리오는 실행하지 않는 문서 확장자로 보존했다.

```bash
npm run typecheck
npm run test -- src/productTags.test.ts src/utils/productFilters.test.js src/services/api.test.js
VITE_API_BASE_URL=/api npm run build
npm run test:browser -- product-tags.spec.js
npm run check
```

최종 선택 단위18개와 태그/기존 범위 프로덕션 Chromium33개가 통과했다. 태그18개에는 Unicode 원문 전송과 제공자400의 보류 중 새 초안·재연결 무재시도·명시 수정/복구, 이전 조건의 늦은400 비차폐가 포함된다.

- 반복 값·단일 쉼표/개행과 정규화, Java whitespace/NBSP/FEFF·UTF-16 원문 경계·비ASCII 대소문자 보존/제공자 변환 경계, 확정 가능한 빈/긴/중복/20개 허용·21개 거절.
- 실제 API 요청의 반복 query·쿠키와 기존 scalar 직렬화, 가격·도수0/조건 AND·원천 unknown/검수[]의 양성 조건/미지정 구분.
- URL 복원·초안/적용 조건·같은 URL의 정규화·페이지/뒤로/해제·이전 태그 보류 응답/503 명시 재시도.
- 390px 웹의 행 추가/삭제·textarea Enter 개행·오류 설명/포커스·키보드 검색과 가로 너비, Product7 장바구니 보존·목록 특성 N+1/업무 쓰기 미실행.

첫 전체 검사에서는 기존 범위의390px Tab 검증이 새 태그 추가 버튼을 거치지 않고 검색 버튼으로 바로 이동한다고 가정해 실패했다. 원문/trace를 보존하고 범위→맛 추가→향 추가→검색의 실제 키보드 연결을 검증하도록 수정했다. assertion 제거·skip·timeout 확대를 하지 않았으며 이 검증 기대의 변경을 제품 결함 감소로 세지 않는다.

직접 작성한 fixture는 실제 주류 사실·추천 학습/평가 자료나 Backend E2E가 아니다. 실제 연결과 fixture를 합산하거나 테스트/CI 수를 서비스 성능으로 표시하지 않는다.

Node **24.22.1** 최종 `npm run check`는 저장소 검사·locked 설치·audit 취약점 **0**·이미지 도구·strict TypeScript·단위 **86개**·프로덕션 빌드·Chromium **234개**를 통과했다. 별도의 최종100개 프로덕션 파일과 소스/시나리오를 SHA-256으로 고정했고 이전 후보 파일과 구분해 보존했다. 자체 preview는 종료했고 기존 사용자 프로세스를 변경하지 않았다.

## 사전 후보의 Unicode 계약 검토와 선택

초기 후보는 브라우저 `toLowerCase()`를 사용했다. 실제 Temurin17.0.21과 Node24.22.1(Unicode17) 비교에서 U+1C89는 Java가 보존하지만 Node는 U+1C8A로 바꿨다. 문맥도 달랐다: `A:Σ`는 Java `a:σ`/Node `a:ς`, `A-Σ`는 Java `a-ς`/Node `a-σ`였다. 신규 후보가 검색할 리터럴을 먼저 바꿀 수 있는 구체적인 제공자 호환성 문제로 분리했다.

Java17 전체 단일 문자 매핑은 작게 만들 수 있지만 Σ는 원문 기반 ROOT WordBreakIterator 문맥까지 필요했다. 작은 예외 마스킹만으로 이를 보장하지 않고, 정규화 엔진/word-break 테이블을 웹에 이식하는 대신 제공자 권위를 선택했다. 생성 실험은 비공개 증거로 보존하고 제품에는 데이터/생성기를 넣지 않았다. Java17 독립 검토에서는 모든 ASCII 쌍의 cased/word-category 일치와 고정 문맥·혼합 문자열의 ASCII 변환 후 제공자 결과 불변을 확인했다. 이는 전 Unicode를 브라우저에서 동일하게 구현했다는 주장이 아니다.

## 실제 연결·README 판단·인계

불변 legacy Backend jar(SHA-256 `dcb73c35b4dbf148b05775992408b8d930977e84022fbabc878e68491ed22b81`), 고정 Recommendation `7ba8c9d21fb7021886f2bdd9f187c1dd3facbf31`/B0와 폐기 MySQL을 사용했다. 원래80상품을 보존하고 새로 만든6개 태그 대조 상품만 추가한 같은86상품 DB에 기준 main/최종 웹과 같은1280px 읽기 전용 하네스(SHA-256 `915fc71529d6b137ae19bd7e512f52cd2804396238f92114ad1e3c3ceb36daf4`)를 적용했다.

- 기준 main에는 두 조건 추가 버튼이 없고 태그 URL을 소비하지 않아 이름/범위 조건의6개를 표시했다. 최종 웹의 쉼표/개행 두 맛 태그·향 태그·네 범위(실제0 포함) AND는 독립 GET과 같은 ID81/총1개였다.
- 쉼표 한 태그를 두 개로 나눈 명시 조건은 다른 대조 ID82와 일치했다. 미제출 편집은 적용 조건과 요청을 바꾸지 않았고, 같은 의미의 명시 제출은 ID81/캐시0 GET을 유지했다. 전체 해제는86개, 확정 가능한 ASCII 중복 URL은 상품 GET0건이었다.
- 미확인 null·검수[]·일부 태그만 가진 상품과 다른 향의 상품은 양성 조건을 만족하지 않았다. 원천의 실제 맛이나 사용 권리를 검증한 결과로 바꾸지 않는다.

Unicode 검증은 위86상품과 별도의 폐기 DB에서 원래80상품+새 Unicode 상품1개로 수행했다. 같은 수정된 하네스(SHA-256 `9ab266be58d6b8af6bd6ce684b85183713b87a73fea71bdda68085edcd53ead6`)를 동결한 **초기 미병합 후보와 최종 후보 양쪽**에 적용했다. 직접 원문 URL은 양쪽 모두 독립 GET과 같은1개였으며, 문제의 트리거는 명시적 검색 제출이었다.

| 별도 Unicode 조건 | 초기 미병합 후보 | 최종 후보 |
|---|---|---|
| U+1C89 / A:Σ / AΣ:A / İ 직접 원문 URL | 원문 전송·같은 상품1개 | 원문 전송·같은 상품1개 |
| 명시적 검색 제출 | U+1C8A / a:ς / aσ:a / i+결합점으로 변형·0개 | U+1C89 / a:Σ / aΣ:a / İ 보존·독립 GET과 같은1개 |
| 제공자의 Σ/σ 중복400·İ 40개 변환 길이400 | 이 전후 조건의 분모에 포함하지 않음 | URL/모든 입력·결과 차폐·명시 포커스 유지, 새 GET/무제약 전송 없음 |

처음 Unicode 하네스가 직접 URL부터 실패할 것으로 가정한 준비와 wire 기대의 보완 기록은 보존했다. 관측에 맞춘 같은 최종 하네스로 양쪽을 다시 실행했으며 직접 URL이 틀렸다고 주장하지 않는다. 이는 초기 미병합 후보의 리터럴 전송 수정이며 과거 main의 운영 장애·자연 오류율·성능 개선이 아니다.

두 실제 검증의 예상하지 않은 API 오류·pageerror·응답 대체·하네스 업무 쓰기는 없었고 알려진 두400은 조건 거절로 별도 확인했다. 조정자가 시작한 모든 프로세스를 정리했으며 원본 상품/계정은 수정하지 않았다. 실제 대조 입력은 허구 시연 값이고 fixture33개와 실제 관측을 합산하지 않는다.

반복 조건과 리터럴 보존·새 입력 UX를 제공한 새 기능이며 기존 네 사례보다 강한 과거 문제 해결의 독립 영향을 입증하지 못했다. README 현재 기능 한 행만 갱신하고 주문/다음 입력, 최신 응답, 파괴적 DOM 포커스, 인증 캐시/진행 중 HTTP의 네 사례와 순서/코드를 보존한다. [선정 기록](../case-study-register.md)에 판단을 남기며 README에는 테스트/CI 집계를 추가하지 않는다.

Unicode 후보 검토는 실제 리터럴 변형의 원인·제공자/브라우저 차이·대안·같은 서버의 트리거까지 확보한 보완이다. 초기 구현이라는 이유로 제외하지는 않았다. 다만 현재 원천 태그의 실서비스 영향 대신 새 허구 대조1상품의 경계이며, 기존 네 사례가 다루는 주문/다음 입력·일반 탐색의 요청 경합·파괴적 작업의 포커스·개인 쓰기 수명보다 강한 독립 영향을 입증하지 못해 이번에는 선정 판단을 유지한다.

최신 PR/CI·완료 Codex 리뷰·미해결 대화·한국어 Squash/main CI·브랜치 정리는 조정자가 확인한다. 비공개 기획 주소·개인 경로·자격정보·원문 로컬 로그는 공개하지 않는다. 이번 기능을 검색 엔진·추천 품질/이유·전체 F02/FE03/C04·DB 이관 완료로 확장하지 않는다.
