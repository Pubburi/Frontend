# FE03 — 기존 소수 후기 평점의 편집 선택 보존

## 기준과 사전 재현

기준 main `372a7a9`의 상품 상세 후기 편집을 대상으로 했다. 공통 API의 CommentCreateRequest/CommentUpdateRequest는 float 평점 0.5–5를 허용하며 반점 간격으로 제한하지 않는다. 반면 웹 편집 select에는 정수 5/4/3/2/1만 있어 유효한 기존 소수값을 선택하지 못했다. 새 후기 생성의 정수 선택 정책이나 API/추천 정책은 이번에 바꾸지 않는다.

기준 프로덕션 웹 100개 파일은 조정자가 불변 보존했다. Node 24·Chromium·같은 직접 작성한 API fixture에서 저장 평점 0.5와 4.5의 본인 후기를 각각 열었다. 두 경우 모두 아직 PUT은 0건이고 fixture 저장값은 그대로인데, 실제 DOM select value와 선택된 option은 5점이었다.

| 고정 조건 — 각 1회 | 저장값 | 기준 편집 선택값 | 수정 편집 선택값 |
|---|---:|---:|---:|
| 기존 0.5점 후기 열기 | 0.5 | 5 | 0.5 |
| 기존 4.5점 후기 열기 | 4.5 | 5 | 4.5 |

선택 표시 위반은 2/2 → 0/2다. **기존 DB 평점 유실을 재현한 것이 아니다.** 원래 코드도 사용자가 평점을 바꾸지 않고 본문만 저장하면 React state에 남은 기존 평점을 PUT했다. 화면 선택값과 제출 상태가 달랐고 정수 선택 후 원래 소수값으로 돌아갈 옵션이 없던 문제다. 자연 장애율·사용자 오류율·성능 개선으로 해석하지 않는다.

## 원인과 구현

제어 select의 value는 API 평점인데 option 집합은 정수뿐이었다. 값에 해당하는 option이 없으면 현재 Chromium은 첫 정수 항목을 표시했다. 데이터를 정수로 반올림하거나 제출값을 표시값 5로 바꾸는 방식은 원래 평점을 변경하므로 채택하지 않았다.

- 편집 시작 평점을 메모리 draft의 initialRating으로 보존한다. 기존 편집 입력/취소/성공의 immutable draft 소유는 유지한다.
- 정수 기본값·편집 시작값·현재 draft값·최신 조회값을 중복 없이 정렬해 편집 선택지에 포함한다. 정수를 골랐다가 원래 소수값으로 다시 돌아갈 수 있다.
- 재연결 조회가 원본 평점을 바꿔도 현재 선택과 시작값을 갑자기 옵션에서 잃지 않는다. 현재 draft를 서버의 동시 변경과 자동 병합하거나 잠그는 기능은 아니다.
- 기존 API 본문에는 rating/comment만 보낸다. initialRating은 서버·브라우저 보관 데이터에 추가하지 않는다. 생성 선택·권한·세션·정적 자산·후기 최대 길이 계약은 유지한다.

반점 선택지만 늘리면 유효한 2.25 같은 기존 값이 빠지고, 현재 draft값만 추가하면 정수로 바꾼 순간 원래 선택지를 잃는다. 전체 API 평점 정책을 새로 만드는 대신 기존 값의 편집 가능성과 표시를 보존하는 범위로 한정했다.

## 검증 범위

고정 두 조건 외에 0.5/4.5/2.25의 본문만 PUT과 정수→원래값 재선택, 재연결 중 원본 변경/초안·시작값 보존, 저장 거절/명시적 재시도, 다른 회원의 편집 조작 숨김/관리자 선택값을 확인한다. 이 추가 조건을 고정 두 표시 비교의 분모에 합산하지 않는다.

390px 웹에서는 정수/원래값 선택 보존 뒤 select→본문→취소→저장으로 실제 Tab 포커스를 이동하고 Enter로 저장한다. option 기능 선택은 selectOption으로, 폼 이동/저장은 실제 키 입력으로 구분한다. 네이티브 popup의 화살표 선택 전체를 검증한 것은 아니다. 초기 ArrowDown/Space/Enter 자동화 시도는 앱 밖의 독립 HTML select에서도 동일하게 선택을 확정하지 못했다. 이 준비 시도는 앱 결함/개선 횟수에 합산하거나 timeout 확대/무조건 재시도로 숨기지 않았다. 전체 OS·스크린리더 인수는 FE03 남은 조건으로 유지한다.

실제 서버 비교는 조정자가 정본의 후기 POST201/GET/PUT200으로 별도 실행했다. 0.5/4.5는 동일한 비교 조건으로, 추가 2.25·390px/다른 시연 USER의 실제 PUT403은 별도 after 표본으로 나눠 확인했다.

## 상태와 한계

제품 수정과 선택 회귀를 완료했다. Node 24 `npm run check`에서 저장소 검사·locked 설치·audit(취약점 0)·이미지 도구·strict TypeScript·단위 53개·프로덕션 빌드·Chromium 124개를 확인했다. 새 회귀는 고정 두 조건과 별도 일곱 경계다. 테스트 집계는 서비스 성능 수치가 아니다. 실제 서버 고정 비교의 표시/재선택 위반도 2/2 → 0/2였고 추가 표본은 별도로 통과했다. 최신 head 리뷰/CI·병합/main CI는 별도 게이트다. 여러 창의 동시 편집 충돌/서버 CAS, API 값의 전수 정밀도, 생성 평점 정책·추천 학습/품질은 이번 변경의 보장 범위가 아니다. FE03/C04 전체 체크리스트나 새 필수 기능을 완료 처리하지 않는다.

README의 기존 네 사례는 보존한다. 실제 계약/화면 불일치 수정이지만 현재 네 소재보다 더 강한 독립 영향·원인 규명/대안·구현 기여를 갖췄다고 볼 근거는 부족하다. 검증 횟수·절차·CI 집계는 이 계획/PR에 둔다.

## 실제 서버 전후 비교

Java 17·MySQL 8.4·Node 24·Chromium의 같은 실행 환경에서 초기 80상품의 동일 시연 seed를 별도 폐기 before/after DB에 준비했다. 같은 시연 계정/입력·같은 Backend jar(SHA256 `c311c255434c558dc0254b0016e3eab96a06cccecedf7bd207bab6944c45af17`)·같은 도구(SHA256 `90bcb4424f5216fb0cb6cae7bf5d03594dcb691d19267ca09f85197c66fd0878`)를 사용했다. 기존 사용자 DB/볼륨·외부 계정을 사용하지 않았다.

기준 main `372a7a9` 웹의 compact 파일 목록 SHA256은 `197768ef0d2e9973f3ce529ace96b57ece4da2d6070b933f0dcc2e68fde4ae56`이다. 수정 웹 100파일의 compact 목록 SHA256은 `58de74d8b998eb64738cbeb787717a5cb7240e1289218c718c3d6afd5559486c`, manifest 파일 자체 SHA256은 `e649f7590fe9a60919ee9e0a399a6b1ae491e5c551a38c0a7a857963c7e8f2f2`다. 파일 목록과 manifest 자체 hash를 구분하며 실제 비교 동안 소스/빌드를 바꾸지 않았다.

| 실제 조건 — 각 1회 | 기준 선택값/원값 옵션 | 수정 선택값/원값 옵션 | 본문만 PUT의 원평점 보존 |
|---|---|---|---|
| 0.5점 후기 | 5 / 없음 | 0.5 / 있음 | 양쪽 모두 보존 |
| 4.5점 후기 | 5 / 없음 | 4.5 / 있음 | 양쪽 모두 보존 |

양쪽 모두 실제 POST201→GET과 본문만 PUT200을 확인했다. 수정 웹은 정수 3을 선택했다가 원래 소수값을 다시 골라 PUT200·서버 조회 보존도 확인했다. 기준 웹은 원값 option이 없어 이 조작을 완료할 수 없었으므로 취소했고, 평점이 이미 유실된 것처럼 표시하지 않았다. 각 모드 인프라는 성공했고 예상외 API 오류·pageerror·API mocking은 없었다. 최초 비회원 auth/me 401만 정상 비회원 응답으로 구분했다. 웹 프록시→Backend→고정 Recommendation B0의 기본 목록 BASELINE도 확인했다.

고정 두 조건의 **선택 표시/원값 재선택 위반**은 2/2 → 0/2, 이 집합의 비율은 100% → 0%(100%p 차이)다. 각각 한 번의 기능/정합성 관측이며 운영 오류율·사용자 선호·데이터 유실 복구·시간 성능 개선이 아니다. 지원하지 않는 옵션 때문에 기준에서 실행하지 못한 원값 복귀를 가짜 PUT으로 채우지 않았다.

### 별도 after 추가 표본

같은 수정 웹/Backend/도구의 별도 추가 모드에서 2.25점 후기 1개를 검증했다. 선택값·본문만 PUT200/평점 보존·정수 3→2.25 재선택/PUT200을 확인했다. 다른 실제 시연 USER의 PUT은 403/FORBIDDEN으로 거절됐고 원문/평점은 바뀌지 않았다. 390px 웹의 가로 넘침도 없었다. 인프라 성공·예상외 API 오류/pageerror/API mocking 없음과 기본 목록 BASELINE을 확인했다.

이 추가 표본의 위반 없음은 고정 두 조건의 원인 비교에 합산하지 않는다. 기존 권한 동작의 확인이며 이번 선택창 수정이 새 서버 권한 기능을 만든 것은 아니다. Tab/Enter 조작과 재연결/거절 경계는 별도 fixture 근거로 유지하며 실제 서버의 전체 키보드·동시성 인수로 확대하지 않는다.

### 공개 재현 절차와 근거

1. 동일 seed와 시연 입력을 별도 폐기 before/after DB에 준비하고 기준/수정 웹의 크기/SHA를 확인해 동결한다. 같은 Backend와 도구를 사용한다.
2. 실제 시연 USER로 로그인하고 유효한 0.5/4.5 후기를 각각 POST201로 만든다. GET의 원평점과 본인 소유를 확인한 뒤 웹 편집창을 연다.
3. 실제 select의 선택값을 기록하고 본문만 수정해 PUT200/GET의 평점 보존을 확인한다. 표시 불일치와 서버 값 유실을 구분한다.
4. 정수 3을 선택하고 원래 소수값 option이 있으면 재선택·PUT200/GET을 확인한다. 없으면 취소하고 재선택 위반으로 집계하며 API 성공을 가짜로 만들지 않는다.
5. 2.25·390px/다른 USER의 403은 별도 after 표본으로 실행한다. 실패/인프라와 제품 위반을 구분하고 원문 계정·비밀번호·개인 경로·로그를 공개하지 않는다.

공개 근거는 [편집 평점 선택/시작값 처리](../../src/pages/CatalogPages.tsx), [고정 및 추가 API fixture](../../tests/browser/smoke.spec.js), Backend의 [등록 평점 계약](https://github.com/Pubburi/Backend/blob/main/src/main/java/com/pubburi/pub/controller/request/CommentCreateRequest.java)·[수정 평점 계약](https://github.com/Pubburi/Backend/blob/main/src/main/java/com/pubburi/pub/controller/request/CommentUpdateRequest.java)와 위 절차다. 원문 실행 도구/보고서는 ignored 기록으로 보존한다.
