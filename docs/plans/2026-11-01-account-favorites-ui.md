# F01 — 본인 찜 상세·목록 연결

## 범위와 상태

- 담당: Frontend. 제공자 정본은 [Backend ACCOUNT-FAVORITES](https://github.com/Pubburi/Backend/blob/main/docs/ACCOUNT-FAVORITES.md)와 [OpenAPI](https://github.com/Pubburi/Backend/blob/main/docs/openapi/account-favorites.json)다.
- 계획/구현: 상품 상세의 저장·해제, 보호된 `/favorites` 목록과 마이페이지 진입, 현재 상품 링크·정보·페이지·빈/실패 상태를 구현했다.
- 프론트 검증: strict TypeScript·API/상태 단위 검증과 프로덕션 Chromium API fixture 검증을 수행한다. 최종 결과는 아래에 기록한다.
- 단건 상태 GET 추가는 조정자가 승인한 계약이다. 제공자 후속 PR의 main 반영 전에는 이 GET을 요구하는 실제 연동 검증·프론트 병합을 대기한다. 기존 목록 GET/PUT/DELETE와 별도의 API를 임의 구현하지 않는다.
- 실제 Backend/MySQL 통합: 조정자가 확정된 제공자 코드와 동결한 dist로 실행할 예정이며, 이 문서 작성 시점에는 미완료다.
- 병합: 최신 head CI·Codex 리뷰·실제 연동 확인 뒤 별도 판정한다. F01 전체와 FE03/C04 최종 인수를 미리 완료 처리하지 않는다.

## 계약과 사용자 흐름

1. 비회원 상세에는 해당 상세로 돌아오는 로그인 링크를 제공한다. 찜 API를 호출하지 않으며, 세션 조회 장애를 비회원으로 취급하지 않는다.
2. 로그인 상세는 승인된 `GET /users/me/favorites/{productId}`의 `{productId, favorited}`로 초기 상태를 확인한다. 미등록/삭제 상품은 false이며, 조회 실패를 false로 꾸미지 않는다. 실패 시 명시적 재조회만 제공한다.
3. 저장은 body 없는 PUT, 해제는 body 없는 DELETE다. 로그인 계정만 소비하며 userId·authEpoch·상품 내용은 전송하지 않는다. ADMIN도 자기 계정의 찜을 본다.
4. 마이페이지와 상세에서 `/favorites`로 이동한다. 최근 담은 순서·현재 Product 7필드·상세 링크를 사용하고 서버 PageResponse의 총수/페이지를 따른다. 첫 페이지에 없다는 이유로 상세의 찜 여부를 판단하지 않는다.
5. 목록은 요청한 12개짜리 페이지 하나만 읽는다. 카탈로그 카드의 N+1 상태 조회, 전체 목록을 얻기 위한 무제한 페이지 순회는 없다. 전체 찜을 브라우저에 저장하지 않는다.
6. 상품 삭제/해제로 마지막 페이지가 사라지면 서버 totalPages를 기준으로 유효한 마지막 페이지로 replace 이동한다. 이 보정 중 전체 목록이 비었다고 안내하지 않는다. 오류·비어 있음·진행 중 상태를 구분한다.

## HTTP 수명과 응답 소유

- 같은 계정·상품의 전송 중 버튼을 비활성화하고 Zustand의 동기 소유 토큰으로 중복 PUT/DELETE와 반대 의도를 차단한다. 전송이 끝난 뒤 새 GET을 확인하고 다음 의도를 받는다. 뒤늦은 자동 반전·재전송·오프라인 쓰기 큐는 만들지 않는다. 다른 상품과 다른 계정은 독립적이다.
- 로그인/로그아웃의 `QueryClient.clear()`는 유지한다. 이미 서버에 도달한 HTTP는 캐시 초기화로 취소되지 않으므로 소유 토큰은 Query 캐시 밖에 둔다. 같은 계정으로 재로그인하면 기존 전송이 끝날 때까지 해당 상세/계정 목록의 새 읽기를 보류한다.
- 성공 여부와 무관하게 소유자의 finally에서 읽기 세대를 증가시킨다. 목록과 단건 상태 키는 계정·페이지/상품·세대를 포함한다. 완료 전의 늦은 GET이 완료 뒤 새 읽기 결과를 덮지 못한다. 응답 실패가 실제 저장 실패를 보장하지 않으므로 오류 뒤에도 GET으로 서버 상태를 다시 확인한다.
- 성공 알림·실패·401 세션 정리는 요청 시작 때 캡처한 세션 객체가 현재 세션과 같을 때만 반영한다. 다른 계정과 같은 계정의 새 로그인 세션에 이전 결과를 적용하지 않는다. 화면을 떠난 뒤 성공 알림을 새 화면에 덮어쓰지 않는다.
- 미완료 토큰/읽기 세대에는 값·비밀번호·찜 목록을 보관하지 않는다. 서버 변경·다른 탭·전체 새로고침을 가로지르는 분산 직렬화까지 보장하는 설계가 아니다. 서버 idempotency/epoch/트랜잭션을 대체하지 않는다.

## 검증과 한계

- API fixture: 상세의 정확한 상태·저장/해제·새로고침·키보드·390px, 첫 목록 페이지 밖 상품의 단건 상태, 조회 실패를 미등록으로 추정하지 않음, 필요한 페이지/현재 상품 정보/삭제 뒤 페이지 보정.
- 계정/경합 fixture: PUT와 DELETE의 전송 중 중복 차단·같은 계정 재로그인 대기, 다른 계정의 늦은 GET/DELETE 성공·401 격리, 늦은 이전 목록 GET의 복원 방지, 503·404와 서버 저장 후 응답 실패의 권위 재조회, 재연결 후 자동 쓰기 재전송 없음.
- 단위: 소유자만 해제·같은 상품 중복/반대 차단·다른 상품/계정 독립성·캐시 초기화 뒤 수명·세대별 GET 키·URL offset 경계·본인 경로/쿠키/body 없는 계약.
- 초기 offline fixture는 온라인 복귀 전 새 조회가 끝나야 한다고 잘못 기대했다. Query의 read는 온라인 복귀를 기다리므로 복귀 뒤 권위 읽기 완료를 기다리도록 고쳤다. 쓰기를 자동 재전송하지 않는 조건은 유지했다. 제품 실패를 재시도로 숨긴 변경이 아니다.
- 실제 서버용 ignored harness는 작성·구문검사만 하고 조정자 실행으로 분리한다. 시연 계정의 찜은 명시 입력이며 실사용자 인기·구매·추천 품질이 아니다. 지연을 제어한 정확성 실험은 자연 부하·서비스 성능 수치가 아니다.
- 기능 추가이므로 과거 운영 장애나 인위적 전후 성능 수치를 만들지 않는다. README의 기존 네 사례와 비교했을 때 이번 흐름은 기존 HTTP 소유 사례의 적용 확장에 가깝다. 독립적인 더 강한 원인/개선 근거를 확보하기 전 네 사례를 보존한다.

## 최종 로컬 검증

Node 24.22.1의 `npm run check`가 통과했다. 저장소 검사·locked npm ci·audit(취약점 0)·이미지 도구·strict TypeScript·Vitest 47개·프로덕션 빌드·Chromium 60개가 모두 성공했다. Chromium 60개 중 새 찜 흐름은 17개이며, 이는 테스트 범위이지 서비스 성능 지표가 아니다. 기존 장바구니·취향·상품 특성·후기·관리자·세션·포커스 회귀를 함께 실행했다.

README 네 사례/코드 발췌는 기준 main과 동일함을 비교했고 기능표만 추가했다. `git diff --check`와 실제 서버 harness의 `node --check`가 통과했다. Playwright가 시작한 4173 preview는 종료했다. 실제 서버 연동은 API fixture와 별도로 조정자가 동결 dist를 사용해 확인해야 한다.
