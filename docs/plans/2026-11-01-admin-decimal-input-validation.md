# FE03 — 관리자 유효 소수값의 native 제출 차단 해소

## 기준과 사전 재현

기준 main `9719d6b3`의 프로덕션 웹100파일·입력·하네스와 최초 결과를 불변 보존했다. 제공자 [ProductRequest](https://github.com/Pubburi/Backend/blob/main/src/main/java/com/pubburi/pub/controller/request/ProductRequest.java)는 도수 float0–100, [MarketRequest](https://github.com/Pubburi/Backend/blob/main/src/main/java/com/pubburi/pub/controller/request/MarketRequest.java)는 위도 double−90–90/경도 double−180–180을 허용하며 이 필드에 소수 자릿수 제한을 두지 않는다. 웹은 도수step0.1·좌표step0.000001을 추가하고 있었다.

Node24·Chromium·독립127.0.0.1 동적 포트의 같은 API fixture에서 기존 행을 열고 **이름만 변경**했다. 주종·가격·필수 이미지/이름 등 다른 입력은 모두 유효하게 준비했다. 양쪽 범위 오류는 false인데 stepMismatch가 true였고, 저장 클릭 후 native validation이 submit을 막아 PUT은0건이었다.

| 고정 조건 — 각1회 | 기존 값 | 기준 결과 | 수정 결과 |
|---|---|---|---|
| 기존 상품 이름만 변경 | 도수6.25 | stepMismatch·PUT0 | 유효·PUT1·6.25 유지 |
| 기존 매장 이름만 변경 | 위도37.1234567/경도127.7654321 | 두 필드 stepMismatch·PUT0 | 유효·PUT1·두 값 유지 |

동일 하네스(`d3c5a7a68e87…`)/입력과 불변 기준/수정 빌드의 native 제출 차단은 **2/2→0/2**, 이 고정 집합의 차단 비율은100%→0%(100%p 차이)다. 양쪽 인프라는 성공했고 예상외API·pageerror는 없었다. API fixture의 기능 정확성 비교이며 자연 사용자 오류율·시간 성능이 아니다. **기준에서 DB 숫자가 유실된 것이 아니라 요청 자체가 전송되지 않았다.**

## 원인·선택과 구현

HTML number의 step은 표시 힌트가 아니라 submit 유효성 제약이다. 제공자가 반환한 유효 소수값이 간격에 맞지 않으면 무관한 이름 편집도 막혔다. 원값을 임의 반올림하거나 저장 전에 좌표/도수를 잘라내면 다른 속성까지 바꾸므로 채택하지 않았다.

- 도수/위도/경도의 세 step만 any로 맞춘다. 기존 number 타입·필수 입력·min/max는 유지한다.
- 가격·누적 주문수·회원 스탬프의 정수/최솟값 정책과 기존 API 본문·권한·세션·페이지/정렬은 바꾸지 않는다.
- 기존 Number 변환을 유지하며 원래 GET값을 보존해 전송한다. 제공자 float/double의 저장 정밀도를 변경하거나 임의의 십진수에 무손실 정밀도를 약속하는 변경은 아니다.
- 신규 생성도 허용 범위의 소수를 입력할 수 있다. 범위 밖/빈 입력·정수 가격 위반은 계속 native validation으로 차단하고, 서버 거절은 초안을 유지해 명시적으로 다시 제출한다.

폼 전체에 noValidate를 적용하거나 정수 필드까지 제약을 풀지 않았다. 현재 API의 허용 범위와 웹이 추가한 불필요한 자릿수 제약만 정렬했다. Backend/DB/DTO나 데이터·모델 정책은 해당 레포의 소유이므로 수정하지 않는다.

## 검증 범위와 상태

고정 두 조건의 원값/PUT/목록·재진입 외에 소수 신규 생성, 도수0/100·위경도 경계, 범위 밖·필수·가격0/소수 가격 차단, 서버400 뒤 원값 보존/명시적 재제출을 검증한다. 390px 웹은 좌표 입력/Enter 제출·가로 넘침을 확인한다. 추가 조건은 고정 두 조건의 분모에 합산하지 않는다. 전체 OS 네이티브 입력/스크린리더 인수는 별도다.

Node24 `npm run check`의 저장소 검사·locked 설치·audit(취약점0)·이미지 도구·strict TypeScript·단위62개·프로덕션 빌드·Chromium144개가 통과했다. 새 브라우저 회귀는 위 네 경계이며 이 집계는 서비스 성능이 아니다. 최종100개 파일의 물리 manifest SHA는 `0c2ac55f0433…`, compact 파일 목록 SHA는 `65279714c2eb…`다. 4173의 기존 listener 없음 확인 뒤 자체 preview를 시작했고 검사 종료 후 listener 없음도 확인했다. 독립 전후 하네스는 OS 동적 포트에서 실행·정리했다.

API fixture는 Frontend 검증이며 실제 Backend/DB E2E가 아니다. 별도 실제 서버 비교도 아래 두 조건에서 통과했다. 기존 관리자 저장/다른 초안·권한/세션·페이지 복귀·주문/장바구니·개인 캐시 차폐 회귀는 유지한다. 전체FE03/C04·PostgreSQL DB06과 새 사용자 기능의 완료는 이 작업으로 체크하지 않는다. 최신 head 리뷰/CI·병합/main CI도 별도 게이트다.

## 별도 실제 서버 비교 절차

1. 조정자가 같은 seed·동일 관리자ID/비밀번호·입력 namespace·생성 순서와 한 하네스를 before/after의 별도 폐기 DB에 적용한다. 현재 MySQL은 PostgreSQL 이관 전 회귀 기준으로만 사용하고 원래 사용자DB는 건드리지 않는다.
2. 실제 UI 관리자 로그인200/본인ADMIN을 확인한다. 자체 시연 상품의 도수6.25·기본 필수값, 자체 시연 매장의 위도37.1234567/경도127.7654321을 실제 POST201로 만든다. 각각 GET의 이름/숫자가 요청과 같은지 먼저 확인한다.
3. 현재 목록의 순서/ID로 해당 관리자 페이지를 찾아 편집한다. 이름만 바꾸고 native validity를 기록한다. 유효하면 실제 PUT200을 기다리고, 무효인 기준은 저장 클릭 뒤 PUT0과 서버 원래 이름/숫자 불변을 확인한다. 가짜 성공 응답을 사용하지 않는다.
4. 수정은 목록·재편집의 숫자와 별도 서버 GET의 변경 이름/원숫자를 확인한다. 제출 차단·저장값 손상·인프라 오류를 구분하고 고정 두 조건 각1회로 집계한다. 초기 비회원 auth/me401만 정상 응답으로 구분한다.

원문 실행 도구/보고서·불변100파일·개인 경로·자격 정보는 ignored에 보존한다. 신규 생성/잘못된 범위·거절·390px은 별도 API fixture 근거로 유지한다.

## 실제 서버 전후 결과

동일 Backend jar(`dcb73c35b4db…`)·고정 Recommendation B0·Java 17/MySQL 8.4/Node 24/Chromium을 사용했다. 최초 상품 80개의 같은 seed로 별도 폐기 before/after DB를 만들고 **한 runner에서 같은 관리자 ID/비밀번호·시연 namespace·입력·생성 순서**를 공유했다. 기준 main `9719d6b3`의 불변 웹 100파일(물리 manifest `8e74016ef3b6…`)과 수정 100파일(`0c2ac55f0433…`), 같은 하네스(`ae02f475e780…`)의 크기/SHA를 실행 전에 확인했다.

| 실제 고정 조건 — 각1회 | 기준 | 수정 | 서버 숫자 확인 |
|---|---|---|---|
| 도수6.25의 자체 상품 이름 수정 | stepMismatch/실PUT0·원래 이름 유지 | 실제PUT200·변경 이름 GET/재진입 | 양쪽 모두6.25 유지 |
| 자체 매장7자리 좌표의 이름 수정 | 두 stepMismatch/실PUT0·원래 이름 유지 | 실제PUT200·변경 이름 GET/재진입 | 양쪽 모두37.1234567/127.7654321 유지 |

양쪽에서 실제 관리자 로그인200/ADMIN, 자체 시연 객체의 POST201→GET 허용값을 먼저 확인했다. 제출 차단은 **2/2→0/2**, 고정 집합의 차단 비율은100%→0%(100%p 차이)였다. 양쪽 인프라는 성공했다. 기준의 실패 종료는 native 제출 차단을 뜻하며 DB 숫자 유실이나 실제PUT 실패로 분류하지 않았다. 수정은 두 실제PUT200 후 서버 이름 변경·원숫자와 다시 연 편집 값까지 확인했다.

예상외 API·pageerror·API mocking은 없었고 최초 비회원 auth/me401만 정상 응답으로 분리했다. 웹 프록시→Backend→고정 Recommendation의 기본 목록 BASELINE도 확인했다. 시연 데이터의 실제 서버 정합성 비교이며 자연 오류율·시간 성능·실사용 선호/인기·새 추천 품질 성과가 아니다. 동적 API fixture의 두 조건과 합산하지 않는다.

현재 MySQL API의 PostgreSQL 이관 전 회귀 기준이다. 제공자 DB/ORM 전환 뒤 같은 입력/API·세션/권한 계약으로 다시 확인해야 하며 DB06·전체FE03/C04를 완료로 표시하지 않는다. 제공자의 float/double 범위를 넘어 십진수 전수 정밀도를 보장하거나 현재 숫자 정책을 확장한 것도 아니다.
