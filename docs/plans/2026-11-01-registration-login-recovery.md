# FE03 — 가입 완료와 자동 로그인 실패 복구

## 기준과 고정 조건

기준 main `fb36d1904923e52d5b5a0c2921aa71981603d05d`의 회원가입을 대상으로 했다. Backend의 `POST /api/users`는 201/boolean으로 계정 생성만 완료하고 자동 로그인은 Frontend의 별도 `POST /api/auth/login`이다. 이미 등록된 ID는 서비스 사전 검사에서 0을 반환하고 컨트롤러가 400/BAD_REQUEST로 거절한다. 기존 fixture의 200/User 성공과 중복 409 가정을 이 경로의 정본인 201/boolean·400/BAD_REQUEST에 정렬한 뒤 같은 조건을 비교했다. 정렬 전 준비 실행은 아래 최종 계약의 분모에 합산하지 않았다.

수정 전에 두 조건을 고정했다. 새 ID 중복 확인과 가입은 성공시키고, 첫 자동 로그인에만 HTTP 503 또는 네트워크 중단을 주입한다. 계정 한 개가 만들어지고 아직 로그인하지 않은 상태에서 사용자가 표시된 기본 폼에 비밀번호를 다시 입력해 재제출한다. 가입을 반복하지 않고 실제 로그인으로 복구·원래 목적지 `/cart`에 도달해야 한다.

Node 24·Chromium·같은 프로덕션 웹/API fixture에서 두 조건 모두 계정은 생성됐지만 폼은 가입 모드에 남았다. 기본 재제출이 두 번째 POST /users를 보내 400/BAD_REQUEST에 머물렀고 두 번째 로그인은 실행하지 않았다.

| 고정 실패 조건 — 각 1회 | 기준 웹 복구 위반 | 수정 웹 복구 위반 |
|---|---:|---:|
| 가입 201 뒤 자동 로그인 HTTP 503 | 1/1 | 0/1 |
| 가입 201 뒤 자동 로그인 전송 중단 | 1/1 | 0/1 |

고정 집합의 위반은 2/2 → 0/2다. 기준은 각 조건에서 가입 전송 2회/로그인 전송 1회였고, 수정 뒤에는 가입 전송 1회/로그인 전송 2회로 원래 목적지에 복귀했다. 실제 사용자 오류율·자연 장애율·시간 성능으로 해석하지 않는다. 별도 실패/권한·키보드 회귀를 이 분모에 합산하지 않는다.

## 원인과 선택

가입과 로그인을 하나의 try/result로 처리해 두 번째 단계가 실패하면 첫 단계의 완료 사실도 UI에서 잃었다. 성공한 가입을 롤백할 수 없는데 같은 가입 버튼과 이미 승인된 ID 확인을 다시 사용해 중복 생성 요청을 유도했다.

- 제출 시 자격을 캡처하고 서버 가입 성공 이후의 완료 사실을 로그인 결과와 구분한다. 가입 성공 뒤 로그인만 실패했으면 UI를 로그인 복구로 전환한다.
- 아이디만 로그인 폼에 보존하고 비밀번호·이전 가입 폼/중복 확인은 비운다. 가입은 완료됐고 비밀번호를 다시 입력해 로그인해야 한다고 안내한다. 자동 재시도하거나 비밀번호를 저장소에 보관하지 않는다.
- 가입 요청 자체의 실패/중복 ID 충돌은 가입 완료로 추정하지 않는다. 기존 가입 입력과 사용자의 명시적 재시도·새 ID 중복 확인을 유지한다.
- 가입/로그인 전송 동안 모드·ID 확인·자격 입력을 잠깐 고정해 원래 제출과 다른 자격/모드가 섞이지 않게 한다. 완료/거절 뒤 입력과 키보드 제출을 다시 사용할 수 있다. 다른 탐색 경로로의 이동은 막지 않는다.
- 정상 가입/자동 로그인·기존 로그인·계정별 query 초기화/원래 redirect 계약을 유지한다. 이탈한 컴포넌트의 실패는 다른 경로에 계정 폼을 강제로 열지 않는다.

가입부터 무조건 다시 실행하거나 중복 거절을 성공으로 간주하는 방식은 채택하지 않았다. 이미 존재한 다른 계정을 본인의 가입 성공으로 오인할 수 있다. 가입 응답 자체가 유실돼 생성 여부를 모르는 경우도 이번 수정만으로 완료를 추정하지 않는다. 서버 멱등성·알 수 없는 생성 결과의 조정과 여러 창의 인증 경쟁은 별도다.

## 검증 경계와 진행 상태

두 기본 비교 외에 가입 API 자체의 503/입력 보존·명시적 재시도, ID 경쟁의 사전 검사 400/새 ID 확인, 가입/로그인 pending의 입력·모드 고정과 단일 전송, 복구 로그인 401 뒤 비밀번호 재입력, 늦은 이전 ID 확인, 다른 경로로 이탈한 실패, 다른 계정을 선택한 복구·개인 화면 소유를 확인한다. 390px 웹에서는 username/current-password 자동 완성 속성·비밀번호 재활성화/입력 제한·Enter 제출과 가로 넘침을 확인한다. 실제 비밀번호 관리자 제품과의 외부 통합을 검증했다고 표시하지 않는다.

실제 서버 비교는 각 조건을 새 브라우저 컨텍스트/새 시연 ID로 분리해 조정자가 실행했다. 가입과 복구 로그인은 실제 서버 원응답을 사용하고 첫 자동 로그인에만 503 응답/네트워크 중단을 명시적으로 주입했다. 미등록→가입 201/boolean→등록 사실, 기본 복구 뒤 실제 로그인 200·본인 profile·가입 시도 수를 확인했다. 503 자체는 주입한 실패 응답이며 모든 응답에 mocking이 없었다고 주장하지 않는다.

제품 수정과 선택 회귀는 완료했다. Node 24 `npm run check`에서 저장소 검사·locked 설치·audit(취약점 0)·이미지 도구·strict TypeScript·단위 53개·프로덕션 빌드·Chromium 115개를 확인했다. 중복 거절의 fixture 계약 정정 뒤에는 앱/빌드를 바꾸지 않고 단위 53개·Chromium 115개를 다시 확인했다. 고정 두 조건과 별도 일곱 경계를 구분한다. 테스트 범위이며 서비스 성능 수치가 아니다. 같은 Backend의 실제 비교에서도 고정 두 조건의 위반 2/2 → 0/2를 확인했다. 최신 head 리뷰/CI·병합/main CI는 별도 게이트다. FE03/C04 최종 체크리스트 전체나 추가 R/F 기능을 완료 처리하지 않는다. 기존 README 네 사례는 그대로 보존하며 원인/전후 횟수·절차·검증 집계는 계획/PR에서 관리한다.

수정 웹은 100개 파일을 동결했다. manifest 파일 자체 SHA256은 `38491af885601a14707d322eff36964bfeb097e495d7a7fbd30b62c55f26b5e6`, compact 파일 목록 SHA256은 `197768ef0d2e9973f3ce529ace96b57ece4da2d6070b933f0dcc2e68fde4ae56`이며 두 값의 의미를 구분한다. 실제 비교에는 다시 빌드하지 않은 같은 산출물을 사용했다.

## 실제 서버 비교와 한계

Java 17·MySQL 8.4·Node 24·Chromium의 같은 실행 환경과 초기 80상품의 동일 시연 seed를 사용했다. 서로 다른 두 폐기 전용 DB에서 조건별 ID·이름·비밀번호 입력을 맞췄고 각 조건은 독립된 새 브라우저 컨텍스트에서 한 번 수행했다. 기존 사용자 DB/볼륨이나 외부 계정을 사용하지 않았다.

원인 비교는 같은 Backend jar(SHA256 `f5313650faf31d80800786fcf3d20e439fdb5aadc200fbdc5333ebc0c348e9e8`)와 기준 웹의 compact 파일 목록 `f520671e257e01c1e3069736042fad27fe258ee58473c303074231ff564320e1`/위 수정 웹으로 수행했다. 검증 도구 SHA256은 `db82ebe1fa4d9846fdbd9faedc89a04e7b9ae8e970a32eff4a5dfc1628f1e212`로 전후 동일했다.

| 실제 서버 — 조건마다 1회 | 기준 웹 | 수정 웹 |
|---|---|---|
| 가입 뒤 첫 자동 로그인 HTTP 503 주입 | 가입 [201, 400], 중복 시도 1, 복구 로그인 200 없음 | 가입 [201] 한 번, 중복 0, 복구 로그인 200 한 번·원래 cart 복귀 |
| 가입 뒤 첫 자동 로그인 네트워크 중단 | 가입 [201, 400], 중복 시도 1, 복구 로그인 200 없음 | 가입 [201] 한 번, 중복 0, 복구 로그인 200 한 번·원래 cart 복귀 |

기준의 두 번째 가입은 첫 번째와 같은 본문이며, 첫 201/boolean과 별도 ID 등록 확인이 끝난 뒤 400/BAD_REQUEST로 거절된 경우만 중복 결함으로 분류했다. 다른 400이나 필드 오류를 정상 인프라로 숨기지 않았다. 수정 뒤 두 조건 모두 아이디 보존·비밀번호 초기화·로그인 복구 폼을 확인했고 실제 로그인 이후 본인 세션/profile의 USER와 원래 목적지를 확인했다. 두 실행 모두 인프라 성공·예상외 API 오류/pageerror 없음이었고, 가입/복구 로그인 등 **업무 성공 응답은 mocking하지 않았다**. 최초 자동 로그인의 503 또는 abort 주입은 각각 한 번이다. 웹 프록시→Backend→고정 Recommendation B0의 기본 목록 BASELINE도 확인했다.

고정 두 조건의 복구 위반은 2/2 → 0/2, 해당 집합의 비율은 100% → 0%(100%p 차이)다. 통제한 실패 조건 각각 한 번의 기능 검증이며 실제 사용자 오류율·자연 장애율·성능 개선이 아니다. 별도 새 Backend의 호환 확인이나 추가 fixture 조건을 이 원인 비교의 분모에 합산하지 않는다.

### 검증 계약 가정의 정정

최초 실제 도구는 중복 ID를 일반 DB 충돌 409로 가정해 서버의 사전 검사 400을 인식하지 못하고 인프라 실패로 끝났다. 이때의 부분 결과는 보존하고 최종 2/2 비교나 제품 오류율의 표본으로 합산하지 않았다. 서비스의 `isUsedId` 사전 검사와 컨트롤러의 result 0 → BAD_REQUEST를 다시 확인해 fixture와 도구를 정정했다. 첫 성공/등록 사실·같은 재전송 본문·400/BAD_REQUEST를 함께 확인하는 도구로 새 두 동일 seed DB를 비교한 결과만 위 최종 값으로 채택했다. 앱 코드/동결 빌드는 이 계약 정정으로 바꾸지 않았다.

### 공개 재현 절차와 근거

1. 같은 시연 seed와 조건별 입력을 별도 폐기 before/after DB에 준비한다. 기준/수정 웹의 크기/SHA를 확인해 동결하고 같은 Backend jar에 연결한다.
2. 조건마다 새 컨텍스트에서 미등록 ID를 확인하고 실제 UI로 가입한다. 서버의 201/boolean을 그대로 전달하고 별도 ID 조회로 등록 완료를 확인한다.
3. 첫 자동 로그인에만 HTTP 503 응답 또는 네트워크 중단을 주입한다. 이 실패를 실제 자연 장애로 표현하지 않는다. 표시된 기본 폼에 비밀번호를 다시 입력해 한 번 재제출한다.
4. 같은 가입 본문의 중복 시도/거절과 실제 복구 로그인 200을 구분한다. 성공 시 본인 세션/profile·USER·원래 cart 화면을 확인하고, 중복 거절은 가입 시도 수와 복구 실패로 집계한다.
5. 인프라/계약 오류는 별도 실패로 보존한다. raw 요청 본문·계정·비밀번호·개인 경로는 공개하지 않고, 동일 본문 여부와 error code 등 필요한 판정만 기록한다.

공개 근거는 [가입/로그인 단계 처리](../../src/pages/AccountPages.tsx), [고정 API fixture와 별도 경계 회귀](../../tests/browser/smoke.spec.js), Backend의 [가입 서비스 사전 검사](https://github.com/Pubburi/Backend/blob/main/src/main/java/com/pubburi/pub/model/service/UserServiceImpl.java)·[가입 응답 처리](https://github.com/Pubburi/Backend/blob/main/src/main/java/com/pubburi/pub/controller/rest/UserRestController.java)와 위 절차다. 원문 도구/보고서는 ignored 기록으로 보존한다. FE03/C04 최종 인수·모든 권한/여러 창의 인증 경쟁을 완료한 근거로 확대하지 않는다.
