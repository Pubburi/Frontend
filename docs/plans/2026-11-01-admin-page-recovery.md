# FE03 — 관리자 마지막 페이지 삭제 후 목록 복귀

## 기준과 재현

기준 main `c370645`의 상품·매장·회원·후기·주문 다섯 관리자 탭을 대상으로 했다. 각 탭에 직접 작성한 시연 항목 21개를 두고 `page=2`의 마지막 한 항목을 확인 뒤 삭제했다. DELETE 성공·확인창 닫힘·잔존 20개를 확인한 뒤에도 URL은 page 2, 화면은 `총 20개`와 `등록된 … 정보가 없습니다`에 머물렀다. 서버가 totalPages 1을 반환하면 페이지 이동 UI도 사라졌다.

기준 프로덕션 웹의 100개 파일을 불변 보존했다. compact 파일 목록 SHA256은 `f85cd0695911c35913bc9760d02ce4a84a381839a07da0dd2734c92e760a9c30`이다. Node 24·Chromium·동일 PageResponse fixture로 수정 전후를 비교했으며, API fixture를 실제 Backend 통합 검증으로 표시하지 않는다.

| 고정 조건 — 각 1회 | 수정 전 복귀 실패 | 수정 후 복귀 실패 |
|---|---:|---:|
| 상품 마지막 행 삭제 | 1/1 | 0/1 |
| 매장 마지막 행 삭제 | 1/1 | 0/1 |
| 회원 마지막 행 삭제 | 1/1 | 0/1 |
| 후기 마지막 행 삭제 | 1/1 | 0/1 |
| 주문 마지막 행 삭제 | 1/1 | 0/1 |

고정 다섯 조작의 복귀 실패는 5/5 → 0/5이며, 해당 시나리오 집합의 비율은 100% → 0%(100%p 차이)다. 운영 오류율·자연 지연·성능 개선이나 사용자 통계로 해석하지 않는다. 기준 실행의 실패는 다섯 URL 보정 단언이었고 준비/삭제 인프라 오류는 없었다.

## 원인과 선택

삭제 뒤 활성 목록을 다시 읽어 총수는 갱신했지만 URL page를 새 totalPages와 비교하지 않았다. Pagination은 totalPages가 1 이하이면 표시하지 않으므로 이전/다음 조작만으로 돌아올 수 없었다. 실제 데이터가 없는 경우와 범위 밖 페이지를 같은 빈 상태로 취급한 것이 원인이다.

- 현재 계정·탭·page query key가 성공한 결과이며, 응답 page가 현재 page와 같고 재조회까지 완료된 경우에만 마지막 유효 페이지로 이동한다. 오래된 캐시의 범위 값으로 새 조회를 앞질러 보정하지 않는다.
- 자동 보정은 URL history를 replace한다. 일반 페이지 이동의 history와 탭별 편집 상태는 유지하며, 잘못된 페이지가 뒤로 가기에 반복해서 남지 않게 한다.
- 페이지 범위를 확인/보정하는 중에는 거짓 빈 상태와 범위 밖 Pagination을 숨긴다. 조회 실패는 기존 오류/재시도 상태로, 실제 빈 목록의 page 1은 기존 빈 상태로 유지한다.
- 삭제 시 page를 무조건 1 감소시키는 방식은 채택하지 않았다. 같은 페이지에 다른 항목이 남아 있거나 외부 삭제·직접 링크로 총수가 달라진 경우를 권위 조회 결과로 함께 처리한다. 임의로 총수를 추정하거나 실패를 빈 성공으로 바꾸지 않는다.
- page 변경으로 AdminPanel을 재마운트하거나 폼을 초기화하지 않는다. 현재 입력 초안은 보존한다.

## 검증 경계

수정한 `tests/browser/smoke.spec.js`의 PageResponse 도우미는 page/size에 맞게 items를 자르고 total/totalPages/hasNext를 계산한다. 제품/매장/관리 목록 fixture가 실제 페이지 계약을 제공하도록 보완했으며 잘못된 서버 응답을 정답으로 만들지 않았다.

다섯 삭제 비교 외에 직접 범위 밖 URL의 성공 대기·replace/뒤로 가기·정상 빈 목록, 외부 삭제 후 재조회와 새 초안 보존, DELETE 거절/명시적 재시도, 읽기 실패/명시적 재시도, 늦은 이전 page·tab 조회의 의도 비탈취를 확인한다. 이전 page의 늦은 범위 밖 값이 캐시에 남은 뒤 다시 진입해도 진행 중 새 조회를 기다리고 현재 유효 페이지를 유지하는지 구분한다.

실제 서버 비교는 조정자가 별도로 실행했다. 전후 동일 seed의 별도 폐기 스키마·같은 계정/namespace·같은 Backend를 사용하고 API로 총수를 20k+1에 맞췄다. 다섯 탭 각각 마지막행 DELETE 200과 원래 페이지의 권위 GET/별도 서버 조회로 잔존 총수·빈 items를 먼저 확인한 뒤 유효 URL/20행 복귀를 집계했다. DESC 후기/주문의 마지막 항목은 전용 seed 시연행이며 실행 관리자 본인은 삭제하지 않았다. 기존 사용자 DB 초기화·삭제를 허용하는 절차가 아니다. 원문 계정/값·인증 설정·로그는 공개하지 않는다.

## 상태와 한계

제품 수정과 선택 회귀는 완료했다. Node 24의 `npm run check`가 통과했으며 저장소 검사·locked 설치·audit(취약점 0)·이미지 도구·strict TypeScript·단위 48개·프로덕션 빌드·Chromium 100개를 확인했다. 전체 검사 뒤 늦은 응답/캐시 재진입의 완료 전제를 보강한 두 회귀도 별도로 통과했다. 테스트 범위이며 서비스 성능 수치가 아니다. 별도의 실제 Backend/MySQL 전후 비교에서도 고정 다섯 조작의 복귀 위반 5/5 → 0/5를 확인했고 새 Backend 호환 확인은 별도 0/5였다. 최신 head CI·Codex 리뷰·병합/main CI는 별도 게이트다. 이 수정은 FE03/C04의 한 페이지 경계이며 기존 최종 기능 동등성 체크리스트 전체나 새 필수 기능을 완료 처리하지 않는다. 프로젝트 완료 분모/상태를 변경하지 않는다.

여러 탭·창의 동시 삭제 전체, 삭제 뒤 키보드/스크린리더 전체, 서버에 반영됐지만 쓰기 응답이 유실된 조정은 이번 페이지 보정으로 해결했다고 주장하지 않는다. README의 현재 네 사례는 그대로 보존하며 회귀 횟수·실험 절차·CI 집계는 계획/PR에 둔다.

수정 dist 100개 파일을 동결했다. manifest 파일 자체 SHA256은 `2d7247dd66226151c0814d3771589b69c1dfaa13f8645a35731f252bded743c2`, compact 파일 목록 SHA256은 `082b241d1bb93e408f270e07aab82d5a0bef823b5bba6843cdb5abb3927dc0c2`다. 실제 서버 비교는 이 산출물을 다시 빌드하지 않고 사용했다.

## 실제 서버 전후 비교와 공개 재현 절차

Java 17·MySQL 8.4·Node 24·Chromium의 같은 실행 환경에서 초기 상품 80개인 동일 seed를 각각의 폐기 전용 스키마에 준비했다. 같은 관리자 계정·인증 입력·고정 시연 namespace와 API padding 생성 순서를 사용했다. 공유 사용자 DB/볼륨은 사용하지 않았고, 조정자가 폐기 컨테이너/스키마/동적 포트의 소유를 확인한 뒤 실행했다.

원인 비교는 **같은 Backend jar**(SHA256 `3fbb61317289c8ea6036efa2243898a21faa5b1c21ed45deed66cd30e28be767`)와 기준 main `c370645`/수정 [제품 코드 ef991e9](https://github.com/Pubburi/Frontend/commit/ef991e933b032cb7ca481a83e1371a90ae45bcf1)의 불변 웹으로 수행했다. 새 Backend jar(SHA256 `ddd3ab6f70f2cb2b7d0b296ac85a1acd4f2f68934733babefe9df930211c9a65`)는 세 번째 동일 seed 스키마에서 수정 웹과의 별도 호환 확인으로 분리했다.

| 실제 삭제 — 각 탭/실행 1회 | 총수 변경 | 복귀할 페이지 | 기준 웹/같은 Backend 위반 | 수정 웹/같은 Backend 위반 | 수정 웹/새 Backend 확인 위반 |
|---|---|---|---:|---:|---:|
| 상품 | 81 → 80 | 5 → 4 | 1/1 | 0/1 | 0/1 |
| 매장 | 21 → 20 | 2 → 1 | 1/1 | 0/1 | 0/1 |
| 회원 | 21 → 20 | 2 → 1 | 1/1 | 0/1 | 0/1 |
| 후기 | 21 → 20 | 2 → 1 | 1/1 | 0/1 | 0/1 |
| 주문 | 21 → 20 | 2 → 1 | 1/1 | 0/1 | 0/1 |

수정 전은 다섯 탭 모두 원래 범위 밖 페이지에서 표시 행 0개·거짓 빈 상태로 남았다. 수정 후와 새 Backend 확인에서는 각 탭이 유효 페이지로 복귀했고 표시 행 20개·거짓 빈 상태 없음이 확인됐다. 각 실행에서 실제 DELETE 200은 5건이며, 원래 페이지의 권위 GET과 별도 서버 조회의 총수 -1·빈 items를 모두 확인했다. 세 실행 모두 인프라 성공이었고 예상외 API 오류·pageerror·API mocking은 없었다. 최초 로그인 전 auth/me 401만 정상 비회원 응답으로 구분했다. 기준 실행의 실패 판정은 기대한 페이지 복귀 위반이며 인프라 실패가 아니다. 각 웹 프록시→Backend→Recommendation B0의 공개 기본 목록도 BASELINE임을 확인했다.

원인 비교의 복귀 위반은 5/5 → 0/5, 고정 시나리오 집합의 비율은 100% → 0%(100%p 차이)다. 각 탭 한 번의 관측이며 운영 오류율·자연 부하·성능 개선·전체 FE03/C04 인수로 확대하지 않는다. 새 Backend 확인 0/5는 별도 호환 확인으로, 원인 비교의 분모/표본에 합산하지 않는다. 제어한 늦은 응답·읽기/삭제 실패·초안/캐시·history 경계는 위 API fixture 근거로 구분한다.

공개 재현 순서는 다음과 같다.

1. 같은 seed와 관리자 인증 입력을 별도 before/after 전용 스키마에 준비한다. 웹 파일들의 크기/SHA를 확인해 각각 동결하고 같은 Backend jar에 연결한다.
2. 원래 API로 각 목록의 총수를 확인하고 시연 상품·매장·회원·후기·데모 주문을 추가해 20k+1로 맞춘다. 같은 namespace·생성 순서를 사용하며 DESC 후기/주문은 마지막 전용 seed 시연행을 대상으로 한다.
3. 마지막 페이지의 항목이 한 개인지 조회·화면으로 확인한다. 실행 관리자 본인은 삭제 대상에서 제외한다. UI의 확인창을 통해 실제 DELETE를 한 번 전송한다.
4. DELETE 200·원래 페이지의 후속 GET 200·총수 -1/빈 items를 확인하고 API로 다시 조회한다. 이 조건이 성립한 뒤에만 URL의 유효 페이지 복귀·표시 20행·거짓 빈 상태 여부를 집계한다. 위반은 다음 탭 검증을 막지 않고 인프라 실패와 구분한다.
5. 수정 웹/새 Backend의 호환 확인은 세 번째 동일 seed 스키마에서 따로 수행한다. 실제 API 응답을 가짜로 만들거나 기존 DB를 초기화하지 않는다.

공개 근거는 [현재 query 결과 기반의 페이지 보정 코드](https://github.com/Pubburi/Frontend/blob/ef991e933b032cb7ca481a83e1371a90ae45bcf1/src/pages/AdminPage.tsx), [고정 API fixture 회귀](https://github.com/Pubburi/Frontend/blob/ef991e933b032cb7ca481a83e1371a90ae45bcf1/tests/browser/smoke.spec.js#L2056)와 위 절차다. 실행 도구/원문 결과는 ignored 기록에 보존하며 비밀정보·개인 경로·원문 로그를 공개 문서로 복사하지 않는다.
