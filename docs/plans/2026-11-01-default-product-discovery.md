# R01 — 설문 없이 기본 상품 둘러보기 연결

## 범위와 상태

- 기준 main: `742f9c9`. Frontend는 공개 `/discover` 화면과 프로필·설문 하단의 진입을 제공한다. Backend/Recommendation은 각 저장소에서 기본 목록 계산·호출/대체를 소유한다.
- 제공자 정본: [DEFAULT-RECOMMENDATIONS](https://github.com/Pubburi/Backend/blob/main/docs/DEFAULT-RECOMMENDATIONS.md), [OpenAPI](https://github.com/Pubburi/Backend/blob/main/docs/openapi/default-recommendations.json).
- 이번 증분은 건너뛴/신규 사용자가 실제 기본 상품에 도달하는 R01의 마지막 연결 과제다. 코드·API fixture 확인과 실제 세 서버 통합·리뷰/CI·병합을 구분하며 전체 R01 완료는 조정자가 최종 판정한다.

## 사용자 흐름과 계약

`GET /api/recommendations/default?size=4`는 공개·비개인 조회다. 응답은 `{items: Product7[], source: 'BASELINE' | 'FALLBACK'}`이며 페이지/점수/이유는 없다. 4개를 요청하고 서버 순서대로 현재 상품 정보를 표시한다. 별도의 전체 카탈로그 수집·상품별 부가 조회는 하지 않는다.

1. 프로필의 기본 주류 둘러보기 또는 설문 아래의 같은 링크로 `/discover`에 도달한다. 건너뛰기 확인/저장 뒤에도 바로 선택할 수 있으며, 아직 입력하지 않은 사람도 저장 없이 둘러볼 수 있다.
2. 화면은 취향 설정과 관계없는 기본 주류임을 안내한다. source 코드는 제품 문구로 표시하지 않으며 개인 맞춤·학습된 추천·실제 인기·판매 가능 여부로 표현하지 않는다.
3. BASELINE과 FALLBACK의 유효한 상품 목록은 같은 화면으로 보여준다. 응답 실패는 별도 실패/명시적 다시 불러오기, 빈 성공은 빈 목록/전체 주류 이동으로 구분한다. 새로고침은 기본 목록만 다시 읽는다.
4. 항목은 기존 ProductCard의 현재 가격·도수·이미지와 상세 링크를 사용한다. 공개 목록을 보는 행위는 개인 취향이나 설문 상태를 바꾸지 않는다.

## 공개 목록과 개인 입력 소유

공개 query는 `catalog/default-products/4` 키를 사용하고 계정·설문·찜을 요청에 넣지 않는다. 개인 취향 GET/PUT·초안·NOT_STARTED/SKIPPED/COMPLETED·null/[]/0·저장 중 새 초안·같은 계정 재로그인 HTTP 수명은 변경하지 않는다. 기존 로그인/로그아웃의 캐시 초기화도 유지한다.

목록에서 떠난 뒤 늦은 공개 GET 성공/실패는 그 query의 결과일 뿐, 현재 개인 폼·세션·global notice를 갱신하지 않는다. 저장된 COMPLETED의 필수 범위가 있어도 이 공개 목록이 이를 적용했다고 표시하지 않는다. 미저장 초안의 경로 이탈 보관은 기존 정책처럼 보장하지 않으며, 기본 목록 진입이 자동 저장·초기화·건너뛰기를 수행하지 않는다.

## 검증과 완료 구분

- API 계약 단위: size 기본 4/유한 요청, 계정 선택자와 body 없음, Product7/source의 원형 응답.
- 프로덕션 Chromium fixture: BASELINE/FALLBACK 성공·현재 상세 링크·비회원 공개 접근, SKIPPED 저장 후 목록·신규 NOT_STARTED의 무쓰기 진입·COMPLETED/실제 0/범위 밖 목표 보존, 실패/빈/명시적 재조회·로딩·늦은 공개 응답과 개인 초안/다른 계정 격리·390px 웹.
- 기존 R01의 건너뛰기 취소/초안·저장/초기화·계정 전환/ABA·이상 응답과 F01/포커스·관리자/후기·장바구니 회귀는 전체 검사에서 유지한다.
- 실제 Backend/MySQL/Recommendation 통합은 조정자가 동결한 앱과 제공자 jar로 실행했다. 추천 서버 기동 BASELINE과 추천 프로세스 중단 FALLBACK에서 같은 실제 harness의 여섯 흐름을 각각 통과했다. 이 결과는 fixture의 FALLBACK 성공과 별도로 구분한다.
- FE03/C04 최종 기능 동등성은 [React 계획의 남은 인수](2026-10-31-react-migration.md#남은-인수-경계) 체크리스트로 계속 남긴다. 이 기본 목록 연결만으로 전체 인수를 완료하지 않는다.

Node 24.22.1의 전체 `npm run check`가 통과했다. 저장소 검사·locked npm ci·audit(취약점 0)·이미지 도구·strict TypeScript·단위 48개·프로덕션 빌드·Chromium 80개를 확인했다. 새 기본 목록 흐름은 10개이며, 이후 좁은 웹의 프로필/설문 진입 검증을 같은 390px 조건에 보강해 별도로 통과했다. 테스트 수는 검증 범위이며 서비스 성능이 아니다. 실제 서버 harness도 조정자가 두 모드에서 실행했으며 아래 결과를 별도로 확인했다. 최신 head CI·Codex 리뷰·각 제공자 main·Frontend 병합/main CI는 별도 게이트다.

## 실제 세 서버 연동과 추천 서버 중단

Frontend 제품 코드 `f59a940`의 동결한 프로덕션 웹, 동결한 Backend 후보 jar, 고정한 Recommendation B0 main 버전과 전용 MySQL 8.4를 연결했다. 같은 실제 harness를 추천 프로세스가 켜진 모드와 중단한 모드에 각각 실행했고 API route mocking이나 외부 서비스는 사용하지 않았다.

동결 웹은 100개 파일의 크기·내용 SHA256을 확인한 산출물이다. manifest **파일 자체**의 SHA256은 `9ad42b4c88a04a2ce2ec18fa8526522cb273e5f43e3dfd00eeb8b8ca6f22d9ec`, 내부 `files` 배열을 compact UTF-8 JSON으로 직렬화한 **파일 목록**의 SHA256은 `c3566228e8e53977db7972f308f9cc353c62fbeea884597bf2fddceee44662cd`다. 두 해시의 대상이 다르며, 이번 문서 갱신에서 소스나 dist를 변경·재빌드하지 않았다.

| 실제 사용자 흐름 | 추천 서버 기동 | 추천 프로세스 중단 |
|---|---|---|
| 비회원 기본 목록·Product7·source 코드 미노출 | 통과, BASELINE | 통과, FALLBACK |
| SKIPPED 실제 전체 저장 → 기본 목록 | 도달·상태 보존 | 도달·상태 보존 |
| 기본 항목 → 현재 상품 상세 | 링크·현재 Product7 일치 | 링크·현재 Product7 일치 |
| COMPLETED 저장 → 기본 목록 → 재진입 | 목표 80.25·최대 가격 0·도수 상한 10 보존 | 같은 저장값 보존 |
| 다른 신규 계정 → 기본 목록 | NOT_STARTED·미입력 보존 | NOT_STARTED·미입력 보존 |
| 390px 웹·브라우저/서버 오류 | 넘침·pageerror·예상외 API 오류 없음 | 같은 결과 |

두 실행의 실제 응답 출처는 각각 BASELINE만, FALLBACK만 관측됐다. 첫 로그인 완료 전 auth/me 401은 정상 비회원 응답으로 분리했고 이후 오류를 그 예외로 포함하지 않았다. 추천 서버가 없어도 유효한 상품 목록과 개인 입력 상태를 유지하는 흐름을 확인한 결과다.

실제 통합은 위 정상/프로세스 중단 흐름을 확인했다. 빈 DB·DB 오류·느린/비정상 원격 응답·진행 중 계정 경쟁은 해당 fixture/제공자 검증과 구분하며 여기서 모두 실제 통합했다고 주장하지 않는다. 실제 사용자 선호·인기·구매·모델 품질이나 시간 성능은 측정하지 않았다. 전체 R01의 main 완료는 제공자/Frontend 리뷰·필수 CI·병합과 main CI 이후 조정자가 판정하며 FE03/C04 최종 인수는 계속 미완료다.

## CI의 목록/단건 조회 검증 범위 보완

[CI 실행 41271739965](https://github.com/Pubburi/Frontend/actions/runs/41271739965)에서는 기존 찜 목록 흐름의 크기 단언 하나가 실패했다. trace의 목록 GET 네 건은 모두 `page=1&size=12`였지만 정상적인 상세 단건 GET `/users/me/favorites/902`는 query가 비어 있었다. `startsWith('/users/me/favorites')`가 서로 다른 두 계약을 함께 size 12로 검사한 것이 원인이었다. 새 기본 목록 API 호출은 이 trace에 없고, 이번 증분의 찜 구현 변경도 없다.

URL 변경만 기다렸다 돌아가면 이전 목록의 동일명 버튼이 잠시 남을 수 있어 단건 조회가 실행됐는지에 따라 잘못된 단언이 통과하기도 했다. 실제 상세 h1과 해당 상품의 찜 상태 완료를 확인한 뒤 돌아가는 사용자 흐름으로 기존 단언의 실패를 재현했다. 목록 GET은 정확한 목록 경로에 한정해 크기를 검사하고, 단건 상태 GET의 빈 query는 별도로 확인하도록 수정했다. 현재 상품 상세/찜 상태까지 검증해 회귀의 의미도 보강했다.

timeout·retry·서버 계약·앱 소스를 변경하지 않았고 기존 두 모드 실제 통합에 사용한 dist를 유지했다. 같은 상세 완료 흐름에서 수정 전 단언 실패와 수정 후 통과를 확인했고, 단위 48개·브라우저 80개도 다시 통과했다. 최신 head 원격 CI·리뷰는 별도로 최종 확인한다. 테스트 단언의 범위 수정이며 서비스 성능·사용자 오류율 개선으로 표시하지 않는다.
