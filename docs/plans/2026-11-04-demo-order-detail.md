# F11 — 보호된 데모 주문 상세와 현재 상태 조회

## 범위와 기준

기준 main `2909554`는 [공개 매장 상세 PR #40](https://github.com/Pubburi/Frontend/pull/40)을 제공한다. 데모 주문 생성·Profile의 목록/기존 상태·관리자 완료/삭제는 이미 있었지만, 본인/관리자가 직접 열고 현재 단건을 다시 확인하는 `/orders/:id`와 목록 링크는 없었다. 이 단건 진입·현재 권위/상태·이력 소비를 연결하며 기존 주문 생성/완료 API 자체를 새 성과로 표시하지 않는다.

현재 필수 완료는 **6/20(R01·F01·F03·F05·F06·F09)**다. 전체 F11 판정은 기존 매장과 데모 주문/상태의 실제 근거·최신 리뷰/CI·병합/main 게이트를 조정자가 함께 대조한 뒤 수행한다. 전체 FE03/C04·PostgreSQL 전환·실결제와 구분한다.

제공자의 [API 계약](https://github.com/Pubburi/Backend/blob/main/docs/API-MAP.md)과 [주문 Controller](https://github.com/Pubburi/Backend/blob/main/src/main/java/com/pubburi/pub/controller/rest/OrderRestController.java)를 소비한다. 새 Backend API·주문 상태 쓰기·결제/예약/재고·알림 계약을 추가하지 않는다.

- `GET /api/orders/{id}`는 기존 OrderResponse/ApiResponse를 반환한다. 본인 또는 실제 ADMIN만 조회하며401·403·404와503을 구분한다. 계정 선택 body/query 없이 credentials를 유지한다.
- 주소는 정규 양의 Java int만 허용한다. 잘못된/반복 경로는 다른 번호로 바꾸지 않고 주문 GET 없이 복구를 안내한다. 비회원의 유효 경로는 query까지 로그인 복귀에 보존한다.
- 주문 ID·본인 소유/실제 ADMIN 권위를 대조한다. `N`/`Y`는 데모 접수/처리 완료, 다른 코드는 미확인이다. 완료를 실제 결제·상품 준비·배송으로 표현하지 않는다.
- 서버의 주문 당시 이름·수량·단가·소계·총액과 ORDER_SNAPSHOT/LEGACY_ESTIMATE/미확인 출처를 사용한다. 현재 상품 가격으로 다시 계산하지 않으며0·null·삭제된 상품/탈퇴 회원 이력을 보존한다.

## 현재 계정·조회 수명

Profile의 각 주문과 관리자 주문 행에 상세 링크를 제공한다. 새 상세 진입은 현재 세션 query 객체·계정 ID·경로 key에 속한 새 view를 만들고, 그 view의 독립적인 실제 me 읽기 뒤 단건을 조회한다. 인증 쓰기 중에는 view를 제거한다. 쓰기 실패 뒤 남은 성공 세션 캐시나 쓰기 전에 시작한 HTTP를 새 권위로 재사용하지 않으며, 같은 ID 재로그인/ABA도 새 view로 격리한다.

매장/공개 조회와 별도로 기존 authReadPrivacy의 실제 query/auth 관측을 재사용한다. 현재 주문401은 이전 데이터를 감추고, cold/paused 재검증이나 수동 데이터 갱신으로 풀리지 않는다. 같은 query의 실제 권위 성공 또는 소유 교체로만 관측을 정리한다. 명시적 재로그인은 여전히 같은 auth/query일 때만 개인 캐시를 지우고 원래 경로로 복귀한다. 이전 계정/이탈 view의200/401은 현재 내용·알림·경로를 바꾸지 않는다.

현재 조회의 pending/paused/오류에는 과거 주문 내용을 표시하지 않는다.403·404·503은 각각 권한 없음·없는 주문·읽기 실패로 안내하며 무쓰기 명시 새로고침으로 다시 확인한다. 자동 재시도/오류의 재연결 재전송은 없고, 연결 때문에 시작하지 못한 조회만 연결 후 재개한다. 새로고침 버튼은 같은 DOM/포커스를 유지하고 aria-disabled와 실행 guard로 중복을 막는다. 응답 effect로 다른 조작의 초점을 옮기지 않는다.

## 구현 전에 고정한 필수 인수

기준 소스73파일·production100파일·README, 시나리오와 실제 하네스를 제품 코드 전에 동결했다. 기준 링크/경로 부재는 새 기능 가용성의 기준이며 과거 장애나 시간 성능으로 세지 않는다.

- Profile/Admin 링크·직접 주소·새로고침/Back·키보드, 엄격한 ID 무조회·게스트 로그인 복귀/query.
- 현재 인증 확인/장애·401 차폐/명시 재로그인·403/404/503, 응답 ID/소유 불일치·ADMIN 회수·다른 계정/ABA·불확실 인증 쓰기 뒤 새 확인.
- 대기·중복 읽기·cached/offline 재진입·늦은 이전200/401과 현재 포커스/경로.
- snapshot0/null·가격 출처·삭제 상품/탈퇴 회원·미확인 상태,100자 이름/20자 요청·1280/390px 문자 영역/키보드·저장 거부와 기존 F05/F06/F09/카트 회귀.

실제 하네스는 조정자 소유의 폭별 신규 시연 상품2개와 별도 두 회원/관리자만 사용한다. 같은 legacy 또는 TLS JPA·Recommendation에서 UI로 자체 주문을 만들고 단건 참조를 확인한다. 후보에서는 관리자 기존 완료→본인 현재 상태, 해당 신규 상품만 삭제→당시 이름/가격 보존, 타인403·자체 세션 만료/재로그인, 정확한 자체 주문 삭제→404를 확인한다. 원본80상품·5매장·사용자 DB는 보존하며 인증/업무/대조/정리 쓰기는 각각 구분한다. 비밀 환경값·계정 원문은 보고서/공개 근거에 넣지 않는다.

원 관찰 하네스의 정적 검토에서 만료 후 정확한 자체 주문401을 보안 기대 결과로 식별하도록 정정했다. 성공한 자체 로그아웃 뒤 해당 ID/단계만 허용하고 새 로그인 성공 뒤 해제한다. 타인403/삭제404도 정확한 자체 ID로 제한했으며 API 오류 전체를 무시하지 않았다. 원 바이트/명세와 실행 전 amendment를 보존했고 다른 계약은 바꾸지 않았다.

## README와 최종 게이트

새 필수 단건 연결은 기존 주문/다음 입력·최신 query·파괴적 확인창 포커스·인증 캐시/HTTP 수명 사례의 소유 원칙을 재사용한다. 기존 네 사례보다 강한 독립 문제 해결 근거가 확보된 것으로 보지 않아 본문·순서·코드를 보존하고 현재 기능 한 행만 갱신한다. 검증 수/새 가용성을 성능이나 자연 오류율로 만들지 않는다.

[TESTING](../TESTING.md)의 Node24 전체 검사와 실제 하네스·최신 head 완료 Codex/native·필수 CI·한국어 Squash·main CI/정리를 유지한다. fixture의 제어 오류/경합, 실제 서버와 기존 기능의 재사용·새 상세 제공을 분리해 관측한 결과만 추가한다.

## 작성 검증의 원 실패와 정정

첫 선택 검사는17개 중16개를 통과했고 관리자 역할 회수라는 fixture가 계정 ID까지 바꾸어, 제품의 올바른 재로그인 차폐를403으로 기다린 한 조건이 실패했다. 원 spec/trace/JUnit/로그를 보존하고 같은 관리자 ID의 역할만 USER로 바꾸어 실제 현재 역할 경계를 검사했다. 완료Y도 fixture의 서버 상태에 지속시켜 Back/새로고침을 기존 단방향 완료 계약에 맞췄다. 제품 소스·빌드·실제 관찰 하네스를 바꾸지 않고 같은17조건을 통과했으며 timeout/retry/skip을 늘리지 않았다.

첫 전체 검사는 단위133개·브라우저334개를 통과하고 기존 삭제 이력 한 조건에서 중단됐다. 기존 spec은 삭제된 상품의 현재 링크가 없어야 한다는 뜻으로 행의 모든 anchor를0으로 검사했으나 새 합법 주문 상세 링크까지 포함했다. 원 trace/JUnit/소스·로그를 보존하고 현재 상품 경로의 링크0과 새 정확한 주문 상세 주소를 함께 검증하도록 범위만 명확히 했다. 제품/불변 배포·실제 하네스는 그대로 두며 assertion·기본 보호를 제거하거나 timeout/retry/skip으로 덮지 않았다.

## 최종 로컬 검증과 F11 판정 조건

정정한 기존 단일 이력 검증을 통과한 뒤 Node24.22.1의 전체 `npm run check`를 직렬 재실행해 exit0을 확인했다. 저장소/locked 설치·audit0·이미지 도구·strict TypeScript·단위133개·production 빌드·Chromium335개가 통과했고 새 JUnit의 실제 testcase/실패·오류·skip0을 대조했다. 새 단위5개와 브라우저17조건은 전체 수에 포함하며 별도로 더하지 않는다. 기존 F05/F06/F09·원문 카트·가격/삭제 이력·소수 평점·저장 거부 회귀도 유지했다.

최종 소스78파일·테스트/설정·배포100파일은 실제 인수용 불변 해시와 일치한다. 링크 assertion만 바뀐 뒤에도 제품/배포/실제 하네스는 그대로였고 원 manifest와 새 테스트 manifest를 각각 보존했다. 같은 outputDir runner를 겹치지 않았으며 문서 최종 결과만 추가한다.

F11의 고정 기준은 데모 주문/매장 화면·상태 개선과 실제 재고/예약/결제의 구분이다. 기존 매장 상세의 병합/실제 근거에 새 고객 접수→주문 단건/현재 상태·당시 금액/삭제 이력, 관리자 기존 완료/삭제와 권한/재로그인·기본 키보드 흐름을 연결한다. 실제 두 제공자·두 폭과 최신 리뷰/CI·main 게이트까지 통과하면 이 범위에 남는 구체적인 필수 미구현 동작은 없다고 판단할 수 있다. 현재는 조정자의 실제 근거 대조·최종 판정을 기다리며6/20을 유지한다. 전체 앱 FE03/C04의 나머지 고객/관리자·장애/시각/보조기술 조합은 별개다.

## 실제 두 제공자의 필수 흐름

불변 하네스(SHA-256 `0a2305a512971bca8cbd8603aaaee1995f0082b39e4db4b6c440d638606b4465`)의 기준 실행은 main `2909554`/고정 legacy/Recommendation에서 두 폭의 자체 UI 주문201·기존 단건 참조와 새 경로/Profile 링크의 부재를 확인했다. 새 기능 제공 전 상태이며 과거 오류율 비교가 아니다.

최종 후보 소스78/production100파일과 최종 manifest를 고정한 뒤, 최종 legacy MySQL JAR과 별도 TLS PostgreSQL/JPA JAR·고정 Recommendation에서 각각1280/390px을 통과했다. 기준/최종 Backend JAR은 구분하고, 각각의 실제 주문 생성 응답과 해당 단건 GET·삭제 후 snapshot 대조를 사용한다. 새로운 Backend 기능이나 동일 JAR의 과거 결함 개선으로 표현하지 않는다.
