# 관리자 키보드 편집 진입과 현재 폼 포커스

## 문제·필수 인수 범위

기준 main `f353464`는 R06까지 병합·검증되어 필수 기능 **8/20(R01·R06·F01·F03·F05·F06·F09·F11)**을 완료했다. 전체 FE03/C04 고객·관리자 인수는 별개로 남는다. 남은 기능의 미제공 API를 성공 fixture로 대신하지 않고, 현재 제공된 관리자 CRUD의 기본 키보드 연결 결함을 먼저 보완한다. 독립 최적화·사례 발굴 작업이 아니다.

상품·매장·회원 목록에서 편집 버튼을 Enter로 실행하면 현재 행의 값은 위쪽 폼에 들어가지만 초점은 원래 목록 버튼에 남는다. 다음 Tab도 입력 폼이 아닌 기존 행의 다음 조작으로 이어진다. 화면만 위로 스크롤하는 기존 `edit` 처리가 실제 DOM focus를 옮기지 않은 원인이었다. 새 폼이 생기는 회원과 기존 폼의 값을 바꾸는 상품/매장을 함께 다룬다.

제품 편집 전에 기준 source83/production100파일·README·시나리오/실제 하네스를 동결했다. 동일 기준 production Chromium API fixture의3탭×1280/390px에서 현재 폼 값은 모두 정확했지만 첫 입력 포커스는 **6/6 위반**이었다. 원 spec·JUnit·trace·화면을 보존하고 timeout/retry/skip으로 덮지 않는다. 이는 현재 인수 조건의 정확성 결과이며 과거 운영 장애나 자연 사용자 오류율·시간 성능이 아니다.

## 최소 변경과 소유

- 실제로 집중된 편집 버튼의 키보드/동등한 활성화만 입력 연결 의도를 만든다. 포인터 클릭과 다른 컨트롤에 초점이 있는 script click은 기존 스크롤/포커스 정책을 유지한다.
- 의도는 새 draft revision·실제 인증 query 객체·계정 객체·경로 key·원 trigger에 결속한다. DOM commit에서 한 번 소비하고 현재 ADMIN/인증 상태·연결된 trigger/입력과 아직 같은 초점인지 확인한다.
- 회원의 조건부 폼도 생긴 뒤 첫 이름 입력에 초점을 주고 수직 위치를 즉시 화면 안으로 이동한다. 다음 Tab은 각각 주종·위도·스탬프로 이어진다. 의도가 실패해도 소비해 뒤늦은 응답/렌더가 재사용하지 않는다. 긴 이름의 별도 가로폭 미해결은 아래에 남긴다.
- 서버 조회/저장/삭제 응답 effect에는 새 focus를 추가하지 않는다. 사용자가 Tab/포인터로 이동하거나 다른 편집/계정/경로로 바뀌면 원 의도로 초점을 빼앗지 않는다. 초안·API payload·기존 저장/삭제·페이지 정책을 변경하지 않는다.

전체 key 변화마다 첫 입력에 focus하는 방법은 조회 완료/사용자 입력/경로 복귀에도 초점을 옮길 수 있어 사용하지 않는다. 타이머로 스크롤 완료를 기다리는 방법도 오래된 trigger·새 초안·이미 이탈한 화면과 소유를 분리하기 어려워 사용하지 않는다. 명시 활성화 한 번과 현재 DOM commit만 연결한다.

## 검증·실제 서버 비교

DOM 단위는 현재 revision/auth/account/location·ready·연결/disabled·Tab 이탈과 중복 focus/scroll을 확인한다. Production browser는3탭·1280/390px의 입력 가시성/정확한 원문과 다음 Tab, 포인터/비활성 script, 반복/Space·다른 행·취소 재진입, 보류 중 조회와 새 초안·Tab 이탈 뒤 응답을 구분한다. 편집을 열기만 해서는 업무 API를 쓰지 않는다.

허용100자 ASCII 이름을 넣은 첫 후보 검사는 포커스 보완 후13조건 성공/5조건 문서 너비 실패였다. 별도의 동일 입력 probe로 기준 main과 후보의 너비가 같음을 확인했다.1280px에서 상품1280·매장1589·회원1372,390px에서 상품1133·매장1506·회원1271px였다. 이 기존 테이블/그리드의 긴 이름 폭 문제는 포커스 소유와 원인이 달라 본 PR의 CSS 변경으로 섞지 않는다. 원 실패/trace·전후 좌표/화면을 보존하고 다음 필수 FE03/C04 수정 과제로 남긴다.

390px의 긴 이름은 입력 box도 확장시키므로 전체 가로 가시성은 아직 충족하지 않는다. 긴 값의 전체 원문·첫 focus/수직 가시성·다음 Tab 회귀는 유지하고, 정상 길이의 별도6조건에서 문서/입력 가로폭을 계속 검사한다. 폭 assert를 전체 통과나 단순 도구 오류로 바꾸지 않으며 허용100자 이름의 전체 폭 인수·전체 관리자 화면 완료를 주장하지 않는다. 포커스 PR의 최종 인계 뒤 깨끗한 main에서 이 폭 결함을 독립 단위로 보완한다.

위 수치는 포커스 PR 당시의 미해결 상태다. 뒤의 [FE14 가로폭 보완](2026-11-04-admin-long-name-layout.md)은 현재 main에서 같은 문서폭과 추가 셀 겹침을 먼저 재현하고, 별도 변경·실제 두 DB/필수 검증으로 인수한다. 원 포커스 결과나 실패를 소급해 바꾸지 않는다.

실제 하네스는 자체 ADMIN/회원과 기존 공개 상품·매장 GET, 관리자 회원 GET만 사용한다. 일반 인증·폼 열기/취소와 업무 쓰기를 구분하며 원본 상품/사용자 자료를 변경하지 않는다. 같은 불변 하네스·기준/후보 웹과 각 DB의 같은 Backend/Recommendation을 사용하고,3탭×2폭의 포커스 위반 및 별도 포인터/script 대조를 비교한다. fixture 경합과 실제 결과의 분모를 합산하지 않는다.

최종 Node24.22.1 `npm run check`는 저장소·locked 설치·audit0·이미지·strict TypeScript·단위165개·production 빌드·Chromium381개를 통과해 exit0으로 끝났다. 새 단위7개와 browser24조건은 전체 수에 포함한다. 두 JUnit의 실제 testcase와 실패·오류·skip0/새 시각을 확인했다. 최종 source85/production100·테스트/설정16파일의 해시는 실제 실행용 불변 후보와 같다.

로컬 전체 실행 중 기존 최근 본 상품 흐름 부근에서 preview의 인증 GET 한 건이 개발 프록시로 전달되어 연결 거절 경고가 있었다. testcase는 모두 통과했고 원 로그를 보존했다. 변경 없는 main 빌드/기존 단일 test를 자체 fallback guard에서 한 번 실행해, 공유 서버로 요청을 보내지 않고 같은 인증 GET fallthrough를 재현했다. trace와 guard 시각은 test 종료/teardown 뒤가 아니라 logout click 직후 다음 로그인 주소로 이동하는 본문 안이었다. 정확한 이전 frame/요청의 소유 원인은 더 확인해야 하며 단순히 expected 경고로 취급하지 않는다. 이 test 격리/전환 수명은 별도 필수 수정 과제로 인계하고 focus diff에는 섞지 않는다. 실제 서버의 API0와도 구분한다.

같은 실제 하네스(SHA-256 `6f4ff9375c627ccd7389780ae6e1b3260224d35e54c3f73f1725abc94ee74b27`)에서 각 제공자의 기준/후보에 같은 Backend JAR·고정 Recommendation을 연결했다. 실제 ADMIN 인증·같은 상품/매장/자체 회원의 GET 페이지·선택 항목 전체 hash와 현재 이름 값을 대조했다.

각 실행의 로그인2회·정리 로그아웃2회와 독립 참조 GET6회를 업무 쓰기와 구분했다. 화면 업무 쓰기·예상외 API/pageerror·응답 대체는0이었다. 정상 시드/자체 계정의 실제 좁은 화면과 허용100자명 fixture의 기존 가로폭 한계는 별도다. 두 제공자의 원12조건은 반복 가능한 인수 관측이며 한 서비스의 자연 오류율이나 시간 성능으로 합산하지 않는다.

실제 소유 서버 정리와 세 전용 DB의 원본7범위 전체 행 해시 불변도 확인했다. 원본80상품·5매장·기존 사용자 자료를 편집하지 않았으며 인증과 read-only 폼 진입으로 비교했다.
