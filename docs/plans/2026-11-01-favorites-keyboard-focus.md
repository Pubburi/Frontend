# FE03 — 찜 해제 뒤 키보드 탐색 연속성

## 범위와 관측

기준 main `9c5ac56`에서 키보드로 찜을 해제하면 서버 결과는 반영되지만 다음 조작의 포커스를 잃었다. 새 기능을 추가하거나 F01을 다시 구현하는 작업이 아니라 기존 목록의 접근성·오류 인수 경계를 개선한다. 기존 두 필수 기능 완료 집계와 FE03/C04 최종 인수 상태는 변경하지 않는다.

관측 조건은 Node 24.22.1, Playwright 1.64.1의 Chromium, Vite 프로덕션 빌드와 `/api`의 직접 작성한 fixture다. 시연 상품/계정·응답·키보드 Enter·뷰포트를 고정하고 각 조건을 한 번씩 실행했다. 시간 성능이나 실사용자 오류율을 측정한 실험이 아니다.

| 고정한 조건 | 수정 전 실패 | 수정 후 실패 |
|---|---:|---:|
| 1280px 첫 항목 해제 → 다음 항목 조작 | 1/1 | 0/1 |
| 390px 첫 항목 해제 → 다음 항목 조작 | 1/1 | 0/1 |
| 마지막 항목 해제 → 둘러보기 | 1/1 | 0/1 |
| 마지막 페이지 해제 → 유효한 페이지의 항목 | 1/1 | 0/1 |
| 해제 뒤 권위 GET 실패 → 재조회 | 1/1 | 0/1 |
| DELETE 거절 뒤 보존된 항목 → 재시도 | 1/1 | 0/1 |

같은 여섯 조건의 실패는 6/6 → 0/6이다. 이 작은 고정 시나리오 집합의 실패 비율은 100% → 0%(100%p 차이)이며, 서비스 전체 오류율·사용자 비율·성능 개선율로 일반화하지 않는다. 첫 조건은 목록의 새 데이터가 안정된 뒤에도 실제 활성 노드가 BODY임을 별도로 확인했다.

## 원인과 선택

찜의 HTTP 소유/읽기 세대는 데이터 정합성을 위해 유지해야 한다. 쓰기 완료 뒤 새 세대의 권위 GET을 기다리는 동안 이전 행·버튼을 포함한 목록이 제거되고, 실패나 빈 상태에서도 다른 DOM으로 교체된다. 그러므로 사라진 트리거에 단순 focus를 호출하거나 마지막 상품을 삭제한 뒤 그 노드가 남아 있다고 가정할 수 없다.

- 키보드/보조 입력의 실제 활성 버튼에서 시작한 경우에만 목록 로컬 포커스 의도를 캡처한다. Query 캐시나 계정 저장값에 포커스를 넣지 않는다.
- 조회·빈 상태·실패 중에도 남는 목록 제목을 임시 포커스로 사용한다. `preventScroll`로 아래 행을 조작하다가 화면이 갑자기 위로 이동하지 않게 한다.
- HTTP가 끝나고 새 세대의 조회와 페이지 보정이 끝나면 같은 상품이 보존됐을 때 그 조작, 삭제됐으면 같은 위치의 다음/이전 조작, 빈 목록이면 둘러보기, 읽기 실패면 재조회로 연결한다.
- 사용자가 Tab·다른 포커스·포인터로 이동하거나 창/경로를 떠나면 의도를 폐기한다. 실제 포커스가 여전히 임시 제목에 있는 경우에만 복원한다. 계정/화면 컴포넌트가 사라지면 의도도 사라진다.

오래된 목록을 그대로 남기는 방법은 로딩/오류·페이지 보정·계정 경계의 표시 계약을 함께 바꾸게 된다. 이번에는 기존 권위 조회·HTTP 소유·응답 격리를 유지하고 포커스만 해당 화면의 일시 상태로 관리했다. 조회 결과마다 무조건 autofocus하는 방법도 사용자의 새 선택을 빼앗으므로 사용하지 않았다.

## 회귀와 검증 범위

위 여섯 조건 외에 마지막 행 해제의 이전 행 연결, 응답을 기다리다 Tab으로 이동한 선택 보존, 화면 이탈/재진입의 이전 의도 폐기, 아래 행에서 임시 포커스의 스크롤 보존을 검증한다. 기존 찜의 계정/같은 계정 재로그인·늦은 응답·오류·페이지 및 취향/특성/장바구니·관리자 회귀를 전체 검사에서 유지한다.

실제 서버용 비교 harness는 API mocking 없이 두 실제 상품을 찜에 준비하고, 1280px/390px에서 첫 항목·마지막 항목의 해제를 확인하도록 작성한다. 포커스 실패를 집계한 뒤 다음 독립 동작 전에 직접 포커스를 회복해 기준/수정 빌드의 비교를 계속한다. 실행과 DB/서버 소유는 조정자가 맡으며, 작성·구문검사를 실제 실행으로 기록하지 않는다.

- 구현: 목록 포커스 의도·복원과 관련 브라우저 회귀 작성.
- 로컬 검증: Node 24.22.1의 전체 `npm run check`가 통과했다. 저장소 검사·locked npm ci·audit(취약점 0)·이미지 도구·strict TypeScript·단위 47개·프로덕션 빌드·Chromium 70개를 확인했다. 동일 여섯 조건의 수정 후 실패는 0/6이며, 비탈취/인접 행/스크롤 보존을 포함한 새 키보드 검증은 10개다. 이는 검증 범위이고 서비스 성능 수치가 아니다. README 전체가 기준 main과 동일함도 비교했다.
- 실제 서버 검증: 조정자가 동일 Backend jar·전용 MySQL 8.4·동일 harness로 기준/수정 웹의 실제 연동을 비교했다. 1280px/390px의 첫·마지막 해제 후 포커스 위반은 4/4 → 0/4다. 권위 목록/빈 상태·정상 경로/계정 전환·예상하지 않은 API 오류 없음도 양쪽에서 확인했다. 제어 지연·오류/Tab 이탈의 fixture 경합 검증과 구분한다.
- 원격 CI·리뷰·병합: 최신 head 기준 조정자 게이트. FE03/C04 전체와 모든 브라우저/보조 기술 인수는 미완료다.

## 대표 사례 판단

기존 README의 네 사례를 유지한다. 현재 세 번째 사례인 처리 중 모달 포커스 격리를 더 강한 독립 사례로 대체할 근거까지 확보한 수정은 아니다. 새로운 다섯 번째 사례나 회귀 횟수·실험 절차·CI 집계를 README에 넣지 않는다.

## 실제 서버에서 같은 조작 비교

조정자가 같은 실험용 Backend jar, 전용 MySQL 8.4, Node 24와 동일한 실제 서버 harness를 사용했다. 기준은 main `9c5ac56`의 불변 dist, 수정은 제품 코드 `15cede16`의 동결 dist다. 수정 dist의 파일 목록 manifest SHA256은 `d6c9af0f5e0666021e8dc8a307aa4633826bbbc38529558528d5a9d5563c5ee3`이다. 문서 갱신 전에도 모든 파일의 내용 해시 일치를 확인했고 앱/빌드를 재실행하지 않았다. API route mocking 없이 실제 로그인, 두 상품의 실제 PUT 준비·키보드 DELETE·후속 GET을 수행했다.

| 실제 조작 뒤 활성 포커스 | 기준 웹 | 수정 웹 |
|---|---|---|
| 1280px 첫 항목 해제 | BODY, 위반 | 다음 해제 BUTTON, 연결 |
| 1280px 마지막 항목 해제 | BODY, 위반 | 둘러보기 A, 연결 |
| 390px 첫 항목 해제 | BODY, 위반 | 다음 해제 BUTTON, 연결 |
| 390px 마지막 항목 해제 | BODY, 위반 | 둘러보기 A, 연결 |

포커스 위반은 고정된 실제 조작 네 조건에서 4/4 → 0/4(해당 집합의 위반 비율 100% → 0%, 100%p 차이)다. 기준 실행의 exit 1은 기대한 포커스 실패를 기록한 것이며 인프라 성공 여부는 양쪽 모두 true였다. 실패 후에는 다음 독립 조건을 진행하기 위해서만 직접 포커스를 회복했다. 실제 저장 결과의 권위 목록·빈 상태, 정상 완료 뒤의 경로/계정 전환과 새 화면의 선택 포커스는 양쪽 모두 통과했다. pageerror와 예상하지 않은 API 오류는 양쪽 모두 없었고 최초 로그인 전 auth/me 401만 정상 비회원 응답으로 분리했다.

이는 위 여섯 API fixture 조건과 별도의 실제 저장 연동 결과다. 진행 중 응답에 대한 Tab 이탈·읽기/쓰기 오류 경합의 비탈취는 제어 fixture에서 확인했으며, 실제 서버의 자연 경쟁이나 모든 보조 기술로 확대하지 않는다. 서버 jar는 전후 동일하게 사용했으므로 이 비교가 Backend 후속 의존성 변경의 main 반영·전체 CI 성공을 의미하지도 않는다. 시간 성능·실사용자 오류율·인기/구매 성과는 측정하지 않았다. 최신 Frontend head CI·리뷰·병합/main CI와 전체 FE03/C04 인수는 별도 게이트다.

## CI의 오프라인 테스트 준비 전제 보완

[CI 실행 41262960721](https://github.com/Pubburi/Frontend/actions/runs/41262960721)에서 기존 찜 해제 실패 테스트가 초기 버튼을 찾지 못해 시간 초과했다. 보관된 브라우저 상태는 목록 로딩 중이었고, trace에는 auth/me 200만 있으며 찜 목록 GET이나 DELETE가 없었다. 쓰기 실패를 검증할 항목이 로드되기 전에 offline 이벤트를 주입한 준비 경합이었다.

동결 앱에서 초기 세션 응답을 보류한 뒤 offline → 응답 해제 순서로 같은 상태를 재현했다. 목록 GET과 해제 버튼이 모두 0인 상태가 유지되다가 online 복귀 후 GET 1개와 버튼이 나타났고 DELETE는 전송되지 않았다. 초기 읽기의 보류를 실제 쓰기 결함으로 분류하지 않았다.

테스트는 이미 로드된 항목의 쓰기 실패·재연결을 대상으로 하므로 offline 전에 해제 버튼의 표시·활성 상태를 확인하도록 전제를 명시했다. 503 뒤 항목 보존, 자동 재전송 없음, 명시적 재시도만 허용하는 기존 검증은 유지한다. timeout·retry·실패 처리·앱 소스는 변경하지 않았다. 임시 원인 관측 테스트는 제거하고 기존 테스트 수를 유지했다. 수정한 조건의 독립 실행 세 번과 단위 47개·브라우저 70개가 다시 통과했으며 동결 dist를 재빌드하지 않았다. 이는 테스트 준비 안정화이며 서비스 성능 개선이 아니다.
