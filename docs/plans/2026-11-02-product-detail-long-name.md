# FE09 긴 상품명의 상세 화면 가로 넘침

## 범위·기준

- FE09는 FE03에 연결한 기존 화면 결함의 기술 작업이다. R/F 필수20개에 추가 합산하지 않으며 전체 FE03/C04를 완료로 바꾸지 않는다. 이전 공개 특성 소비 PR #29와 별도 브랜치/PR에서 진행한다.
- 기준 main은 `9ebbe1f78a29d61e14ca4ff2508c9e5450746ed6`이다. 실제 기준 빌드는 PR #29 원본 `96048e3d598ae812132533154148b68b5cf5c52d`에서 만든100파일이며, 병합 main과 추적된 src 전체의 byte가 같음을 확인했다. 병합 후 main CI 성공·ff-only·기존 작업 브랜치 정리가 끝난 뒤 새 작업을 시작했다.
- 제품 CSS를 바꾸기 전에 같은 API/폐기DB/시연 상품의 실제 baseline을 고정했다.390px에서 문서 너비451px로61px 넘쳤고,1280px 대조는1280px였다. 좁은 조건 위반1/1·정상 대조0/1을 따로 관리한다. [측정 정의와 원값](../measurements/2026-11-02-product-detail-long-name.md)을 정본으로 삼는다.

## 문제·원인 좁히기

API와 관리 입력이 허용하는 긴 ASCII 상품명이 줄바꿈되지 않아 상세의 이미지/정보 카드까지 화면 밖으로 넓어졌다. 실제 기준 DOM은 제목397.328125px·정보 카드439.328125px·문서451px였다. 이름이 짧은 기존 fixture로는 이 조건을 드러내지 못했다.

상세의1fr track과 item의 auto 최소폭이 제목의 끊기지 않는 최소 너비를 전달하고 있었다. 고정한 이전 프로덕션 파일에 진단 스타일만 적용해 원인을 분리했다. track/item 최소폭만0으로 두면 카드366px는 맞지만 제목이 남아 문서는430px였다. 제목의 anywhere 줄바꿈만 적용해도 이 표본은 문서390px로 복구됐다. 두 설정을 함께 적용하면 카드366px·제목324px 안에서 두 문자 조각으로 나뉘어 문서390px를 유지했다. 이 진단은 직접 작성한 API fixture이며 실제 Backend 전후와 합산하지 않는다.

## 선택·구현

상세의 세 반응형 track에서 유연한 열을 `minmax(0, 1fr)`로 명시하고 직계 카드의 `min-width: 0`을 허용했다. 제목에는 `overflow-wrap: anywhere`를 적용한다. 제목 줄바꿈은 전체 원문을 보존하고, track/item 설정은 상세 레이아웃이 자식의 기본 최소폭에 의해 바깥으로 넓어지지 않게 한다. 이 표본의 복구에 모든 설정이 각각 필수였다고 주장하지 않는다.

- track 최소폭만 바꾸는 대안은 내부 제목 넘침을 남겨 채택하지 않았다.
- 제목 줄바꿈만으로 이 표본은 복구되지만, 컨테이너와 텍스트의 책임을 함께 명시하는 작은 상세 전용 변경을 선택했다.
- `overflow-x: hidden`, clipping, line clamp, 이름/글꼴 축소는 전체 이름을 가려 수치만 맞추거나 정상 화면을 바꿀 수 있어 사용하지 않았다.

API/상품 이름·가격·수량·장바구니 저장·특성·조회/인증 코드는 바꾸지 않았다. 공유 DB/원본 시드를 변경하지 않았으며 이번 CSS는 상세 컨테이너와 제목에만 적용한다.

## 검증·인수

```bash
npm run test:browser -- --grep '390px 긴 ASCII 상품명'
VITE_API_BASE_URL=/api npm run build
npm run test:browser -- --grep '긴 ASCII 상품명|허용 길이의 긴 상품명'
npm run check
```

같은 이름/390px의 새 production fixture를 기존 dist에 실행해451px 위반1/1을 먼저 재현했다. 실패 screenshot/trace는 ignored에 보존했다. 수정 후 같은 조건과320/720/721/980/1280px의 허용100자명을 포함한6개 경계가 통과했다. 제목 DOM 원문·문자 조각의 실제 좌표와 이미지 alt를 확인하므로 문서 overflow를 숨기거나 이름을 잘라 통과시키지 않는다. 가격·키보드 수량2·기존 Product 저장 형식·검수한 빈 특성·무쓰기 조회도 확인했다.

첫 시도는 sandbox의 loopback bind EPERM으로 시작하지 못했고, 다음 시도는 파일 접두사를 고려하지 않은 grep anchor 때문에 테스트를 찾지 못했다. 이 두 실행 경계는 제품 실패 분모에 넣지 않았고, 접근 경로와 선택식만 바로잡아 위 baseline을 재현했다. 원인 분리 도구의 빈 style 초기화 거절도 별도 보존했으며 제품 소스/성공 결과로 취급하지 않았다. 같은 실패를 무조건 재시도하거나 검사를 우회하지 않았다.

Node **24.22.1** 전체 `npm run check`에서 저장소 검사·locked 설치·audit 취약점 **0**·이미지 도구·strict TypeScript·단위 **76개**·프로덕션 빌드·Chromium **195개**가 통과했다. 원래 API/계정/비동기 흐름을 포함한 필수 검사를 줄이지 않았다. 자체 preview는 종료했고4173은 비었으며, 이후 제품 소스·빌드·설치·하네스를 동결했다.

같은 실제 baseline의 after는2026-11-02 11:24 UTC에 확인했다. 이전 API jar·같은 폐기 DB/상품·동일 Chromium/뷰포트·같은 원래 진단 하네스/너비 산식에서390px 문서 너비는 **451→390px**, 넘친 폭은 **61→0px**였다. 고정 좁은 조건 위반은 **1/1(100%)→0/1(0%)**, **100%p 감소**다. 별도1280px 대조는 문서 **1280→1280px**, 위반 **0/1→0/1**로 유지했다. fixture6개나 추가 불변식 관측을 실제 분모에 합산하지 않고 시간 성능/자연 오류율로 해석하지 않는다.

두 실제 뷰포트의 특성 패널 전체 텍스트가 이전과 같았다. 추가 읽기 전용 하네스는 실제 공개 GET과 제목 전체/모든 문자 조각의 화면 내 수용·가격·키보드 수량2·동일 Product 일곱 필드의 로컬 장바구니·검수한 빈 태그를 확인했다. 업무 API 쓰기·성공 응답 대체·예상하지 않은 API 오류·pageerror는 없었다.390px 실제 full-page 이미지도 확인해 이름 숨김/잘림 없이 전체 제목과 기존 조작이 보이는 것을 확인했다. 이 추가 검사는 주측정의 전후 하네스를 바꾸지 않았으며 전체 화면 인수는 아니다.

조정자 실제 runner의 Backend/preview와 추가 하네스의 Chromium은 종료했다. 폐기 DB/container의 최종 정리는 조정자 소유로 유지한다. 이번 상태는 구현·로컬/선택 실제 검증까지이며, 최신 PR/CI·완료된 리뷰·main 병합은 별도 게이트다.

## 사례·인계

재현과 원인 분리·구현 대안이 있는 실제 결함이지만 기존 네 사례보다 더 강한 독립 영향을 입증하지 못했다. [선정 기록](../case-study-register.md)에 이유를 남기고 README 전체와 네 사례/순서를 보존한다. 전체 화면/기기/보조기술 인수는 이번 한 표본의 범위가 아니다.

검증 후 새 dist100파일·소스·하네스를 동결한다. 실제 결과·PR 초안·최신 head는 ignored 기록에 보존하고, 조정자가 최신 CI·완료 Codex 리뷰·대화 해결·Squash·main CI·ff-only와 병합 브랜치 정리를 담당한다. 비공개 주소·개인 경로·자격정보·원문 로컬 로그/시드는 공개하지 않는다.
